## 一、七层目录：每个文件夹存在的理由

`模板结构.txt` 只有 8 行，但它是整个仓库的骨架：

```
App          ：应用层（业务逻辑）        ← 表达「这台设备要做什么」
Middleware   ：中间件                    ← 可复用的软件栈（RTOS、协议栈、文件系统）
Driver       ：片外外设驱动  bsp_xxx      ← 「板子上焊了什么」
Firmware     ：ARM 内核 + 标准片内外设库  ← 芯片原厂给的，别改
Hardware     ：片上外设驱动  msp_xxx      ← 「芯片内部有什么」
Project      ：工程文件                  ← 编译器怎么把这些源码拼起来
User         ：程序入口                  ← main.c / systick.c / 中断向量实现
```

### 1.1 Driver 和 Hardware 的区别（最容易混）

这是本工程最核心的一条分界线，用一句话记住：

> **Driver 里的东西，是别人焊在板子上的；Hardware 里的东西，是长在芯片里的。**

| | Hardware（`msp_`） | Driver（`bsp_`） |
| --- | --- | --- |
| 面向对象 | 芯片内部集成的外设 | 板子上的元器件 |
| 例子 | USART0、EXTI、TIMER、DMA | LED、独立按键、蜂鸣器、数码管、矩阵键盘 |
| 引脚固定吗 | **芯片定了，改不了**（USART0 就是 PA9/PA10） | **板子改了就得跟着改**（LED 换到别的脚很常见） |
| 本工程文件 | `msp_uart.c`、`msp_exti.c` | `bsp_leds.c`、`bsp_keys.c`、`bsp_buzzer.c` |

**为什么这个区分有价值？** 换一块板子（比如从梁山派换到另一家的 GD32 板），`Hardware/` 一个字都不用改，只改 `Driver/` 里那几张引脚参数表就够了。第 02、03 篇会看到，作者正是为了这件事，把 LED 和按键的引脚从代码里抽成了数组。

### 1.2 Firmware 里有什么

```
Firmware/
├── CMSIS/
│   ├── core_cm4.h / core_cmFunc.h / core_cmInstr.h / core_cm4_simd.h   ← ARM 官方内核接口
│   └── GD/GD32F4xx/
│       ├── Include/  gd32f4xx.h、system_gd32f4xx.h
│       └── Source/ARM/startup_gd32f407_427.s   ← 本工程用的启动文件（ARM 汇编）
└── GD32F4xx_standard_peripheral/
    ├── Include/  gd32f4xx_usart.h、gd32f4xx_timer.h …（37 个外设头文件）
    └── Source/   gd32f4xx_usart.c、gd32f4xx_timer.c …（对应实现）
```

规律很好记：**一个外设一对 `.h`/`.c`，名字就是外设名**。写串口就翻 `gd32f4xx_usart.h`，写定时器就翻 `gd32f4xx_timer.h`——找不到函数时先来这里翻，比在网上搜快。

### 1.3 `gd32f4xx_libopt.h`：库的开关面板

`User/gd32f4xx_libopt.h` 是一张「允许哪些外设头文件被包含」的清单：

```c
#if defined (GD32F450) || defined (GD32F405) || defined (GD32F407) || ...
#include "gd32f4xx_rcu.h"
#include "gd32f4xx_adc.h"
#include "gd32f4xx_can.h"
...
```

它的作用是：**让不同型号的 GD32F4xx 共用同一套库源码**，靠宏 `GD32F407` 决定具体包含哪些。工程里只要 `#include "gd32f4xx.h"`，最终就会走到这里。

> 常见坑：如果新增了某个外设的头文件却报「未定义标识符」，检查它是不是被这个 `#if` 挡掉了。

## 三、从复位到 `main()`：芯片偷偷干了什么

写代码之前先知道自己的代码是怎么被调起来的，出问题才知道该往哪看。

```
① 上电 / 按下复位键
        ↓  硬件把 PC 指向 0x0000_0004（复位向量）
② 启动文件 startup_gd32f407_427.s
   ├─ 建立栈指针（__initial_sp）
   ├─ 把 .data 段从 Flash 搬到 RAM，把 .bss 段清零
   ├─ 给 C 库运行环境做准备
   └─ 调用 SystemInit()
        ↓
③ system_gd32f4xx.c 里的 SystemInit()
   ├─ 打开外部晶振（HXTAL，8 MHz）
   ├─ 配置 PLL，把 8 MHz 倍频到 168 MHz
   ├─ 切换系统时钟源到 PLL
   └─ 更新全局变量 SystemCoreClock = 168000000
        ↓
④ 进入 main()
```

**这条链路解释了三个经常让人困惑的现象**：

| 现象 | 原因 |
| --- | --- |
| 没写一行时钟代码，`SystemCoreClock` 就是 168 MHz | 启动文件里已经调过 `SystemInit()` |
| 全局变量初值不是 0 也不报错 | `.bss` 段被启动文件清零，`.data` 段被从 Flash 搬进 RAM |
| 中断函数名字必须写成 `USART0_IRQHandler` | 中断向量表在 `startup_gd32f407_427.s` 里就把函数名写死了，名字不对就跳不到 |

**中断向量表长什么样**（启动文件的核心内容）：

```asm
__Vectors:
    DCD     __initial_sp        ; 栈顶地址
    DCD     Reset_Handler       ; 复位
    DCD     NMI_Handler
    DCD     HardFault_Handler
    ...
    DCD     EXTI0_IRQHandler    ; ← 中断号对应的入口
    DCD     EXTI3_IRQHandler
    DCD     DMA1_Channel0_IRQHandler
    DCD     USART0_IRQHandler
    ...
```

所以后面写中断处理函数时**名字一个字都不能改**，第 04 篇（`USART0_IRQHandler`）和第 06 篇（`EXTI0_IRQHandler`）还会反复强调这一点。

## 四、中断的统一入口：`gd32f4xx_it.c`

原厂模板把所有中断处理函数集中放在 `User/gd32f4xx_it.c`：

```c
#include "gd32f4xx_it.h"
#include "main.h"
#include "systick.h"

/*!
    \brief    this function handles SysTick exception
*/
void SysTick_Handler(void)
{
    delay_decrement();
}
```

**本工程的实际做法是把中断「就近放」**：串口中断写在 `msp_uart.c`、EXTI 中断写在 `msp_exti.c`、DMA 中断写在 `main.c`（后面会分别看到）。好处是谁的驱动谁维护，坏处是找中断函数得先知道模块。两种做法都合理，只要**别同一个中断在两个文件里各写一份**（会重复定义链接报错）。

`SysTick_Handler` 留在 `gd32f4xx_it.c` 里，因为它是全局时间基准，不属于任何单个外设。

## 六、`systick.c`：整个工程的时间基准

这是第一个提交里最有技术含量的一段代码，后面所有 `delay_1ms()`、非阻塞定时、按键消抖都建立在它之上。

### 6.1 配置：为什么是 1 MHz

```c
void systick_config(void)
{
    /* setup systick timer for 1000000Hz interrupts */
    if (SysTick_Config(SystemCoreClock / 1000000U))
    { // 1us
        while (1) { }
    }
    /* configure the systick handler priority */
    NVIC_SetPriority(SysTick_IRQn, 0x00U);
}
```

`SysTick_Config(ticks)` 的参数是**每多少次内核时钟来一次中断**：

```
SystemCoreClock / 1000000 = 168000000 / 1000000 = 168
```

即「每 168 个内核时钟中断一次」= 每 **1 微秒**中断一次。

| 配置 | 中断频率 | 适合做什么 |
| --- | --- | --- |
| `/1000` | 1 kHz（1 ms 一次） | 只做毫秒延时，中断负担最小 |
| **`/1000000`（本工程）** | **1 MHz（1 μs 一次）** | 毫秒 + 微秒都要，且要能读「当前时刻」 |

**代价要知道**：1 MHz 中断意味着 CPU 每秒被打断 100 万次，每次进中断都是有开销的（压栈、出栈、函数调用）。本工程选它，是为了**同时支持 `delay_1us()` 和「读时间戳」两件事**——串口消抖、`wait_us()` 都靠它。

`NVIC_SetPriority(SysTick_IRQn, 0x00U)` 把 SysTick 设成**最高优先级**，因为它是时间基准，被别的中断拖慢会导致所有延时都不准。

### 6.2 延时：`delay` 变量与中断的配合

```c
volatile static uint32_t delay;      // 软件计数器
volatile static uint64_t us_cnt;     // 微秒时间戳（后续提交加进来的）

void delay_1ms(uint32_t count)
{
    delay = count * 1000;            // 1ms = 1000 个 1us
    while (0U != delay) { }          // 死等，直到被中断改到 0
}

void delay_1us(uint32_t count)
{
    delay = count;
    while (0U != delay) { }
}

void delay_decrement(void)           // 由 SysTick 中断调用
{
    us_cnt++;                        // 时间戳自增

    if (0U != delay)
    {
        delay--;                     // 每次中断减 1
    }
}
```

**运行过程**：

```
调用 delay_1ms(500)
   → delay = 500000
   → while 空转
        ↑ 每 1us 被 SysTick 中断打断一次，delay--
        └ 减到 0 时循环退出，共耗时约 500 ms
```

**三个关键点**：

| 点 | 说明 |
| --- | --- |
| 为什么 `delay` 是 `volatile` | 它在中断里被改、在 `while` 里被读。没有 `volatile`，编译器会认为「循环里没人改它」，直接把循环优化掉或只读一次，`delay_1ms` 立刻返回 |
| 为什么是 `while (0U != delay)` | 无符号变量的惯用写法，明确表达「非零即继续」 |
| 缺点：这是**阻塞式**延时 | 空转期间什么都干不了。第 05 篇的充电流水灯、第 09 篇的数码管扫描，都会改用「读时间戳 + 比较」来替代它 |

### 6.3 `get_us_cnt()`：给后续提交铺的路

```c
uint64_t get_us_cnt(void)
{
    return us_cnt;
}
```

这个函数在 `00d0615`（EXTI 消抖）那次提交里被加进来，之后成了**全工程做非阻塞定时的标准手段**，用法固定成这个形状：

```c
uint64_t start = get_us_cnt();
while ((get_us_cnt() - start) < us)   // 喇叭播放时的等待
{
    ...
}
```

## 七、工程配置：两套并存的构建方式

这个仓库同时支持 **Keil** 和 **VS Code + EIDE** 两种编译方式，配置各有一套：

| 文件 | 给谁用 | 什么时候要改 |
| --- | --- | --- |
| `Project/GD32F407_myLibrary.uvprojx` | Keil MDK | 用 Keil 加/删源文件、改宏定义 |
| `.eide/eide.yml` | VS Code 的 EIDE 插件 | **新增驱动目录时必须加包含路径** |
| `.eide/files.options.yml` | 单文件的编译选项 | 一般不动 |
| `.vscode/tasks.json` | VS Code 编译快捷任务 | 一般不动 |
| `GD32F407_myLibrary.code-workspace` | VS Code 多根工作区 | 一般不动 |

**翻提交会发现一条铁律**：`176bd0a`（LED 封装）、`b4f56b7`（蜂鸣器封装）、`40817c5`（按键封装）……**凡是新增驱动目录的提交，`eide.yml` 一定同时被改**。因为 `.c` 文件能被编译，但 `.h` 文件所在目录必须被加进包含路径，否则 `#include "bsp_xxx.h"` 直接报错。

> **实战提醒**：新建 `Driver/bsp_xxx/` 目录后，要动的通常是两处——`eide.yml` 加包含路径、Keil 工程里加 `.c` 到分组。漏掉任何一处，就会出现「Keil 能编译、EIDE 报错」或者反过来。

### 7.1 `.gitignore` 的两次更新（工程卫生）

这个模块的两次提交（`a0a1a0f` 在 `main`、`acb207a` 在 `dma_usart` 分支）**只改了 `.gitignore`，各 3 行**，属于典型的「工程卫生」提交——**看起来无关紧要，漏了会很烦**。

```diff
 # ===== 其他 =====
 # 忽略编译生成的 .lst、.map 等已在上面涵盖
 # 忽略 clang-format 缓存（如有）
 .clang-format.cache
+
+.workbuddy
```

**加 `.workbuddy` 这件事有两层含义**：

| 层面 | 说明 |
| --- | --- |
| **它是什么** | AI 助手在项目里留下的工作目录（记忆、临时产物等），属于**个人环境的东西**，不是项目源码 |
| **为什么要忽略** | 不忽略的话，每次 `git status` 都会看到一堆无关文件；团队协作时别人也会莫名其妙多出一堆文件 |

**同类应该被忽略的东西**（对照 `.gitignore` 里已有的条目）：

| 类别 | 例子 | 为什么 |
| --- | --- | --- |
| 编译产物 | `build/`、`*.o`、`*.axf`、`*.hex`、`*.lst`、`*.map` | 能重新生成，进版本库只会制造冲突 |
| 工具缓存 | `.clang-format.cache`、`.vscode/`（视团队约定） | 与本机环境绑定 |
| AI/编辑器私有数据 | **`.workbuddy`** | 同上 |
| 系统文件 | `desktop.ini`、`.DS_Store` | 操作系统生成的垃圾 |

> **一个值得养成的小习惯**：`.gitignore` 应该「**跟人走**」——你在开发过程中发现某类文件总是出现在 `git status` 里、且不应该提交，就立刻补进 `.gitignore`。
> 这两次提交正是这个习惯的产物（同一个改动在两个分支各做了一遍，因为两个分支的 `.gitignore` 是各自演进的）。

**为什么 `dma_usart` 分支上也做了一次？** 因为那个分支当时还在独立开发（第 08 篇提过它尚未合并）。**分支自带的配置改动，会在合并时自然带进主线**——如果两个分支都对同一个文件做了「相同语义」的修改，Git 通常能自动合并。

## 七之二、2026-10-10：`main.c` 的一次大瘦身（本篇主旨的"回访"）

**这次整理带来的三条"通用经验"**（比删了什么更重要）：

1. **整理前先写方案**：同一次提交新增了 `Doc/整理操作参考.md`（672 行），
   把 `main.c` 逐行盘点成"行号/名称/类别/问题/目标归属/git 来源"六列表，并**先列出两个高危隐患**
   ——① `msp_adc_get` **符号冲突**（C 不支持重载，链接期报错）；② `DMA1_CH0` **资源争用**。
   **重构之所以能安全进行，是因为先把"会炸的地方"找了出来。**（详见第 20 篇 §14.1）
2. **迁移顺序要"先建后拆"**：这次是**先拆（20:08）后建（20:19 / 20:30）**，中间态**不可编译**。
   之所以没出事，是因为被删的恰好都是"死代码"（调用处早就注释掉了）——**碰巧安全，不是设计安全**（第 27 篇 §3.3）。
3. **"整理"的边界是"只搬不改行为"**：连 `bsp_ntc_init()` 这种空函数都原样保留，
   接口对称性优先于"顺手清理"（第 27 篇 §7）。

`ce1d68e`【整理】做了一件很小但很典型的事：**把 `__weak` 的定义从 6 个文件里提到一个公共头文件**。

```c
// User/util_weak.h（新增，3 行）
#ifndef __weak
#define __weak __attribute__((weak)) // GCC / armclang
#endif
```

| 之前 | 之后 |
| --- | --- |
| `bsp_keys.c` / `bsp_pcf8563.c` / `msp_rtc.c` / `msp_uart.c` / `bsp_adkey.c` / `bsp_ec12d.c` **各自抄一份** `#define __weak …`（6 份重复） | 全部换成 `#include "util_weak.h"`（**7 个文件 ±9/-18 行**） |

**为什么这件事值得单独记一笔**：

1. **它是"同一个东西出现第 3 次就该提出来"这条规则的第 N 次应用**——
   和第 02 篇 `bsp_leds` 的 `leds[]` 参数表、第 28 篇 `bsp_adkey` 的 `adkeys[]` 是**同一类整理动作**；
2. **`__weak` 不只是"某种编译器扩展"**：它是本工程**"驱动层给默认实现、应用层可覆盖"**这套机制的地基
   （第 03 篇 `bsp_keys` 的回调、第 17 篇的 `on_rtc_alarm`、第 29 篇的三个旋钮回调全靠它）；
3. **放在 `User/` 而不是某个 `Driver/` 下**，语义也正确——它**不属于任何器件**，
   而是"整个工程共用的语言层小工具"。

> **命名上的小遗留**：`util_` 前缀是本工程第一次出现（之前只有 `bsp_` / `msp_`）。
> 将来若再攒出几个类似的小工具（`ARRAY_LEN`、`MIN/MAX`、`_Static_assert` 包装），
> 可以一并放进 `User/util_*.h`，**形成一个"工程公共工具"的小角落**——
> 这正是 `模板结构.txt` 里 `Middleware/`（当前为空）预留的位置。

**回到 §1 那张"七层目录"的表**：当时 `App/` 和 `Middleware/` **都是空的**，
`Middleware/` 甚至还是 `模板结构.txt` 里"预留"的位置。

**三次提交之后，两层都填上了**：

| 提交 | 填了哪一层 | 内容 |
| --- | --- | --- |
| `7f55853`（10-16） | **`App/`** | `app.h` + `app_input/` + `app_show/` + `app_test/`（第 33 篇） |
| `7f55853` 同一次 | **`Middleware/taskmanager.c/h`** | 裸机周期任务表（第 33 篇） |
| `09acacc`（10-19） | **`Middleware/FreeRTOS/`** | FreeRTOS 内核 + `FreeRTOSConfig.h`（第 34 篇） |

**现在的真实分层**（对比 §1 的"七层"）：

```
User/          入口与系统级（main.c / it.c / systick.c / main.h / util_weak.h）
   ↓
App/           ★ 应用层：业务（input / show / test）          ← 10-16 新建
   ↓
Middleware/    ★ 中间件：调度（taskmanager）+ RTOS（FreeRTOS）  ← 10-16 / 10-19 新建
   ↓
Driver/        片外器件驱动（bsp_*，15 个目录）
   ↓
Hardware/      片上外设驱动（msp_*，8 个目录）
   ↓
Firmware/      GD32 官方库 + CMSIS
```

**每层的"换掉成本"完全不同**（这正是分层的意义）：

| 层 | 换掉它要改什么 |
| --- | --- |
| `Driver/` | 换一块板子 → **只改引脚参数表**（第 02 篇的 `leds[]` 就是为此） |
| `Hardware/` | 换一颗芯片（GD32 → STM32）→ **改这一层 + Firmware** |
| `Middleware/` | 裸机 → RTOS → **只换调度器，App 层任务函数不用动** ✅ |
| `App/` | 换需求 → 只改业务 |

> **★ `Middleware/` 这一层的价值在 10-19 被真实验证了**：
> `App/` 层那 6 个 `app_show_*_task()` 函数，**从"任务表驱动"换成"FreeRTOS 任务"时，一行都没改**
> （它们本来就是"无参无返回的周期函数"）。
> **这就是"先函数化、再任务化"（第 33 篇 §3.1）的回报。**

### 7.4.1 ⚠️ 但这里出现了一次"分层反转"（第 3 例，也是最结构性的一例）

```c
// Middleware/taskmanager.h
#include "app.h"          // ★ 中间件 include 了应用层
```

**依赖方向反了**：`App → Middleware` 才对，现在变成了 `Middleware → App`。

| 例 | 位置 | 性质 |
| --- | --- | --- |
| 1 | `msp_exti.c` include `bsp_ec12d.h`（第 29 篇） | 片上外设 → 器件驱动 |
| 2 | `msp_exti.c` include `bsp_touch_key.h`（第 31 篇） | 同上 |
| **3** | **`taskmanager.h` include `app.h`（本篇）** | **中间件 → 应用层（跨了两层）** |

**为什么它能工作**：因为 `taskmanager.c` 里的任务表**直接写了具体的任务函数名**：

```c
static TASK tasks_list[] = {
    {app_input_touch_key_task,   STOP, 10,   1},   // ← 直接引用 App 层的函数
    {app_show_digital_leds_task, STOP, 10,   2},
    ...
};
```

**更干净的做法**（本工程已有先例：`msp_uart` 的 `__weak` 回调、`util_weak.h`）：

```c
// Middleware/taskmanager.h —— 不认识任何具体任务
void task_register(task_callback func, uint64_t period);

// App/app.c（或 main.c）—— 由应用层"注册"
task_register(app_input_touch_key_task,   10);
task_register(app_show_digital_leds_task, 10);
```

**好处**：`Middleware/` 可以原样搬到下一个工程（只要那边也提供 `task_register`）。

> **但也要说句公道话**：`taskmanager` 本来就是"裸机遗留物"（第 34 篇遗留 #11 说它"还没拆成独立任务"）。
> **一个"临时方案"有点分层问题是正常的** —— 关键是**别把这种写法当模板复制**。

## 八、排查清单

| 现象 | 优先检查 |
| --- | --- |
| 报「找不到 bsp_xxx.h」 | 新目录没加进 `eide.yml` 包含路径 / Keil 的分组没添加 |
| 报「重复定义 `xxx_IRQHandler`」 | 同一个中断函数在两个文件里都写了，或旧代码没删干净 |
| `delay_1ms(1000)` 几乎不延时 | `delay` 忘了 `volatile`；或 `systick_config()` 没调用 |
| 中断里改了变量，主循环看不到新值 | 变量缺 `volatile`（典型如 `preStas`、`song_stop_flag`） |
| 编译报「未定义标识符」，但函数明显存在 | 对应的外设头文件被 `gd32f4xx_libopt.h` 的 `#if` 挡掉了 |

| 换个板子就要改一堆代码 | 说明引脚没抽成参数表——参考第 02、03 篇的做法 |
