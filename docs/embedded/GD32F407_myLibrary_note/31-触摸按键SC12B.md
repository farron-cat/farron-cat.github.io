## 一、为什么用"触摸芯片"而不是自己测电容

### 1.1 机械按键的四个毛病

本工程已经有四种机械式输入（第 03 篇独立按键、第 10 篇矩阵键盘、第 28 篇 AD 按键、第 29 篇旋转编码器）。机械按键的固有问题：

| 毛病 | 说明 |
| --- | --- |
| **抖动** | 金属触点闭合瞬间会弹跳，**每次都得写消抖**（第 03/06/28 篇都在处理这件事） |
| **磨损** | 触点有寿命（几万~几十万次） |
| **怕水怕尘** | 触点裸露，无法做密封面板 |
| **面板难做** | 必须开孔，影响外观和防水 |

**触摸按键用"电容感应"替掉金属触点**，从原理上把这四条一起解决了。

### 1.2 电容触摸的两条技术路线

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| **自己实现** | 用 GPIO + RC 充放电，测"手指靠近导致的电容变化" | 要精确计时、算法复杂、**抗干扰极难调**（温湿度、电源纹波都会影响） |
| **用触摸芯片**（本板选择） | 芯片内部完成检测、基线校准、去抖动，**MCU 只读结果** | 多一颗芯片，但**开发量小、结果稳定** |

**SC12B 就是后者**：一颗 **12 通道**电容触摸检测芯片，通过 **I2C** 把"哪几个键被摸了"告诉 MCU。

**它为什么这么省 IO**：

```
自己用 GPIO 做 12 个触摸键 → 至少 12 根线（或者用 ADC 矩阵）
用 SC12B            → 3 根线（SCL + SDA + INT），却能读到 12 个键
```

> **这就是"用一根总线换 12 根 IO"的思路**，和第 28 篇 AD 按键（1 根 ADC 线换 3 个键）、第 10 篇矩阵键盘（8 根线换 20 个键）是**同一个目标的不同解法**——**第五章会把它们放在一张表里比**。

### 1.3 板上是怎么做的（硬件侧）

| 要求 | 原因 |
| --- | --- |
| **大面积铺铜做触摸电极** | 手指与铜箔之间的电容**面积越大、变化越明显**，越容易检测 |
| **电极周边不铺铜** | 防相邻通道互相干扰、防"手靠近就误触" |
| **贴亚克力面板** | 保护铜箔不被氧化/短接，同时亚克力本身是**介质层** |

**面板厚度与灵敏度的关系（这是电容触摸设计的核心取舍）**：

| 面板厚度 | 检测难度 | 灵敏度配置 |
| --- | --- | --- |
| 薄（<1 mm） | 容易 | 可以调低（抗干扰更好） |
| 厚（3~5 mm） | 难 | **必须调高**，但太灵敏容易误触 |

> **所以"面板多厚"和"灵敏度写多少"必须一起定。** 本工程 `bsp_touch_key_init()` 里的 `0x79` 就是在调灵敏度，**换面板厚度后这个值要重新调**。

## 二、SC12B 的外部世界

### 2.1 两种通信方式

教材原理图上 SC12B 有**两套**引出：

| 方式 | 引脚 | 信息量 | 有中断吗 |
| --- | --- | --- | --- |
| **I2C** | `TK_SCL` / `TK_SDA` / **`TK_INT`** | ★ **能读到完整 12 位状态（可同时多键）** | ✅ 有 `TK_INT` |
| **BCD 直出** | `TK_BCD0` ~ `TK_BCD3` | 只有 4 位 → **基本只能表示"某一个键"** | ❌ 只能轮询 |

> **信息量的差别是决定性的**：I2C 拿到的是"12 个键的位图"，BCD 拿到的是"一个 4 位编码"。
> **所以能选 I2C 就选 I2C**——本工程选的正是 I2C。

### 2.2 三个设备地址（ASEL 引脚决定）

| ASEL 状态 | 7 位地址 | 写（8 位） | 读（8 位） |
| --- | --- | --- | --- |
| **悬空**（本工程） | **0x40** | 0x80 | 0x81 |
| 低电平 | 0x42 | 0x84 | 0x85 |
| 高电平 | 0x44 | 0x88 | 0x89 |

**两个要点**：

1. **7 位 → 8 位是"左移一位"**：`0x40 << 1 = 0x80`（写），`|1 = 0x81`（读）。
   本工程的 `msp_iic_write_nbyte()` 内部做 `i2c_master_addressing(i2cx, addr << 1, ...)`（第 15 篇讲过），
   **所以代码里传的是 7 位地址 `0x40`** ✅ —— 和 PCF8563 传 `0x51` 是一致的规矩。
2. **为什么要 3 个地址**：为了**在同一块板上挂多片 SC12B**（12 键不够就再挂一片）。
   这和 AD 按键"一根线上挂多个键"是同一类思路：**都是在扩展输入数量。**

### 2.3 六个寄存器

| 寄存器 | 地址 | 作用 | 本工程 |
| --- | --- | --- | --- |
| `SenSet0` | `0x00` | **CIN4 通道**的灵敏度 | 写 `0x79` |
| `SenSetCOM` | `0x01` | **其他通道**的灵敏度 | 写 `0x79` |
| `CTRL0` | `0x02` | 控制 0：响应时间 / 休眠 / 校准策略 | 写 `0x6B`（见 3.2） |
| `CTRL1` | `0x03` | 控制 1 | 写 `0x08`（`0b1000`） |
| **`Output`** | **`0x08`** | ★ **12 位按键状态**（最常读的） | 读 2 字节 |
| `SAMP` | `0x0A` | 原始电容值（调试用） | **没用** |

> **为什么 `SenSet0` 要单独给 CIN4 一个寄存器？** 说明 **CIN4 这个通道比较特殊**（教材原理图里它是 `CMOD` 附近的通道）。
> 参数按"一个通道单独配 + 其余 11 个共用"来组织，**这种"特例 + 通用"的寄存器布局在芯片里很常见**。
> 本工程把两者都写成 `0x79`，**等于"特例也没特殊对待"**——能用，但如果哪天 CIN4 上的按键手感不一样（比如它的电极面积不同），就要单独调它。

## 三、提交 `2bdc21f`：驱动封装

### 3.1 头文件：三类宏

```c
#define TOUCH_KEY_ADDR                         0x40

#define TOUCH_KEY_WRITE_NBYTE(addr, reg, p, n) msp_iic_write_nbyte(addr, reg, p, n)
#define TOUCH_KEY_READ_NBYTE(addr, reg, p, n)  msp_iic_read_nbyte(addr, reg, p, n)
```

**① 读写宏**：把 `msp_iic_*` 包一层，**换总线只改这两个宏**——这是本工程第 4 次用这个模式（前三次：串口 DMA、看门狗二选一、数码管开关，见第 15 篇 §7）。

**② 地址宏——但有两个名字**：

| 宏 | 值 | 用在哪 |
| --- | --- | --- |
| `TOUCH_KEY_ADDR` | `0x40` | **读**状态时用 |
| `SC12B_ADDR` | `0x40` | **写**寄存器时用（4 处） |
| `SC12B_ADDR1` | `0x42` | ❌ **定义了没人用** |
| `SC12B_ADDR2` | `0x44` | ❌ **定义了没人用** |

> **同一个地址有两个名字、而且"写用一个、读用另一个"**，这是移植时留下的冗余。
> 正确做法是只留 `SC12B_ADDR`（或统一成 `TOUCH_KEY_ADDR`），把另外两个做成可选宏或删掉。

**③ 位域宏（CTRL0 的五个字段）**：

```c
#define RTM0  0 / RTM1 1 / RTM2 2 / RTM3 3          // 响应时间模式
#define KVF_STOP_CORREC (1u << 2)   // 按键有效时不校准
#define KVF_50S_CORREC  (0u << 2)   // 按下有效后 50s 开始校准
#define HOLD            (1u << 3)   // 基线保持不校准
#define NOTHOLD         (0u << 3)   // 基线持续校准
#define SLPCYC_LGT  (0u << 5) ... SLPCYC_6R5T (7u << 5)   // 休眠后采样间隔
#define FAST_TO_SLEEP (1u << 4) / SLOW_TO_SLEEP (0u << 4)  // 进入休眠的快慢
```

**这套宏的写法值得学**：每一组都给出"**互斥的一对**"（`HOLD`/`NOTHOLD`、`FAST_TO_SLEEP`/`SLOW_TO_SLEEP`、`KVF_STOP_CORREC`/`KVF_50S_CORREC`），
用的时候按位或拼起来，**意图一看就懂**：

```c
databuf = SLPCYC_3R5T | SLOW_TO_SLEEP | HOLD | KVF_50S_CORREC | RTM3;
```

**但要注意 `(0u << 2)` 这种写法**：`KVF_50S_CORREC` 的值是 0，
**所以"或上去"等于什么都没做**——它在这里的作用是**说明"这个位我选的是 0"**（可读性），
而不是真的设置某位。**读懂这点，才知道它其实等价于 `SLPCYC_3R5T | HOLD | RTM3`。**

**④ 一段"移植残留"（值得单独记住）**：

```c
// 特殊寄存器配置宏 移植自手册示例
#define SDA_OUT_OR_IN   TRISAbits.TRISA0 // 定义 SDA 输入输出方向
#define SCL_OUT_OR_IN   TRISAbits.TRISA2
#define SDA             LATAbits.LATA0
#define SDA_IN          PORTAbits.RA0
#define SCL             LATAbits.LATA2
```

**这一整块是 PIC 单片机的 XC8 编译器语法**（`TRISAbits` / `LATAbits` / `PORTAbits` 是 PIC 的寄存器结构体），
**在 GD32 上根本不存在这些符号**。它们之所以留在文件里、又没报错，是因为：

```
① 只是 #define，没有被任何代码引用 → 不参与编译
② SC12B 的官方"手册示例程序"原本是给 PIC 写的 → 照抄时一起抄了过来
```

> **教训**：**从别的平台移植代码时，"能编译过"不等于"移植干净"**。
> 这类"死宏/死代码"不会报错，但会让人误以为"这里需要操作 SDA 方向"，读到一半去满世界找 `TRISAbits` 是什么。
> **移植的收尾动作应该是：把所有用不到的宏/函数删掉，只留 GD32 的版本**（参考笔记里也指出教材自己的示例是基于 PIC/STC 平台写的）。

### 3.2 `bsp_touch_key_init()`：四次写寄存器

```c
void bsp_touch_key_init(void)
{
    unsigned char databuf;
    databuf = 0x79;                                                        // 灵敏度
    TOUCH_KEY_WRITE_NBYTE(SC12B_ADDR, SenSet0_REG,   &databuf, 1);
    databuf = 0x79;
    TOUCH_KEY_WRITE_NBYTE(SC12B_ADDR, SenSetCOM_REG, &databuf, 1);

    databuf = SLPCYC_3R5T | SLOW_TO_SLEEP | HOLD | KVF_50S_CORREC | RTM3;
    TOUCH_KEY_WRITE_NBYTE(SC12B_ADDR, CTRL0_REG, &databuf, 1);

    databuf = 0b1000;
    TOUCH_KEY_WRITE_NBYTE(SC12B_ADDR, CTRL1_REG, &databuf, 1);
}
```

**把它们算成实际数值**（位域要自己代入验算，别只信注释）：

| 寄存器 | 表达式 | 代入计算 | 结果 |
| --- | --- | --- | --- |
| `SenSet0` | `0x79` | —— | **0x79**（121，值越大越灵敏） |
| `SenSetCOM` | `0x79` | —— | **0x79** |
| `CTRL0` | `SLPCYC_3R5T \| SLOW_TO_SLEEP \| HOLD \| KVF_50S_CORREC \| RTM3` | `0x60 \| 0x00 \| 0x08 \| 0x00 \| 0x03` | **0x6B** |
| `CTRL1` | `0b1000` | —— | **0x08** |

**`CTRL0 = 0x6B` 这四组位的含义**（这是本模块最需要理解的一段）：

| 字段 | 取值 | 含义 | 为什么这么选 |
| --- | --- | --- | --- |
| **RTM3**（bit1~0） | 3 | **6 个采样周期有效 / 4 个周期判无效** | 最保守的档位 → **抗干扰最好**，代价是响应慢一点。开发板不差这点时间 |
| **KVF_50S_CORREC**（bit2） | 0 | **按下期间冻结校准；超过 50 s 后恢复校准** | 折中：既不会"长按几秒就自己松开"，也不会"环境漂移后卡死" |
| **HOLD**（bit3） | 1 | **基线保持（整体不主动校准）** | 环境稳定的场合更可靠；**环境剧变的应用应改用 `NOTHOLD`** |
| **SLPCYC_3R5T**（bit7~5） | 3 | 休眠后**每 300 ms** 采样一次 | 插着 USB 的开发板，偏"响应快" |
| **SLOW_TO_SLEEP**（bit4） | 0 | **75 秒**后才进休眠 | 同上 |

> **「基线」和「校准」是电容触摸最核心的两个概念**（一张图说清）：
>
> ```
> 无手指时的电容值 ────持续跟踪───→ 基线
>                                     │
>                当前值 > 基线 + 阈值 ─┴─→ 判定"有手指"
>
> 为什么必须持续校准？ 因为温湿度/积灰/老化会让"无手指时的电容"缓慢漂移
> 持续校准的致命问题？ 用户一直按着不放 → 芯片把"手指的电容"当成新基线 → 自己把自己判成"松开"
> 所以需要 KVF / HOLD 这两组"什么时候不校准"的策略
> ```
>
> **RTM 其实就是芯片内部的"去抖"**：采 6 个周期才确认，等价于给触摸加了一个时间窗口。
> **所以本篇的按键没有（也不需要）软件消抖**——这一点和机械按键完全不同（对比第 03/28 篇）。

**另外 `0b1000` 是 C 的 GNU 扩展（二进制字面量）**，GCC / armclang 都支持（C23 才标准化）。
**这类"非标准但编译器认"的写法在嵌入式里很常见**，但要注意换编译器（比如某些商用编译器）可能不支持。

### 3.3 ★ 中断处理：2 个字节 → 12 位状态

```c
static uint16_t pre_key_state = 0x0000;

void on_touch_key_interrupt(void)
{
    uint8_t key_data[2];
    TOUCH_KEY_READ_NBYTE(TOUCH_KEY_ADDR, 0x08, key_data, 2);   // 读 Output_REG 起 2 字节
    printf("touch key value: %#x %#x\n", key_data[0], key_data[1]);

    // key_data[0] 0x CH0 CH1 CH2 CH3  CH4 CH5 CH6 CH7
    // key_data[1] 0x CH8 CH9 CH10 CH11 0000
    // state 0x 0000 CH0 CH1 CH2 CH3  CH4 CH5 CH6 CH7  CH8 CH9 CH10 CH11
    uint16_t key_state  = (key_data[0] << 4) | (key_data[1] >> 4);
    uint16_t key_change = key_state ^ pre_key_state;

    for (int8_t i = 0; i < 12; i++)
    {
        if ((key_change >> i) & 0x0001)
        {
            if ((key_state >> i) & 0x0001)
                on_touch_key_press(12 - i);      // 按下
            else
                on_touch_key_release(12 - i);    // 松开
        }
    }
    pre_key_state = key_state;
}
```

**① 位拼接：按寄存器位域布局画一张表**

`Output_REG` 的寄存器是 16 位（读 2 字节），**但只有 12 位有意义**：

| 字节 | bit7 | bit6 | bit5 | bit4 | bit3 | bit2 | bit1 | bit0 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `key_data[0]`（寄存器低字节） | CH0 | CH1 | CH2 | CH3 | CH4 | CH5 | CH6 | CH7 |
| `key_data[1]`（寄存器高字节） | CH8 | CH9 | CH10 | CH11 | *保留* | *保留* | *保留* | *保留* |
| 拼成的 `key_state` | bit15~12 | | | | bit11 | bit10 | bit9 | bit8 |

拼接后：

| `key_state` 的位 | bit11 | bit10 | bit9 | bit8 | bit7 | bit6 | bit5 | bit4 | bit3 | bit2 | bit1 | bit0 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 对应通道 | CH0 | CH1 | CH2 | CH3 | CH4 | CH5 | CH6 | CH7 | CH8 | CH9 | CH10 | CH11 |

**拼接的两步**：

```c
(uint16_t)key_data[0] << 4      // 把 CH0~CH7 从 bit7~bit0 挪到 bit11~bit4
(key_data[1] >> 4)              // 把 CH8~CH11 从 bit7~bit4 挪到 bit3~bit0
|                               // 两段不重叠 → 直接按位或
```

**本工程这一行比教材的写法更好**：

| 版本 | 写法 | 评价 |
| --- | --- | --- |
| 教材示例 | `(((uint16_t)data[0] << 4) & 0xFFF) + ((data[1] >> 4) & 0x0F)` | 用 `+` 表示"拼接"、还多两处掩码 |
| **本工程** | `(key_data[0] << 4) \| (key_data[1] >> 4)` | ✅ 用 `\|`（语义正确）；掩码是冗余的——`key_data[1]` 本来就是 `uint8_t`，`>>4` 后天然只有 4 位；`key_data[0] << 4` 最大 `0xFF0 < 0xFFF` |

> **两种写法结果相同，但 `|` 表达的是"拼接"的意图**。
> 用 `+` 会让人怀疑"会不会进位"——**这种"恰好也对"的写法，一旦位域布局改了就出错**。

**② 边沿检测：`diff = now ^ last`**

```c
uint16_t key_change = key_state ^ pre_key_state;
```

**这是"事件驱动"的经典技巧**（本工程 4 个按键模块都在用，见第 28 篇）：

```
key_change 的某一位 = 1  →  这个键"状态变了"（不是"被按了"）
再看 key_state 那一位：
      1  → 变的是"0 → 1"  →  按下
      0  → 变的是"1 → 0"  →  松开
```

**好处**：同一份代码天然支持"多键同时按下"（一次循环处理所有变化的位），
而且**主循环轮询也不丢事件**——因为比较的是"当前 vs 上次"，中间没扫到也没关系（只要状态没变回去）。

**③ 索引反转：为什么要 `12 - i`？**

`key_state` 的 **bit0 = CH11**、**bit11 = CH0**（见上表），而板子上丝印是 **KEY1 ~ KEY12**：

| 位 | 通道 | 板子丝印 |
| --- | --- | --- |
| bit11 | CH0 | **KEY1** |
| bit10 | CH1 | KEY2 |
| … | … | … |
| bit0 | CH11 | **KEY12** |

所以 **`key` 编号 = `12 - i`**：`i=11 → 1`、`i=0 → 12` ✅ 落在 **1~12**。

> **★ 与教材的差异（本工程修正了教材的一个 off-by-one）**：
>
> | 版本 | 写法 | 得到的编号 |
> | --- | --- | --- |
> | 教材示例 | `tk_on_down(11 - i)` | `i=11 → 0`、`i=0 → 11` → **会出现 "KEY0"，最大只到 11** |
> | **本工程** | `on_touch_key_press(12 - i)` | **1 ~ 12** ✅ |
>
> 板子上丝印是 **KEY1~KEY12**（教材原理图里也是 `KEYTK1`~`KEYTK12`，没有 KEYTR0），
> 所以 **`12 - i` 才是对的**。
>
> **这类"硬件接线决定软件索引"的反转关系，必须在代码里写清理由**——
> 教材的注释只写了 `// bit0 -> key11`，**后来的人看到 `12 - i` 根本不知道为什么减 12**。
> 本工程连注释都没写，**这行是本篇最需要补注释的地方**。

**④ 一个 `static` 变量的双重身份**

```c
static uint16_t pre_key_state = 0x0000;
```

- 它是 `static` → **只在 `bsp_touch_key.c` 内部可见**（不污染全局命名空间）✅
- 它保存"上一次的状态"→ 是**边沿检测的记忆**，本质是**一个最小的状态机**
- **但它是"驱动内部的隐藏状态"**：如果哪天初始化时按键正好被按着，第一次中断就会报一次"按下"事件（因为初值全 0）。
  这类"初值假设"在第 09 篇（`clear_buffer()` 的隐式契约）、第 29 篇（`pre_*` 变量）都出现过，**是本工程反复出现的模式**。

## 四、提交 `dcdda0d`：修复"触摸按键干扰 OLED"

### 4.1 现象与根因

**现象**：触摸按键被按下时，IIC OLED 屏幕出现异常（显示错乱/花屏）。
**提交信息**：「修复触摸按键干扰 oled 屏幕，中断只改变标志，调用 `on_touch_key_interrupt` 移动到 main 中，避免 iic 重入」。

**根因链**（一次典型的"资源被中断抢走"）：

```
主循环正在做的事：
    oled_show_rtc() → bsp_iic_oled_show_picture() → msp_iic_write_nbyte() → 软件 I2C 时序
                                                                              │
                                    时钟：SCL 拉高 → SCL 拉低 → …（每一位都要按时序进行）
                                                                              │
用户手指按了触摸键 ──→ TK_INT 拉低 ──→ EXTI8 中断 ──→ on_touch_key_interrupt()
                                                          │
                                                          ├─ msp_iic_read_nbyte()  ← ★ 又走一遍软件 I2C！
                                                          │     （把主循环那半截时序完全打乱）
                                                          └─ printf(...)           ← ★ 再阻塞 2~3 ms
                                                                              │
主循环恢复 ──→ 它以为"还在按自己的节奏发时序"，其实 SCL/SDA 被中断改过了
                        ↓
                   OLED 收到的字节错位 → 花屏
```

**为什么"重入"会造成这种后果**：

| 原因 | 说明 |
| --- | --- |
| **软件 I2C 没有"事务"概念** | 它就是"翻来覆去地拉高拉低 SCL/SDA"，**中间被抢走后没人告诉它"刚才那半截白做了"** |
| **中断里又发起了一次完整的 I2C 事务** | 于是**两段时序在物理线上交织**——器件看到的是一串谁都不认识的脉冲 |
| **中断里还有 `printf`** | 串口是阻塞发送（115200 下 25 字节 ≈ **2.2 ms**），把中断拉长了上千倍 |

**计算一下 `printf` 的代价**（第 13 篇的方法）：

```
"touch key value: 0x1 0x0\n"  ≈ 25 字节
115200 波特率下每字节 10 位 → 87 μs
25 × 87 μs ≈ 2.2 ms
```

**再看一眼这条 I2C 总线上都挂了谁**（`Doc/硬件信息汇总.md` 4.6 节）：

```
PB6(SCL) ─┬─ U5  ssd1306_12864_i2c（IIC OLED）
          ├─ U8  PCF8563（RTC）
          ├─ U10 LCD FPC / J1 触摸屏座
          └─ H5  外部 I2C 排针
PB7(SDA) ─┴─ （同一串设备）
```

> **同一条总线上有 4 类从机** —— 所以"打断一次 I2C 事务"，受害的可能是**任何一次正在进行的操作**（OLED 刷屏、PCF8563 读时间），
> 而不只是"当前这一个"。**总线是共享资源，"重入"是共享资源的头号敌人。**

### 4.2 修法：中断只置标志，主循环处理

**修法只有三处**（很干净）：

**① `msp_exti.c`：中断里只置标志**

```c
volatile uint8_t g_touch_key_int_flag = 0;      // 新增

void EXTI5_9_IRQHandler()
{
#if USE_EXTI5
    if (exti_interrupt_flag_get(EXTI_5) == SET)
    { exti_interrupt_flag_clear(EXTI_5); g_rtc_int_flag = 1; }        // PCF8563（第 17 篇）
#endif
#if USE_EXTI8
    if (exti_interrupt_flag_get(EXTI_8) == SET)
    {
        exti_interrupt_flag_clear(EXTI_8);
        g_touch_key_int_flag = 1;      // ★ 之前这里是 on_touch_key_interrupt();
    }
#endif
}
```

**② `main.c`：主循环里处理**

```c
while (1)
{
    if (g_rtc_int_flag)                      // PCF8563（第 17 篇，10-10 已修）
    { g_rtc_int_flag = 0; on_rtc_interrupt(); }

    if (g_touch_key_int_flag)                // ★ 新增（10-15）
    { g_touch_key_int_flag = 0; on_touch_key_interrupt(); }

    bsp_188_leds_set_num(bsp_ntc_get_tem());
    ...
}
```

**③ 顺带一次"命名对齐"**：`on_rtc_int()` → **`on_rtc_interrupt()`**，
让两个模块的处理函数名字形一致（`on_xxx_interrupt()`），**并且正好配上"由主循环调用"这个新身份**。

**前后对比**：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 中断里做的事 | 读 I2C（几百 μs）+ `printf`（~2.2 ms） | **只是清标志 + 置一个 `volatile` 变量**（几纳秒） |
| 中断时长 | **毫秒级** | **纳秒级** |
| 还会打断 I2C 吗 | ❌ 会 | ✅ 不会（I2C 只在主循环的"同一条线"上跑） |
| 响应延迟 | 立即 | 多等"一圈主循环"（几毫秒，人感觉不到） |
| 风险 | 花屏 / 总线错乱 / 可能撑爆看门狗 | 无 |

> **代价只有一个：响应变慢"半圈主循环"**。
> 但主循环里最耗时的是 `oled_show_rtc()`（一屏 1024 字节软 I2C，约 38 ms，见第 22 篇），
> **所以最坏情况"按下去 38 ms 后才有反应"**——**人手感觉不出来**。
> **用几十毫秒的延迟换"彻底消除重入"，这笔账永远划算。**

### 4.3 「中断三不做」这条规矩的第二次沉淀

**这是本工程第二次同一类修复**：

| 次序 | 提交 | 时间 | 谁被修 | 症状 |
| --- | --- | --- | --- | --- |
| 1 | `87da7e0` | 10-10 21:29 | **PCF8563 闹钟** | 闹钟中断打断 IIC OLED 数据传输（第 17 篇 §5.5） |
| 2 | **`dcdda0d`** | **10-15 20:25** | **触摸按键 SC12B** | **触摸按键干扰 OLED 屏幕（本篇）** |

**两次的根因、修法、结论完全一样** —— 于是"规矩"可以正式写成清单了：

**★ 中断服务函数（ISR）三不做**

| # | 不做 | 为什么 | 本工程反例 | 正确做法 |
| --- | --- | --- | --- | --- |
| **1** | **不做 I2C / SPI 事务** | 总线是共享资源，**事务被抢占会重入**，器件收到错乱脉冲 | `on_touch_key_interrupt()`（本篇）、`on_rtc_int()`（第 17 篇） | 中断**只置 `volatile` 标志**，主循环再读 |
| **2** | **不做 `printf`** | 阻塞式串口，**每字节 87 μs**，几十字节就是毫秒级 | `EXTI0/EXTI3` 里的 `printf("KEY4_D\n")`（第 06 篇） | 存到环形缓冲，主循环打印（或干脆去掉） |
| **3** | **不做 Flash 擦写 / 长延时** | 擦一个扇区 **45 ms**，远超看门狗窗口 | 第 24 篇指出的"写 Flash 与开看门狗互斥" | 拆成"请求 + 后台执行" |

**统一的替代模式**（本工程已经用了 3 次）：

```c
// 驱动/Hardware 层
volatile uint8_t g_xxx_int_flag = 0;      // 中断与主循环之间的唯一接口
void XXX_IRQHandler(void) { 清标志(); g_xxx_int_flag = 1; }   // 极短

// main.c
while (1)
{
    if (g_xxx_int_flag) { g_xxx_int_flag = 0; on_xxx_interrupt(); }   // 重活都在这儿
    ...
}
```

> **这套模式的名字叫"下半部（bottom half）"**，在 Linux 中断处理、RTOS 的任务/中断通信里是通用概念：
> **"上半部"（中断）只做最紧急的事，把耗时工作"递交"给"下半部"（任务/主循环）。**
> **本工程用 3 个 `volatile uint8_t` 标志，手写了一个最简版的下半部机制。**

**顺便说清"为什么 `volatile` 不能省"**：

```c
volatile uint8_t g_touch_key_int_flag = 0;
```

| 不加 `volatile` 的风险 | 说明 |
| --- | --- |
| **编译器"看不到"这个变量被改过** | 主循环里 `while(1) { if (flag) ... }` 没有任何函数调用修改 `flag`，`-O2` 下编译器**可能把它优化成"只读一次"** → 死循环永远进不去 |
| **中断是"编译器看不见的调用者"** | `volatile` 的唯一作用就是告诉编译器"**别缓存它，每次都从内存读**" |

**但更彻底的写法是加 `_Atomic` 或加内存屏障** —— 因为 `volatile` **不保证原子性和顺序**，
只保证"不去优化"。对本工程的场景（单字节标志、单核 Cortex-M）**够用**，但要知道它的边界在哪。

## 五、★ 本工程 5 种按键输入方案大对照

**到这里，本工程已经有 5 种"读按键"的方案了**。它们是同一道题的 5 种解法，**放在一起看，选型思路立刻清晰**：

| # | 方案 | 笔记 | 键数 | 占用引脚 | 读取方式 | 消抖 | 有中断吗 | 事件类型 | 现状 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | **GPIO 独立按键** | 03 | 4 | **4 根（1 键 1 线）** | GPIO 电平 | 软件（时间戳+位图） | ✅ EXTI0/EXTI3 | 按下/松开 | 启用 |
| 2 | **4×4 矩阵键盘** | 10 | 20 | **8 根（行 4 + 列 4）** | 行列扫描（准双向口） | ❌ **没做** | ❌ | 键值 | **代码已合入，但注释掉** |
| 3 | **AD 按键（ADKEY）** | 28 | 3 | **1 根（ADC 线）** | 读 ADC → 查电阻窗口 | ✅ 30 ms 时间门 | ❌ | 单击/双击/长按 | 启用 |
| 4 | **旋转编码器（EC12）** | 29 | 1 键 + 旋转 | **3 根（A/B/按键）** | EXTI + 相位判断 | ✅ 30 ms 时间门 | ✅ EXTI11/15 | 正转/反转/按下 | 启用 |
| 5 | **触摸按键（SC12B）** | **31** | **12** | **3 根（I2C 2 + INT 1）** | **读 I2C 寄存器** | **芯片内部（RTM）** | ✅ EXTI8 | 按下/松开（可多键） | 启用（最新） |

### 5.1 从这张表提炼的三条结论

**① 「省 IO」的排序：触摸(12 键/3 线) > 矩阵(20 键/8 线) > AD(3 键/1 线) > 旋转(1 键/3 线) > 独立(4 键/4 线)**

**按"每根线能带几个键"算**：

| 方案 | 每根线平均带几个键 | 备注 |
| --- | --- | --- |
| **触摸按键** | **4.0** | 12 / 3（而且外接芯片，**不占 MCU 的额外逻辑**） |
| 矩阵键盘 | 2.5 | 20 / 8 |
| AD 按键 | 3.0 | 3 / 1，**但"1 根线"是 ADC 通道，属于稀缺资源** |
| 独立按键 / 旋转 | 1.0 起 | 简单、直接、无依赖 |

**② 「实现成本」的排序正好相反**

```
独立按键 ──→ 几十行代码，零依赖
AD 按键  ──→ 要占用 ADC 通道 + 分压电阻（硬件设计）
矩阵键盘 ──→ 8 根线 + 准双向口技巧 + 扫描代码
旋转编码器→ 相位判断状态机 + 中断
触摸按键 ──→ 要一颗芯片 + I2C 驱动 + 灵敏度/基线调参
```

**这就是"省 IO 是要付出代价的"** —— 和省 IO 程度正相关。

**③ 「抖动」这条线：越靠后越省心**

| 方案 | 抖动来源 | 处理方式 |
| --- | --- | --- |
| 独立 / 矩阵 / 旋转 | **金属触点的机械弹跳** | 必须自己写（时间戳、位图、时间门） |
| AD 按键 | 机械触点 + ADC 噪声 | 时间门 + 窗口判断 |
| **触摸按键** | **无机械触点**；但有人体静电、电源干扰 | **芯片内部用"RTM 采样周期"解决**——软件一行消抖都不用写 |

> **所以触摸按键这一列"消抖"是空的**——不是漏了，**是芯片替你做完了**。
> **"把复杂留给自己、把简单留给调用方"是驱动设计的好境界**（对比第 30 篇 WS2812 的时序也要靠芯片+软件折腾半天）。

### 5.2 一个必须说明的"现实限制"

这 5 种方案**不是"都可以同时用"**——受引脚冲突限制（第 20 篇的"冲突账本"）：

| 冲突 | 涉及方案 | 结论 |
| --- | --- | --- |
| PE15/PE13/PE11/PE9 | **矩阵键盘 ✕ 188 数码管** | **必须二选一**（第 10 篇 §4.7） |
| PD11/PD13/PD15 | **旋转编码器 ✕ LED4/LED6/LED8** | 需要重新分配（第 29 篇） |
| **PB8** | **触摸按键 INT ✕ 振动马达** | ★ **见第七章第 1 条**（本篇新发现） |

**所以"5 种方案"里，真正能"同时开"的是 1、3、5**（独立按键 + AD 按键 + 触摸按键）——
**而这恰好是"输入端做加法"的正确姿势：优先选互不抢引脚的方案。**

## 七、遗留问题与隐患（★ 这一章建议整章读）

### 7.1 ★ PB8 引脚冲突：触摸按键 INT ✕ 振动马达

**代码把 SC12B 的 `TK_INT` 接到 `PB8`**：

```c
#define EXTI8_PORT      GPIOB
#define EXTI8_PIN       GPIO_PIN_8
```

**但硬件文档里 `PB8` 是电机控制脚**：

PB8(pad61) ── R5 ── Q4(S8050 NPN) 基极
                    发射极 → GND ；集电极 → MOT1.1 ；MOT1.2 → VCC

引脚表第 61 行：| 61 | PB8 | `MOT_CTRL` | R5 → Q4 基极 → 振动马达控制 |

**而且 `practice` 分支的马达驱动写的也是 PB8**（`bsp_vibration_motor`，第 20 篇提过）：

| 位置 | 用途 | 方向 |
| --- | --- | --- |
| 硬件文档 §4.5 | **振动马达控制** | 输出（推 Q4 基极） |
| `practice` 分支 `bsp_vibration_motor` | 振动马达 PWM | 输出 |
| **`main` 分支 `EXTI8`** | **触摸按键 INT** | **输入（中断）** |

**三种可能，必须核对原理图才能定**：

| 可能 | 判断依据 | 后果 |
| --- | --- | --- |
| **① SC12B 是外接模块，用杜邦线接 PB8** | 板上 BOM 里**查不到 SC12B**（见 7.2） | 那它和马达**互斥**：插上触摸模块就不能驱动马达 |
| ② 板上 SC12B 的 TK_INT 就是接 PB8，硬件文档记错了 | 需要看原理图 `TK_INT` 的落点 | 那硬件文档要改 |
| ③ 代码引脚选错了 | 需要看原理图 | 那代码要改 |

> **⚠️ 无论哪种，这条都要正式记进第 20 篇的"冲突账本"（P9）**：
> **`PB8` = 触摸按键 INT（代码）✕ 振动马达 `MOT_CTRL`（硬件文档）**。
> **判据："一个引脚不可能既是'输入中断'又是'输出推马达'"——这是硬冲突，不是隐患。**

### 7.3 EXTI8 配 `GPIO_PUPD_NONE` + 双边沿 → 与 PA0 的 P3 同类隐患

```c
#define EXTI8_PUPD      GPIO_PUPD_NONE      // ★ 无上下拉
#define EXTI8_TRIG_TYPE EXTI_TRIG_BOTH      // ★ 双边沿
```

**对比一下本工程 6 条 EXTI 线的配置**：

| 线 | 引脚 | 上下拉 | 触发 | 是否有隐患 |
| --- | --- | --- | --- | --- |
| EXTI0 | PA0 | **PUPD_NONE** | BOTH | ⚠️ **板上悬空**（P3 问题，第 20 篇） |
| EXTI3 | PC3 | PULLUP | BOTH | ✅ |
| EXTI5 | PB5 | PULLUP | FALLING | ✅ |
| **EXTI8** | **PB8** | **PUPD_NONE** | **BOTH** | ⚠️ **见下** |
| EXTI11 | PD11 | PULLUP | BOTH | ✅ |
| EXTI15 | PD15 | PULLUP | FALLING | ✅ |

**EXTI8 为什么不配上拉？** 大概率是"照抄了 PA0 那一路的参数"。

**风险取决于 `TK_INT` 的电气类型**：

| 如果 TK_INT 是… | `PUPD_NONE` 的后果 |
| --- | --- |
| **开漏输出**（多数触摸/中断芯片都是） | **引脚悬空** → 电平随机漂移 → **在 BOTH 触发下会产生大量伪中断**（和 P3 的 PA0 一模一样） |
| 推挽输出 | 无上下拉也没关系（芯片会主动驱动） |

**处理建议**（按代价从小到大）：

1. **确认 `TK_INT` 的类型**（查原理图/SC12B 手册）——**先做这一步，别猜**；
2. 如果是开漏：把 `EXTI8_PUPD` 改成 **`GPIO_PUPD_PULLUP`**（一行改动），或确认板上已有上拉电阻；
3. **顺便重新评估 `BOTH` 是否必要**：触摸中断通常是"状态变化"→ 若芯片是**低有效脉冲**，用 `FALLING` 就够，
   **`BOTH` 会把"上升沿"也当事件**——如果只是为了"保险"，不如改成与芯片语义一致的单边沿。

> **这个隐患和 PA0 的 P3 是同一类**：**`PUPD_NONE` + `BOTH` + 一个不由 MCU 主动驱动的输入脚**。
> **写笔记时把 6 条线横向摆一张表，才看得出"哪两条是与众不同的"**——这就是"横向汇总"的价值。

### 7.4 include guard 有一个空格 → 保护失效

```c
#ifndef BSP_TOUCH_KEY_H
#define BSP_ TOUCH_KEY_H        // ★ BSP_ 和 TOUCH_KEY_H 之间多了一个空格！
```

**后果分析**（很重要：**这是个"现在不炸、以后可能炸"的 bug**）：

| 场景 | 后果 |
| --- | --- |
| **第一次** `#include "bsp_touch_key.h"` | `#ifndef BSP_TOUCH_KEY_H` 为真 → 进入 → 定义了一个**叫 `BSP_` 的宏**（值为 `TOUCH_KEY_H`） → **`BSP_TOUCH_KEY_H` 始终没被定义** |
| **第二次** 再 include（比如 `main.c` 和 `msp_exti.c` 都包含） | `#ifndef BSP_TOUCH_KEY_H` **仍然为真** → **整个头文件被重新展开一遍** |
| 当前为什么没报错 | 这个头文件里**只有宏定义和函数声明**——重复展开只是"重复声明"，**C 语言允许**，所以编译通过 ✅ |
| **什么时候会炸** | **一旦有人往头文件里加一个变量定义或结构体定义**（比如加 `extern` 之外的全局变量、加一个 `typedef struct`）→ **重复定义 → 编译错误** |
| **还有一个副作用** | `BSP_` 这个宏**跑进了全局命名空间**，**极短的宏名很容易和别人撞车**（尤其以后写 `#define BSP_xxx` 时） |

**正确写法**：

```c
#ifndef BSP_TOUCH_KEY_H
#define BSP_TOUCH_KEY_H       // ← 中间没有空格
...
#endif
```

> **参考笔记里教材的原始代码是 `#ifndef __BSP_TOUCH_KEY_H__`（正确的）**——
> **所以空格是"手抄移植"时引入的笔误**。这类"打错一个字符"的问题，**只有对照原版才能发现**。

### 7.5 `Output_REG` 定义了没用，读的时候用魔法数字 `0x08`

```c
#define Output_REG  0x08             // 触摸状态寄存器输出地址

// 但代码里：
TOUCH_KEY_READ_NBYTE(TOUCH_KEY_ADDR, 0x08, key_data, 2);   // ★ 直接写 0x08
```

**同一个地址，一个用宏（写寄存器时用 `SenSet0_REG` 等）、一个用数字**。
**"定义了却不用"是一种很常见的小腐化**——它让人以为代码很规范，其实关键那行是硬编码的。

### 7.6 处理函数里的 `printf`（现在是主循环，但仍然阻塞）

```c
void on_touch_key_interrupt(void)
{
    ...
    printf("touch key value: %#x %#x\n", key_data[0], key_data[1]);   // ★ 25 字节 ≈ 2.2 ms
}

__weak void on_touch_key_press(uint8_t key)   { printf("key_%d press\n", (int)key); }    // ★ 再 1.2 ms
__weak void on_touch_key_release(uint8_t key) { printf("key_%d release\n", (int)key); }
```

**`dcdda0d` 把它们从"中断里"搬到"主循环里"，风险已经从"会花屏"降到"会卡一下"**——这是**关键的一步** ✅。
**但代价还在**：一次触摸事件最多会打印 **3 条**信息（值 + 按下 + 松开）≈ **3~5 ms**，
而主循环里还有 **OLED 刷屏（38 ms）+ 数码管 + 188 数码管 + NTC** —— **叠起来会让显示有可感的卡顿**。

**改进方向**：

| 方案 | 做法 |
| --- | --- |
| **改成"事件队列"** | 中断/处理函数只把 `(key, event)` 压进环形缓冲，主循环空闲时统一打印 |
| **用调试开关包起来** | `#if TOUCH_KEY_DEBUG` 包住三处 `printf`，量产时一行宏全关掉 |
| **降级为计数** | 不上报每次事件，只维护"最近一次事件 + 次数"，需要时才打印 |

> **这是个典型的"调试代码留在功能代码里"的例子**。本工程已经积了不少类似情况
> （`EXTI0/EXTI3` 里的 `printf`、`on_rtc_int` 里的 `printf`）——
> **值得做一次"调试输出统一治理"**（第 20 篇的"冲突账本"可以再加一栏"调试打印"）。

### 7.7 `msp_exti.c` include 器件驱动 → 分层反转第 2 例

```c
#include "msp_exti.h"
#include "bsp_ec12d.h"        // ← 第 29 篇就指出过
#include "bsp_touch_key.h"    // ← 本篇又加了一个
```

**本工程自己的分层约定**（`模板结构.txt` / `README.md`）：

```
Hardware/  ← 片上外设驱动（msp_*）
Driver/    ← 片外器件驱动（bsp_*）
```

**片上外设不该知道"板外接了什么器件"**。每加一个用中断的器件就往 `msp_exti.c` 里加一个 include，
结果是：**"换个触摸芯片型号"要改 `msp_exti.c`**。

**干净的做法（`msp_uart`/`msp_rtc` 已有先例）**：

```c
// Hardware/msp_exti.c —— 只声明弱回调，不 include 任何 Driver
__weak void on_exti8(void) { }          // 由器件层"认领"
void EXTI5_9_IRQHandler(void)
{
    if (exti_interrupt_flag_get(EXTI_8) == SET) { exti_interrupt_flag_clear(EXTI_8); on_exti8(); }
}

// Driver/bsp_touch_key.c —— 器件层提供实现
void on_exti8(void) { g_touch_key_int_flag = 1; }   // 或直接调用处理
```

**顺带一个观察**：`dcdda0d` 之后，EXTI8 这条线**其实根本不需要 `bsp_touch_key.h` 了**——
因为 Handler 里只剩 `g_touch_key_int_flag = 1;`，**这个变量就定义在 `msp_exti.c` 自己文件里**！
**这个 include 现在是一个"可以顺手删掉的遗留"**。⭐

### 9.2 练习题

1. **改成事件队列**：把 `printf` 换成"环形缓冲 + 主循环统一打印"，体会"中断只入队、打印在后台"带来的时序改善。
2. **加宏替换魔法数字**：把 `12`、`0x08`、`0x0000` 分别换成 `TOUCH_KEY_NUM`、`Output_REG`、`TOUCH_KEY_NONE`，编译验证。
3. **修 include guard**：把 `#define BSP_ TOUCH_KEY_H` 改对，然后**故意在头文件里加一个全局变量**，观察"修之前/修之后"的编译差异——**这是理解 include guard 最好的实验**。
4. **补一个 `bsp_touch_key_get_state()`**：返回当前的 12 位状态（供轮询模式使用），并思考"轮询 vs 中断"在功耗上的差别（教材 §驱动封装 讨论过这个取舍）。
5. **实现长按**：在 `on_touch_key_press/release` 之上加一层状态机（参考第 28 篇 ADKEY 的 7 状态机），实现"长按 1 秒触发某动作"。
6. **印出原始电容值**：读 `SAMP_REG`（`0x0A`）并打印，**摸/不摸**对比数值变化，直观理解"基线与阈值"。
7. **横向核对**：把 `msp_exti.h` 里 6 条线的参数（上下拉/触发/IRQ）抄成一张表，标出"哪两条与众不同"，并说明为什么。
8. **补硬件文档**：把 SC12B 按 `Doc/硬件信息汇总.md` 的格式补一节（器件、引脚、布线要求、ASEL 状态），**并顺手核对 `TK_INT` 到底接哪个脚**。
