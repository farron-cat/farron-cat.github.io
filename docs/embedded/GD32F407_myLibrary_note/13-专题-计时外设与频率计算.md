## 知识点地图

```

├── 计数类外设（本工程全部）
│   ├── SysTick           1 μs 节拍（所有非阻塞定时的时间基准）
│   ├── 基本定时器        TIMER5：1 s 定时中断
│   ├── 通用定时器 PWM    TIMER1_CH2 / TIMER3_CH0（硬 PWM、呼吸灯）
```

## 一、一张图看懂：所有计时外设都是同一个套路

```
            ①源时钟                ②分频                      ③计数
        ┌──────────────┐    ┌──────────────────┐    ┌────────────────────┐
        │ CK_AHB 168MHz│    │ ÷(PSC+1)          │    │ 数到 (ARR+1) 溢出   │
        │ PCLK1  42MHz │───▶│ ÷4096 ÷PSC        │───▶│ 或数到 0 复位       │
        │ PCLK2  84MHz │    │ ÷128 ÷(S+1)       │    │ 或数到 win/0x3F     │
        │ IRC32K 32kHz │    │ ÷16（波特率过采样）│    │ 或数 ARR 个比较      │
        │ RTCCLK 320kHz│    └──────────────────┘    └────────────────────┘
        └──────────────┘              │                        │
                                      ▼                        ▼
                              f_cnt（计数频率）        输出：周期 T / 频率 f / 占空比
```

**记住三句话，剩下的都是套公式**：

1. **每个计时外设都有「一个源时钟」** —— 先查它挂在哪条总线上。
2. **分频永远是「除以 (值+1)」** —— 写进去的寄存器值要 **减 1**（这是最容易错的点）。
3. **数满多少个计数就是多长时间** —— `时间 = 计数个数 ÷ 计数频率`。

## 二、通用公式卡（背这 6 条）

设：
- `f_src` = 源时钟频率（Hz）
- `PSC` = 预分频寄存器值（**实际分频 = PSC + 1**）
- `ARR` = 周期/重装载寄存器值（**实际计数个数 = ARR + 1**）
- `CCR` = 比较值（占空比用）

| # | 公式 | 用途 |
| --- | --- | --- |
| ① | `f_cnt = f_src / (PSC + 1)` | 计数频率（每个计数走多快） |
| ② | `t_cnt = 1 / f_cnt = (PSC + 1) / f_src` | 一个计数代表多长时间 |
| ③ | `T_out = (ARR + 1) × t_cnt = (PSC + 1)(ARR + 1) / f_src` | **溢出周期**（定时中断 / PWM 周期） |
| ④ | `f_out = 1 / T_out = f_src / ((PSC + 1)(ARR + 1))` | **输出频率** |
| ⑤ | `占空比 = CCR / (ARR + 1)` → `CCR = (ARR + 1) × 占空比` | PWM 占空比 |
| ⑥ | 引脚**翻转**（toggle）时：`f_out = f_cnt / 2` | 方波发生（蜂鸣器） |

**两个「隐形」的加法**（本篇反复强调）：

| 位置 | 规律 |
| --- | --- |
| 分频寄存器 | 写 `N-1` 才等于除以 `N`。写 `PSC = 168-1` 表示分频 168 倍 |
| 计数寄存器 | 数 `N` 个计数要写 `ARR = N-1`。写 `ARR = 100-1` 表示数 100 个 |

## 三、时钟底账：动手算之前先弄清「源时钟是多少」

### 3.1 三条时钟路径

```
外部 8 MHz 晶振 (HXTAL)
      │
      ├─ SystemInit() 里 PLL 倍频 → CK_AHB = 168 MHz     ← 系统时钟、SysTick、HCLK
      │        │
      │        ├─ APB1 分频 ÷4 → PCLK1 = 42 MHz          ← APB1 上的外设
      │        └─ APB2 分频 ÷2 → PCLK2 = 84 MHz          ← APB2 上的外设
      │
      └─ RTC 可另选时钟源：HXTAL ÷25 = 320 kHz

内部 32 kHz RC 振荡器 (IRC32K) = 32 000 Hz                ← FWDGT 专用 + RTC 可选
外部 32.768 kHz 晶振 (LXTAL)   = 32 768 Hz                ← RTC 可选（精度最高）
```

### 3.2 外设挂在哪条总线（从库源码核实过）

| 总线 | 频率 | 本工程用到的外设 | 源码依据 |
| --- | --- | --- | --- |
| **CK_AHB** | **168 MHz** | SysTick、GPIO、DMA | — |
| **PCLK1（APB1）** | **42 MHz** | **TIMER1~6、TIMER11~13**、**WWDGT**、**USART2**、**UART3/4**、USART1 | `RCU_APB1EN_*` |
| **PCLK2（APB2）** | **84 MHz** | **TIMER0/7**、TIMER8~10、**USART0**、USART5、SYSCFG | `RCU_APB2EN_*` |
| **备份域** | 由 RTCCLK 驱动 | **RTC** | `RCU_BDCTL_RTCEN` |
| **独立振荡器** | 32 kHz | **FWDGT** | —— |

> **一个实用推论**：**「同一个波特率、不同串口，分频值不一样」**就是因为 USART0 在 APB2（84 MHz）、USART2 在 APB1（42 MHz）。见 5.9 节。

### 3.3 定时器为什么要「倍频」——以及它到底是怎么统一的

```c
// 时钟倍频(全局配置 所有定时器都是168Mhz)
rcu_timer_clock_prescaler_config(RCU_TIMER_PSC_MUL4);
```

这一行的目的一句话：**让「定时器时钟」和「系统主频」相等，这样算参数时只需要记住一个数 168 MHz**。

**但它的实现规则比想象中讲究**（直接看库里的注释，`gd32f4xx_rcu.h` 第 962~969 行）：

> `RCU_TIMER_PSC_MUL4`：如果 **APB1PSC/APB2PSC ∈ {0b0xx(÷1), 0b100(÷2), 0b101(÷4)}**，则 `CK_TIMERx = CK_AHB`；
> 否则 `CK_TIMERx = 4 × CK_APBx`。

**套到本工程**：

```
APB1PSC = ÷4 (0b101) ✔ 在允许集合里
APB2PSC = ÷2 (0b100) ✔ 在允许集合里
        ↓
CK_TIMERx = CK_AHB = 168 MHz   ← 所有定时器（APB1 上的和 APB2 上的）都是 168 MHz
```

**这就是「所有定时器都是 168 MHz」的准确依据**，也解释了教材那张表里的「倍频」列为什么 APB1 写 ×4、APB2 写 ×2 —— 两条总线的分频比不同，但**最终结果都是 168 MHz**。

⚠️ **边界提醒**（值得记住的反例）：如果哪天把 APB1 分成 ÷8，那么它就不在允许集合里，`CK_TIMERx = 4 × 42/2 = ...` 会变成另一个值，**所有定时器参数都得重算**。**改时钟树 = 所有基于时间的参数全部重算**，这是条铁律。

## 五、逐个拆解（含验算）

### 5.1 SysTick：全工程的时间基准

```c
/* setup systick timer for 1000000Hz interrupts */
if (SysTick_Config(SystemCoreClock / 1000000U))
{ // 1us
    while (1) { }
}
```

```
reload = SystemCoreClock / 1000000 = 168 000 000 / 1 000 000 = 168
        ↓
每 168 个内核时钟中断一次 → 中断周期 = 168 / 168 MHz = 1 μs
```

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 源时钟 | CK_AHB = 168 MHz | SysTick 用的是**内核时钟**，与 APB 无关 |
| 重装载 | `168 - 1 = 167`（库内部完成） | `SysTick_Config(168)` 会自己写成 167 |
| 中断周期 | **1 μs** | 也就是 `us_cnt` 每 1 μs +1 |

**⚠️ 一个容易忽略的限制**：SysTick 是 **24 位**递减计数器。

```
最大重装载 = 0xFFFFFF = 16 777 215
最长中断周期 = 16777215 / 168 MHz ≈ 99.9 ms
```

**所以：`delay_1ms(1000)`（1 秒）不是 SysTick 数了 1 秒**，而是**软件计数器 `delay` 累加了 100 万次**：

```c
void delay_1ms(uint32_t count)
{
    delay = count * 1000;       // 1 ms = 1000 个 1 μs
    while (0U != delay) { }     // 每次中断减 1，减到 0 才退出
}
```

> **结论**：**SysTick 只负责「提供 1 μs 的节拍」，「多长时间」是软件数的**。
> 这也解释了为什么它能同时支持 `delay_1ms`（数大数）和 `get_us_cnt()`（读时间戳）—— 同一个 1 μs 节拍，两种用法。

### 5.2 定时器三兄弟：同一个公式，不同的「能干什么」

| 类型 | 本工程用到的 | 有输出通道吗 | 源时钟 |
| --- | --- | --- | --- |
| 基本定时器 | TIMER5、TIMER6 | ❌ 只能中断 | 168 MHz |
| 通用定时器 | TIMER1、TIMER2、TIMER3、TIMER4 | ✅ 4 通道 | 168 MHz |
| 高级定时器 | TIMER0、TIMER7 | ✅ 4 通道 + **互补** | 168 MHz |

**核心公式（第二章的 ③ 式）**：

```
T_out = (PSC + 1) × (ARR + 1) / f_src
```

**本工程的两个实例**：

```
① TIMER5 定时 1 秒（4cec095）
   PSC = 16800 - 1 → f_cnt = 168e6/16800 = 10 000 Hz → t_cnt = 100 μs
   ARR = 10000 - 1 → 数 10000 个 → T = 10000 × 100 μs = 1 s ✅

② TIMER1 PWM 周期 1 ms（1f76f67）
   PSC = 1680 - 1  → f_cnt = 100 000 Hz → t_cnt = 10 μs
   ARR = 168e6/(1680)/1000 - 1 = 100 - 1 = 99 → 数 100 个 → T = 100 × 10 μs = 1 ms ✅
```

**两种算参数的思路**（都要会）：

| 思路 | 步骤 | 适合 |
| --- | --- | --- |
| **A：先定 tick 长度** | ① 选 PSC 让 t_cnt 是整数（100 μs / 10 μs / 1 μs）② ARR = 目标时间 / t_cnt - 1 | 手算、讲解、验证 |
| **B：用代码算** | `#define PERIOD (SystemCoreClock/(PRESCALER+1)/1000) - 1` | 写工程代码，改周期只改一个除数 |

### 5.3 PWM：两个旋钮，一个管频率一个管占空比

```
f_src ──÷(PSC+1)──▶ f_cnt ──数满 (ARR+1) 个──▶ 一个 PWM 周期
                     │
                     └── 硬件比较 CNT 与 CCR：CNT < CCR 输出高（PWM0 模式）

频率   ← 由 (PSC+1) 和 (ARR+1) 决定
占空比 ← 由 CCR / (ARR+1) 决定
```

**本工程验算**：

| 项 | 计算 | 结果 |
| --- | --- | --- |
| f_cnt | 168e6 / 1680 | 100 kHz（t_cnt = 10 μs） |
| T | (99+1) × 10 μs | **1 ms** |
| CCR | (99+1) × 0.5 | **50** → 占空比 50/100 = 50% |
| 呼吸灯的 CCR 范围 | 10% → `(99+1)×0.10 = 10`；100% → 100 | 10 ~ 100 |

**呼吸灯的「10 ms 改一次」是软件时间**，不在硬件公式里：

```
主循环每 10 ms 改一次 CCR，每次 ±1%
→ 从 10% 到 100% 需要 90 步 ≈ 90 × 10 ms = 0.9 s 一个来回
```

### 5.4 软 PWM 与软方波：**中断周期 ≠ 输出周期**

这是最容易算错的一类，因为**输出是「在中断里手动翻转/拉高拉低」出来的**。

**① 软 PWM（`a2eeece`）：高电平占 1/5**

```c
#define PRESCALER 1680 - 1     // → f_cnt = 100 kHz，t_cnt = 10 μs
#define PERIOD 20 - 1          // → 中断周期 = 20 × 10 μs = 200 μs

cnt = (cnt + 1) % 5;           // 5 个中断一轮
if (cnt == 0) 高电平; else 低电平;
```

```
PWM 周期 = 5 × 200 μs = 1000 μs ？ —— ❌ 错！
实际：中断每 200 μs 来一次，每次根据 cnt 决定高低
     5 次中断 = 5 × 200 μs = 1 ms 一轮
     其中 1 次高、4 次低
     ⇒ 「PWM 周期」= 1 ms，「高电平时间」= 200 μs，「占空比」= 20% ✅
```

> ⚠️ **提醒**：第 07 篇里指出过，这一版的**注释写的是「周期 1ms 占空比 20%」**，但如果只按 `ARR = 20-1` 理解成「中断周期 1 ms」就错了。**软 PWM 的周期 = N × 中断周期**（N 是 `%` 里的模数）。**算软 PWM 一定要数「几个中断算一轮」。**

**② 软方波（`698a2c6` 蜂鸣器）：翻转要 ×2**

```c
PSC = 1680 - 1;  ARR = 100 - 1;      // 中断周期 = 100 × 10 μs = 1 ms

void TIMER5_DAC_IRQHandler(void)
{
    gpio_bit_toggle(GPIOB, GPIO_PIN_9);   // 每次中断翻转一次引脚
}
```

```
一次翻转 = 半个方波周期
⇒ 方波周期 = 2 × 中断周期 = 2 × 1 ms = 2 ms
⇒ 发声频率 = 1 / 2 ms = 500 Hz ✅
```

**记住这个 ×2**：**`toggle` 出方波时，输出频率 = 计数频率 ÷ 2；如果是在中断里 toggle，就是「中断频率 ÷ 2」。**

### 5.5 蜂鸣器：把频率变成「参数」算

`bsp_buzzer` 用的是**反推**：给定要发出的频率 `hz`，算 ARR。

```c
#define PRESCALER (168 - 1)        // → f_cnt = 168e6/168 = 1 MHz，t_cnt = 1 μs

void bsp_buzzer_play(uint16_t hz)
{
    uint16_t period = (SystemCoreClock / (PRESCALER + 1) / hz) - 1;   // ← ARR
    uint16_t duty   = (period + 1) * 0.5;                             // ← CCR（固定 50%）
    ...
}
```

**代入 4 式**：

```
f_out = f_src / ((PSC+1)(ARR+1)) = 1 MHz / (ARR+1)
⇒ ARR + 1 = 1 MHz / hz
⇒ ARR = 1000000/hz - 1          ✅ 就是代码里那一行
```

| 想发的音 | ARR | 验算 |
| --- | --- | --- |
| 20 Hz（最低音） | 49999 | 1e6/20 = 50000 → 50 ms → 20 Hz ✅ |
| 1000 Hz | 999 | 1e6/1000 = 1000 → 1 ms → 1 kHz ✅ |
| 20000 Hz（最高音） | 49 | 1e6/20000 = 50 → 50 μs → 20 kHz ✅ |

**⚠️ 为什么 PSC 取 `168-1` 而不是 `1680-1`？** 因为 `ARR` 是 **16 位**（最大 65535）：

```
用 1 μs tick：最低可发 1e6/65536 ≈ 15.3 Hz   ← 覆盖整个可听频段（20 Hz~20 kHz）✅
用 10 μs tick：最低可发 1e5/65536 ≈ 1.5 Hz   ← 够了；但 20 kHz 时 ARR = 4，分辨率太差 ⚠️
```

**结论**：**tick 越细，高频端的「频率分辨率」越好**。蜂鸣器要覆盖 20~20000 Hz（跨 1000 倍），用 1 μs tick 让 ARR 在 49~49999 之间保持较高的相对精度。

### 5.6 RTC：两级预分频，目标是 1 Hz

```
RTCCLK ──÷(FACTOR_A+1)──▶ CK_APRE ──÷(FACTOR_S+1)──▶ CK_SPRE = 1 Hz
         7 位（0~0x7F）                15 位（0~0x7FFF）
         ↑ 给「亚秒」用                 ↑ 给日历用（每秒 +1）
```

**两个公式**：

```
CK_APRE = RTCCLK / (FACTOR_A + 1)
CK_SPRE = RTCCLK / ((FACTOR_A + 1) × (FACTOR_S + 1)) = 1 Hz
```

**为什么异步固定取最大值 `0x7F`**（教材原话：「异步预分频尽可能大」）—— 让同步部分（耗电的部分）尽量慢：

```
FACTOR_A = 127  →  (FACTOR_A + 1) = 128
⇒ FACTOR_S = RTCCLK / 128 - 1        ← 只剩下「除以 128」这一件事
```

**三种时钟源的验算**：

| 时钟源 | RTCCLK | ÷128 后 | FACTOR_S | 验算 |
| --- | --- | --- | --- | --- |
| **HXTAL ÷25**（本工程） | 8 000 000/25 = **320 000** | 2 500 | **2499**（`0x9C3`） | 320000/128/2500 = 1 ✅ |
| **LXTAL** | **32 768** | 256 | **255**（`0xFF`） | 32768/128/256 = 1 ✅ |
| **IRC32K** | **32 000** | 250 | **249**（`0xF9`） | 32000/128/250 = 1 ✅ |

**⚠️ LXTAL 与 IRC32K 只差 768 Hz，但预分频差了 6**：

```
32768 vs 32000 → 相差 2.4%
如果混用（LXTAL 的 256 配 IRC32K 的 32000）：
   实际 CK_SPRE = 32000/128/256 = 0.9766 Hz   → 慢了 2.34%
   每天偏差 = 86400 × 0.0234 ≈ 2025 s ≈ 33.8 分钟/天  ❌
```

**这类错误的表现是「时间在走，但越走越偏」**——比「完全不走」难发现得多。

### 5.7 独立看门狗 FWDGT：最简单的计数模型

```
IRC32K ──÷(PSC)──▶ f_cnt ──数满 RLD 个──▶ 复位
```

**本工程（`6827512`）**：

```c
fwdgt_prescaler_value_config(FWDGT_PSC_DIV32);
fwdgt_reload_value_config(100);
```

```
f_cnt = 32 000 / 32 = 1 000 Hz      → t_cnt = 1 ms
T_out = RLD × t_cnt = 100 × 1 ms = 100 ms     ← 100 ms 不喂狗就复位 ✅
```

**量程（12 位计数器）**：

```
最小超时 = 1 × (4 / 32000)      = 0.125 ms
最大超时 = 4095 × (256 / 32000) ≈ 32.76 s
```

**教材的心算法**（很好用，建议记住）：

```c
fwdgt_config(2 * 500, FWDGT_PSC_DIV64);
//             ↑        ↑
//      计数值=1000   32kHz/64 = 500 Hz（每秒数 500 次）
// ⇒ 想设 n 秒，第一个参数就写 n × 500
```

### 5.8 窗口看门狗 WWDGT：多了一个固定的 ÷4096

```
PCLK1 ──÷4096──▶ ──÷(PSC)──▶ f_cnt ──7 位递减：0x7F → 0x3F（复位）
                                    └─ 且必须在 WIN 之下才能喂（否则复位）
```

**本工程（`bbce6b7`）**：

```c
wwdgt_config(0x7F, 0x50, WWDGT_CFG_PSC_DIV1);
//             ↑     ↑
//         counter  window
```

```
f_cnt = 42 000 000 / 4096 / 1 = 10 253.90625 Hz
t_cnt = 1 / 10253.90625 = 97.523 μs
```

**为什么有 4096**？窗口看门狗内部有一个**固定的 12 位分频器**（`2^12 = 4096`），硬件写死，你只能在它之后再分频。

**窗口区间计算**：

```
最短喂狗时间 = (counter - window) × t_cnt = (127 - 80) × 97.523 μs = 47 × 97.523 = 4583.6 μs ≈ 4.58 ms
最长喂狗时间 = (counter - 0x3F) × t_cnt = (127 - 63) × 97.523 μs = 64 × 97.523 = 6241.5 μs ≈ 6.24 ms

→ 窗口宽度只有 6.24 - 4.58 = 1.66 ms
→ 本工程喂狗周期取 5 ms（`delay_1ms(5)`），正好落在窗口中间 ✅
```

> **WWDGT 与 TIMER 的时钟来源不同**：TIMER 经过 `TIMERSEL` 倍频（168 MHz），而 **WWDGT 直接用 PCLK1 = 42 MHz**（库源码里 WWDGT 的时钟位在 `RCU_APB1EN`，项目注释也写的是 `42mhz`）。**算 WWDGT 时千万不要按 168 MHz 算**。

### 5.9 串口波特率：16 倍过采样，本质也是分频

UART 是**异步**通信，收发双方靠「约定的位时间」对齐，所以**波特率本质上就是「用总线时钟分出一个位时钟」**。

```
波特率 = f_PCLK / (16 × USARTDIV)          ← 16 倍过采样（默认）
波特率 = f_PCLK / (8  × USARTDIV)          ← 8 倍过采样（USART_CTL0_OVSMOD 置位）
```

**库函数的做法**（`gd32f4xx_usart.c`）：

```c
uclk = rcu_clock_freq_get(CK_APB2);   // USART0 → 84 MHz
uclk = rcu_clock_freq_get(CK_APB1);   // USART2 → 42 MHz
udiv = (uclk + baudval / 2U) / baudval;        // 四舍五入
intdiv = udiv & 0xfff0U;                       // 整数部分（12 位）
fradiv = (udiv >> 1U) & 0x7U;                  // 小数部分（3 位，步进 1/8）
USART_BAUD = intdiv | fradiv;
```

**本工程两个串口都配 115200，但分频值完全不同**（我按库函数算法逐位复算过）：

| 串口 | 总线 | f_PCLK | 理想 USARTDIV | 实际寄存器值 | 实际 USARTDIV | 实际波特率 | 误差 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **USART0** | APB2 | **84 MHz** | 45.5729 | mantissa 45 + frac 4 | **45.5** | 115384.6 | **+0.16%** |
| **USART2** | APB1 | **42 MHz** | 22.7865 | mantissa 22 + frac 6 | **22.75** | 115384.6 | **+0.16%** |

**验算（USART0）**：

```
udiv = (84 000 000 + 57 600) / 115 200 = 729.67 → 取整 729
mantissa = 729 >> 4 = 45          frac = (729 >> 1) & 7 = 4
解码回 USARTDIV = 45 + 4/8 = 45.5
实际波特率 = 84 000 000 / (16 × 45.5) = 84 000 000 / 728 = 115 384.6
误差 = (115384.6 - 115200) / 115200 = +0.16%   ✅ 远小于 2% 的经验上限
```

> **两个结论**：
> 1. **同一个波特率在不同总线上，USARTDIV 不同**（45.5 vs 22.75，正好差一倍——因为总线频率差一倍）。**改串口或改时钟树，波特率要重新确认**。
> 2. **取整误差很小但不能忽略**：本工程 +0.16% 完全没问题；如果误差接近 2%，通信就会不稳定（接收端采样点会漂到错误位置）。

**顺带算一下「时间」**（这个数字在好几篇笔记里用到）：

```
一帧 = 1 起始位 + 8 数据位 + 0 校验 + 1 停止位 = 10 bit
一个字节耗时 = 10 / 115200 = 86.8 μs
最大吞吐 ≈ 11520 字节/秒

→ printf 输出 60 字节  ≈ 5.2 ms（第 12 篇：够把看门狗喂狗节奏打乱）
→ printf 输出 100 字节 ≈ 8.7 ms（第 04/08 篇：远超 WWDGT 的 1.66 ms 窗口）
```

**这就是「波特率」为什么会影响实时性**：**串口发送是阻塞的，而「要多久」完全由波特率决定**。

## 六、反推参数：通用四步法

拿到一个需求（「我要每 500 ms 做一次」「我要 1 kHz 方波」），按这四步走：

```
① 查源时钟 f_src
   它挂哪条总线？定时器要先 ×4 倍频到 168 MHz 吗？看门狗是 32 kHz 还是 42 MHz？

② 定「一个计数代表多长时间」t_cnt
   原则：让 t_cnt 是个好算的整数（1 μs / 10 μs / 100 μs）
   ⚠️ 同时检查计数器位数够不够（TIMER 16 位、FWDGT 12 位、WWDGT 7 位）

③ 算分频：PSC = f_src / f_cnt - 1 = t_cnt × f_src - 1

④ 算计数值
   定时/方波 → N = 目标时间 / t_cnt，写 ARR = N - 1
   PWM      → ARR = f_src/((PSC+1)×f_pwm) - 1，CCR = (ARR+1) × 占空比
   看门狗   → RLD = 目标超时 / t_cnt
   串口     → USARTDIV = f_PCLK / (16 × baud)，交给库函数
```

**用第 07 篇的呼吸灯反推一遍**（要求：PWM 周期 1 ms、占空比可调）：

```
① f_src = 168 MHz（TIMER3 在 APB1，×4 后 = 168 MHz）
② 取 t_cnt = 10 μs（好算）→ f_cnt = 100 kHz
③ PSC = 168e6 / 100e3 - 1 = 1680 - 1 ✓（和代码一致）
④ N = 1 ms / 10 μs = 100 → ARR = 99 ✓；CCR 从 10 到 100 扫 → 占空比 10%~100% ✓
```

**再用串口反推一遍**（要求：115200）：

```
① USART0 在 APB2 = 84 MHz
② 不需要定 t_cnt，直接套公式
③④ USARTDIV = 84e6/(16×115200) = 45.5729 → 寄存器 45 + 4/8 → 实际 115385（+0.16%）
```

## 七、精度与误差：硬件算得准，但源不一定准

**公式算得再准，源时钟不准也白搭。** 这是「频率计算」里最容易被忽视的一环。

### 7.1 三类时钟源的精度对比

| 时钟源 | 类型 | 典型精度 | 影响 |
| --- | --- | --- | --- |
| **HXTAL**（8 MHz 晶振） | 石英晶振 | ±10~50 ppm（0.001~0.005%） | 很好；本工程 RTC 与系统时钟都用它 |
| **LXTAL**（32.768 kHz 晶振） | 石英晶振 | ±20 ppm 级 | **RTC 的最佳选择**（但需焊晶振 + 匹配电容） |
| **IRC32K**（内部 RC） | RC 振荡器 | **±1%~±5%**（受温度/电压影响大） | FWDGT 用它（只看「死没死」，不看绝对时间）；**RTC 若用它走时会明显偏差** |

**估个数量级**：假设 IRC32K 实际是 32 100 Hz 而代码按 32 000 算：

```
频率误差 = (32100 - 32000)/32000 = 0.3125%
RTC 每天偏差 = 86400 s × 0.003125 ≈ 270 s ≈ 4.5 分钟/天
```

**同一份代码，换个时钟源，结果差几十倍** —— 这就是「为什么 RTC 要配 32.768 kHz 晶振」。

### 7.2 误差来源清单

| 来源 | 量级 | 怎么减小 |
| --- | --- | --- |
| **源时钟精度** | RC：0.1%~5%；晶振：ppm 级 | 需要绝对时间的（RTC）用晶振；只看相对时间的（FWDGT）用 RC 也行 |
| **分频/计数取整** | 小于 1 个计数 → 相对误差 ≈ 1/N | 让 N 尽量大（tick 细一点） |
| **波特率分频取整** | 本工程 +0.16% | 换更「整」的波特率（如 9600 在 42 MHz 上误差更小）；或降低波特率 |
| **总线频率搞错** | 直接 2 倍 ~ 4 倍偏差 | 先查 `RCU_APBxEN` 确认外设在哪个总线、再确认 TIMERSEL |
| **软件调度的抖动** | 主循环一轮的时间不确定 | 用 `get_us_cnt()` 时间戳，别用「计数 × 固定延时」 |

### 7.3 软件时间 vs 硬件时间

这是本篇最值得带走的观念：

| | 硬件时间 | 软件时间 |
| --- | --- | --- |
| 谁在数 | 定时器/看门狗/RTC 的计数器 | 主循环里的代码 |
| 精度 | 硬件级，不受代码影响 | 取决于循环耗时是否稳定 |
| 例子 | PWM 周期、RTC 秒、FWDGT 超时 | 消抖 30 ms、状态机 500 ms、呼吸灯 10 ms |
| 风险 | 几乎没有 | **一旦循环里加了耗时操作就漂移** |

**本工程里「软件时间」被硬件逼着改进的两次**：

1. **第 09 篇**：数码管扫描需要 1 ms 刷新，如果主循环里有 `delay_1ms(10)`，一帧就变 80 ms → 闪烁。于是呼吸灯从 `delay_1ms(10)` 改成 `get_us_cnt()` 时间戳。
2. **第 12 篇**：WWDGT 的窗口只有 **1.66 ms**，喂狗周期必须精确在 4.58~6.24 ms 之间。**任何「偶尔耗时长」的操作都会导致复位** —— 硬件直接强制了非阻塞。

### 7.4 第三类时间：物理时间（不靠计数器，但照样要算）

前面两类都是"数出来的时间"，还有一类**跟时钟、分频、计数全都无关**——**器件内部物理过程需要的时间**。
新增的 SPI Flash（第 24 篇）就是最典型的例子：

| 操作 | 手册标称（typ） | 换成"多少个 SPI 时钟"（21 MHz） | 谁在等 |
| --- | --- | --- | --- |
| 读 14 字节（ID 事务） | 无额外时间 | $14 \times 8 = 112$ 个时钟 ≈ **5.3 μs** | 总线 |
| 编程 256 B 页 | **0.7 ms** | 命令本身 264 B ≈ 100 μs | **芯片内部高压电路** |
| **擦除 4 KB 扇区** | **45 ms** | 命令只要 4 B ≈ **1.5 μs** | **芯片内部高压电路** |
| 芯片全擦 | 约 10 s 量级 | 同上 | 同上 |

**三个结论**：

1. **提高 SPI 时钟对擦写速度毫无帮助**：命令 1.5 μs 就发完了，剩下 44.9985 ms 全在等芯片。
   想快只有一条路——**减少擦除次数**（攒满一个扇区再写）。
2. **它比任何"计数器时间"都长两个数量级**：45 ms vs WWDGT 窗口 1.66 ms ——
   **所以"打开窗口看门狗"和"用 Flash 存数据"在当前代码结构下是互斥的**（必然复位）。
3. **`bsp_flash_wait_busy()` 那个 `while` 轮询，就是本工程最长的一次"忙等"**：
   它把 45 ms 硬生生变回了"软件时间"（阻塞主循环），
   处理它的正确方式正是**第 05 篇的状态机**（发指令 → 返回 → 主循环里查状态 → 完成）。

## 九、常见错误清单

| 现象 | 最可能的原因 |
| --- | --- |
| 定时时间**差整数倍**（快 2 倍 / 慢 4 倍） | **总线频率搞错**：把 APB1 外设按 APB2（84 MHz）算，或忘了 `TIMERSEL` 倍频 |
| 定时时间差一点点（差 1 个单位） | **忘了减 1**：`PSC`/`ARR` 写的是「值」，实际分频/计数要 +1 |
| PWM 频率对但占空比差一点 | 占空比基准用错：应该是 `CCR/(ARR+1)`，**分母有 +1** |
| 蜂鸣器发声频率正好是预期的一半 | 用了中断里 `toggle` 的方式，**忘了 ×2**（一次翻转只走半个周期） |
| 蜂鸣器低音发不出来 | `ARR` 超过 16 位上限（`uint16_t`），或 tick 选得太粗 |
| 改了 `period` 后没生效 | 定时器改 `ARR` 必须重新 `timer_init()`（库没有单独的 set 接口） |
| WWDGT 一启动就复位 | 忘了 **`/4096`**；或 `window` 取了比 `counter` 还大的值 |
| WWDGT 时间差 4 倍 | 按 168 MHz 算了 WWDGT —— 它用的是 **PCLK1 = 42 MHz** |
| FWDGT 超时不对 | 分频/重装载写不进去（**忘了 `fwdgt_write_enable()`**）；或用了 32768 而不是 32000 |
| RTC 越走越偏 | 预分频与时钟源不匹配（LXTAL 的 `0xFF` 配了 IRC32K）；或用了精度差的 IRC32K |
| 串口乱码 | 波特率误差太大（>2%）；或两个串口挂不同总线却抄了同一份分频思路 |
| 串口能收但偶尔错一两个字节 | 波特率误差处于临界；或接收端有阻塞导致丢字节（与波特率无关，但表现类似） |
| 主循环加了个任务就抽搐 | **软件时间被拖长**了（第 05/09/12 篇都是这个坑） |
| 换了一块板子/改了时钟配置就全乱 | 时钟树一变，**所有基于时间的参数都要重算** |

## 十、时间尺度总览（本工程所有周期一览）

把本工程出现的所有时间，按快慢排成一张表 —— **能直观看到「哪个量在哪个数量级」，也能看出哪些量之间必须满足大小关系**。

| 时间 | 出处 | 怎么来的 |
| --- | --- | --- |
| **1 μs** | SysTick 节拍（**裸机版**） | 168 MHz ÷ 168 |

**这张表里藏着的三条约束关系**（值得自己推一遍）：

| 约束 | 说明 |
| --- | --- |
| 喂狗周期必须夹在 **4.58 ms 和 6.24 ms** 之间 | 所以 5 ms 是唯一舒服的选择，而 `printf`（8.7 ms）会**直接破坏它** |
| 数码管刷新（1 ms）必须远小于 **41.7 ms**（人眼视觉暂留） | 所以一帧 8 ms 是安全的，125 Hz 远超临界 |
| 按键扫描（20 ms）要远小于抖动时间窗口（**~30 ms**）的相对量 | 所以 20 ms 扫描天然过滤了大部分抖动 |
| **188 一帧（5 ms）与数码管一帧（8 ms）都必须远小于 41.7 ms 视觉暂留** | 所以两者都不闪；而 188 的 20% 占空比意味着**要靠峰值电流换亮度** |
| **Flash 擦除（45 ms）必须避开看门狗窗口（1.66 ms）与超时（100 ms）** | 所以"开看门狗"与"写 Flash"在当前代码结构下**互斥**（第 24 篇 §7.2） |
| ★ **同一个"1 μs"在裸机和 RTOS 下是两种实现** | 裸机靠 **SysTick 1 MHz 中断**递减；RTOS 靠 **TIMER6 自由运行计数器**轮询差值。**而 `get_us_cnt()` 的精度从 µs 退化到 1 ms**（tick hook 每 tick 加 1000）—— 第 34 篇 §4 |
| ★ **触摸按键的"去抖时间"根本不在 MCU 里** | RTM3 = 6 个采样周期由 **SC12B 芯片内部**完成 → **本工程唯一一个"消抖不需要 MCU 定时器"的按键方案**（第 31 篇）。**对照**：独立按键靠 SysTick 时间戳、AD 按键靠 30 ms 时间门、**矩阵键盘压根没做** |
