## 知识点地图

```
看门狗（Watchdog）
├── 为什么需要看门狗      死机/跑飞/电磁干扰 → 自动复位自恢复，无人值守场景的兜底
├── 本质                  一个倒计时计数器，到 0 就复位
├── 独立看门狗 FWDGT      free watchdog：IRC32K 独立时钟源、12 位递减计数、喂狗无时限
├── 窗口看门狗 WWDGT      window watchdog：APB1 时钟、7 位递减计数、喂狗必须在窗口内
├── 喂狗                  把计数器的值重新装回去（FWDGT）/ 更新计数器（WWDGT）
├── 参数计算              分频 + 重装载值 → 超时时间
├── 窗口区间              [最短喂狗时间, 最长喂狗时间]，太早太晚都复位
├── 两个复位条件          WWDGT：CNT 归 0x3F 复位；窗口内喂狗才算合法
├── 写保护                FWDGT 改参数前要 fwdgt_write_enable()
├── 不可逆                一旦使能，软件无法关闭
└── 使能时机              必须在「主循环能够周期性喂狗」之后才使能
```

- 说清看门狗解决什么问题，以及「喂狗」到底在做什么
- 掌握 FWDGT 与 WWDGT 在时钟源、计数器位数、喂狗规则上的区别

- 知道看门狗一旦使能就无法软件关闭，因此**使能位置**是个工程决策

## 一、为什么需要看门狗

### 1.1 问题：单片机也会「死机」

程序跑飞、陷入死循环、被强电磁干扰打乱状态机——这些情况在实验室里少见，在**现场设备**里很常见。而现场设备往往是：

```
装在配电箱里 / 装在野外 / 装在无人值守的机房
        ↓
死机了没人能去按复位键
        ↓
设备一直僵在那儿，直到供电重启
```

**看门狗就是为这个场景设计的兜底机制**：

```
正常情况下：程序周期性「喂狗」→ 看门狗认为系统活着 → 计数器被不断重置 → 永不超时
异常情况下：程序卡死 → 没人喂狗 → 计数器数到 0 → 硬件强制复位整个系统
```

**四个价值**（教材的总结，值得背）：

| 价值 | 说明 |
| --- | --- |
| 系统健壮性 | 故障时自动重启，恢复运行 |
| 防止死锁 | 死循环、意外暂停能被检测出来 |
| 数据完整性 | 避免长期僵死导致关键数据丢失 |
| 实时性保障 | 任务没按时完成可以复位重来 |

### 1.2 本质：一个倒计时计数器

```c
fwdgt_counter_reload();     // 「喂狗」= 把计数器重新装回重装载值
```

**一句话记忆**：**喂狗 = 把炸弹的倒计时拨回去**。拨得及时，炸弹永远不炸；不拨了，到点就炸（复位）。

> **注意一个反直觉点**：看门狗的「喂狗」**不是**「告诉它我很好」，而是「**把它重新开始数**」。所以喂得对不对，本质是「节奏对不对」。

## 二、两个看门狗：FWDGT vs WWDGT

GD32F4 有两个看门狗，**名字和职责都不一样**：

| | **独立看门狗 FWDGT** | **窗口看门狗 WWDGT** |
| --- | --- | --- |
| 全称 | Free Watchdog Timer | Window Watchdog Timer |
| **时钟源** | **IRC32K（内部 32 kHz）独立振荡器** | **APB1 时钟**（本工程 42 MHz） |
| 主时钟挂了还工作吗 | **✅ 会**（这就是「独立」的含义） | ❌ 不会（依赖系统时钟） |
| 计数器 | **12 位**递减（0 ~ 0xFFF） | **7 位**递减（0x00 ~ 0x7F） |
| 喂狗规则 | **只要在归 0 之前喂就行**（无下限） | **必须在窗口区间内喂**（早了晚了都复位） |
| 复位条件 | 计数器递减到 0 | ① 递减到 `0x3F` ② 在窗口外喂狗 |
| 预分频 | 4 / 8 / 16 / 32 / 64 / 128 / 256 | 1 / 2 / 4 / 8（再叠加固定的 ÷4096） |
| 计时精度 | 低（RC 振荡器） | **高**（来自晶振） |
| 适用场景 | **整机兜底**：死锁、跑飞、强干扰 | **监控时序严格性**：防止程序异常地「跑得太快」 |
| 本工程参数 | `PSC_DIV32` + reload `100` → **100 ms** | `0x7F/0x50/DIV1` → 窗口 **4.58 ~ 6.24 ms** |

> **一句话记住两者分工**：
> **FWDGT 管「你还活着吗」，WWDGT 管「你活得是不是太快了」。**

## 三、提交演进

### 3.1 `6827512`：独立看门狗

**提交信息**：`[更新] 独立看门狗`（`main.c` +39/-8，`.eide/eide.yml` 加入 `gd32f4xx_fwdgt.c`）

```c
void msp_fwdgt_config(void)
{
    // 打开时钟
    rcu_osci_off(RCU_IRC32K);
    delay_1ms(1);
    rcu_osci_on(RCU_IRC32K);

    if (rcu_osci_stab_wait(RCU_IRC32K) == ERROR)
    { // 等待稳定
        printf("turn_on_osci_error\n");
        return;
    }

    // 写使能
    fwdgt_write_enable();
    // 配置分频系数 32000 / 32 = 1000
    fwdgt_prescaler_value_config(FWDGT_PSC_DIV32);
    // 配置重装载值
    fwdgt_reload_value_config(100);
    // 启动看门狗
    fwdgt_counter_reload();
    fwdgt_enable();
}
```

**五个步骤，逐个说清**：

| # | 代码 | 作用 | 不做的后果 |
| --- | --- | --- | --- |
| 1 | `rcu_osci_off(RCU_IRC32K)` + `delay_1ms(1)` + `rcu_osci_on(...)` | **强制重启内部 32 kHz 振荡器** | 教材版只做 `on`；本工程先 `off` 再 `on`，是为了**保证它从确定的状态开始起振** |
| 2 | `rcu_osci_stab_wait(RCU_IRC32K)` | 等振荡器**稳定** | 没稳定就用，计数频率不准 → 超时时间不准 |
| 3 | **`fwdgt_write_enable()`** | **解除寄存器写保护** | 后面的分频/重装载配置**全部写不进去**（静默失败） |
| 4 | `fwdgt_prescaler_value_config` + `fwdgt_reload_value_config` | 配超时时间 | — |
| 5 | `fwdgt_counter_reload()` + `fwdgt_enable()` | 装初值 + 启动 | 不启动就等于没配 |

> **第 3 步 `fwdgt_write_enable()` 是 FWDGT 特有的坑**：教材里用的是 `fwdgt_config(reload, psc)`（它内部会帮你写使能），本工程改成手动三步调用，所以必须自己写使能。
> 教材的原话说得很清楚：**「使能独立看门狗的寄存器写保护功能可以避免寄存器的值被意外的配置篡改」**——这是**防跑飞把看门狗参数改掉**的安全设计。

**主循环里喂狗**：

```c
    uint8_t cnt = 0;
    while (1)
    {
        // if (cnt == 50)
        // {
        //     cnt = 0;
        //     // 读取RTC
        //     msp_rtc_read(&time);
        //     printf("sec=%d, min=%d, hour=%d\n", (int)time.sec, (int)time.min, (int)time.hour);
        //     printf("day=%d, week=%d, month=%d, year=%d\n", (int)time.day, (int)time.week, (int)time.month, (int)time.year);
        // }

        // 喂狗
        fwdgt_counter_reload();

        delay_1ms(20);
        cnt++;
    }
```

**这次提交干了一件很重要的「清理」**：把上一版（RTC 测试用）的「每 50 轮打印一次时间」**整块注释掉**了。为什么？看下面这段推理：

```
如果保留 printf：
  1 秒钟打印 2 行（约 60 字节）
  115200 波特率下发 60 字节 ≈ 60×10/115200 = 5.2 ms   ← 阻塞在串口上
  +
  组合起来，喂狗间隔会从 20 ms 变成 25 ms 以上（还好，没超 100 ms）
```

**表面上看没超时，但风险在于「不可预测」**：一旦打印内容变多、或中断占用变长，喂狗间隔就可能越过 100 ms，导致**复位**。而这类复位特别难查——因为**它表现得像「跑一段时间就重启」**。

> **这条经验值得记**：**看门狗使能之后，任何「不可预测耗时」的操作都是隐患**（`printf` 是典型的）。调试期间要么先关狗，要么确保喂狗路径独立于耗时操作。

### 3.2 `bbce6b7`：窗口看门狗

**提交信息**：`[更新] 窗口看门狗`（`main.c` +25/-12，`.eide/eide.yml` 加入 `gd32f4xx_wwdgt.c`）

```c
void msp_wwdgt_config(void)
{
    // 打开时钟
    rcu_periph_clock_enable(RCU_WWDGT);
    // 42mhz
    // 42000000hz / 4096 = 10,253.90625hz
    // 10,253.90625hz / 1 = 10,253.90625ms
    // 10,253.90625hz <=> 1000000us
    // 数1个数 <=> 97.523us
    // 配置窗口看门狗属性
    // 最短喂狗时间   47*97.5us = 4582.5us
    // 最长喂狗时间   64*97.5us = 6241.5us
    wwdgt_config(0x7F, 0x50, WWDGT_CFG_PSC_DIV1);
    // 启动看门狗
    wwdgt_enable();
}
```

**这段注释把「参数怎么算」写得明明白白**，第四章（独立）和第五章（窗口）会把每一步都验算一遍。

**这次提交真正重要的改动是「把使能位置挪到了 `main()` 末尾」**：

```diff
     // EXTI0 PA0 和 EXTI3 PC3初始化
     msp_exti_init();
     // RTC
     msp_rtc_init(HXTAL);
-    // 独立看门狗
-    msp_fwdgt_config();
 
     //============ 片外外设 ============
     ...
     // 闹钟配置
     msp_rtc_alarm_config(&time);
 
+    // 独立看门狗
+    // msp_fwdgt_config();
+    // 窗口看门狗
+    msp_wwdgt_config(); // 前面的初始化会消耗时间
+
     uint8_t cnt = 0;
     while (1)
     {
-        // if (cnt == 50) { ... }
-
-        // 喂狗
-        fwdgt_counter_reload();
+        delay_1ms(5);
 
-        delay_1ms(20);
+        // 喂狗
+        wwdgt_counter_update(0x7F);
+
         cnt++;
     }
 }
```

**那句注释 `// 前面的初始化会消耗时间` 是全篇最值钱的一行**。它解释了为什么必须挪位置：

```
❌ 错误顺序（6827512 的做法）：
    使能看门狗  →  再做 LED/按键/蜂鸣器/RTC/闹钟/DMA 初始化  →  进主循环开始喂狗
                   └────────── 这一段可能耗时几十~几百 ms ──────────┘
                   └── 窗口只有 6.24 ms！ 狗早就复位了 ──┘

✅ 正确顺序（bbce6b7 的做法）：
    做完所有初始化  →  使能看门狗  →  立刻进主循环  →  每 5 ms 喂一次
```

**《用户手册》里的说法是「看门狗一旦启动就必须周期性喂狗」，工程上的推论是**：

> **看门狗必须使能在「此后不会再出现长时间不喂狗」的位置。**

这也解释了为什么两次提交里**两个看门狗只能启用一个**（一个被注释掉）：不是不能同时用，而是**当前主循环的喂狗节奏只能服务一种窗口设定**。

**另一个变化：喂狗周期从 20 ms 改成 5 ms**。因为窗口看门狗的合法区间是 **4.58 ~ 6.24 ms**：

```
delay_1ms(5)  →  实际喂狗间隔约 5 ms（加上循环开销略多）
                ↓
     4.58 ms ≤ 5 ms ≤ 6.24 ms   ✅ 正好落在窗口中间
```

**选 5 ms 的原因**：窗口宽度只有 1.66 ms（6.24 - 4.58），**必须选中间值**才不容易因为循环抖动而越界。

```c
// msp_fwdgt_config();
// 窗口看门狗
// msp_wwdgt_config();   // 前面的初始化会消耗时间
```

**"原样搬出"里唯一值得注意的一处**——`msp_fwdgt_config()` 开头那三行：

```c
// 打开时钟
rcu_osci_off(RCU_IRC32K);   // ① 先关掉 IRC32K
delay_1ms(1);
rcu_osci_on(RCU_IRC32K);    // ② 再打开（强制重新起振）
if (rcu_osci_stab_wait(RCU_IRC32K) == ERROR)   // ③ 等稳定，失败就报错返回
{
    printf("turn_on_osci_error\n");
    return;
}
```

**为什么要"关一下再开"**：`IRC32K` 是 **FWDGT 的唯一时钟源**，它可能已经被别的代码以未知状态打开过。
先关再开 + 等稳定标志，能得到一个**确定的起点**；而 `rcu_osci_stab_wait()` 失败就 `return`（不往下配、不使能），
避免"用一个没起振的时钟去喂狗"——**这条防御写得很到位**。

> ⚠️ **但它带来一个跨模块的隐患，必须记住**：
> **IRC32K 也是 MCU 内部 RTC 的候选时钟源之一**（第 11 篇：`RTC_CLOCK_SOURCE` 有 `IRC32K` 这一档）。
> 本工程 `msp_rtc_init(HXTAL)` 用的是 **HXTAL 分频**，所以现在**相安无事**；
> 但如果你哪天把 RTC 时钟源改成 `IRC32K`，那么**调用一次 `msp_fwdgt_config()` 就会把 RTC 的时钟源"重启"一遍**
> —— 表现为**走时突然变快/变慢或跳变**。
>
> **教训**：凡是"关掉某个共享振荡器"的操作，都要先问一句"**还有谁在用它**"。
> （这也是第 23 篇"查手册"里"外设之间共享的资源"那一类问题的实例。）

**这次封装顺带说明的一件事**：`main.c` 的整理（`067922c`，比这次只早 22 分钟）把这两个函数先从 `main.c` **删掉**，
22 分钟后它们才在 `Hardware/` 下重生。**"先删后建"的迁移顺序**在 `067922c` 与 `8115f1f` 之间制造了一个**不可编译的中间态**
（详见第 27 篇 §3.3 的完整分析）。

## 四、独立看门狗参数计算

### 4.1 公式

```
① 计数时钟频率
   f_cnt = f_IRC32K / 预分频系数 = 32000 / 32 = 1000 Hz

② 每个计数的时间
   t_cnt = 1 / f_cnt = 1 ms

③ 超时时间（复位时间）
   T_out = 重装载值 × t_cnt = 100 × 1 ms = 100 ms
```

### 4.2 本工程的值

| 项目 | 值 | 验算 |
| --- | --- | --- |
| 时钟源 | IRC32K **32 000 Hz** | — |
| 预分频 | `FWDGT_PSC_DIV32` | 32000 ÷ 32 = **1000 Hz** → 1 ms/计数 |
| 重装载值 | `100` | 100 ms |
| **超时时间** | **100 ms** | 100 × 1 ms ✅ |
| 实际喂狗间隔 | 20 ms（`6827512`） | 20 ms << 100 ms ✅ |

**教材的对照算法**（另一种表述，结果一致）：

```
fwdgt_config(2 * 500, FWDGT_PSC_DIV64);
   → 32 kHz / 64 = 500 Hz，即 1 秒计 500 次
   → 第一个参数「计数值」= 想设的秒数 × 500
   → 2 × 500 = 1000 → 2 秒
```

**教材的例子更直观**（值得记住这个心算方法）：

```c
while (1) {
    delay_1ms(2400);          // 重启（因为 2400ms > 2000ms 超时）
    // delay_1ms(450);        // 正常
    fwdgt_counter_reload();
}
```

**「改延时看它什么时候复位」是验证看门狗最简单的实验方法**。

### 4.3 12 位计数器的量程

```
最大超时 = 0xFFF × (256 / f_IRC32K) = 4095 × 8 ms ≈ 32.7 s   （预分频取最大 256）
最小超时 = 1 × (4 / f_IRC32K)        = 1 × 0.125 ms          （预分频取最小 4）
```

**结论**：FWDGT 能覆盖 **0.125 ms ~ 32.7 s** 的超时范围，对绝大多数应用够用。**需要更长就得上 RTC 的唤醒定时器**（第 11 篇提到过 RTC 还有这个功能）。

## 五、窗口看门狗参数计算

### 5.1 时钟链

```
WWDGT 时钟 = PCLK1 / 4096 / 预分频

本工程：
  PCLK1 = 168 MHz / 4 = 42 MHz        （APB1 分频系数为 4）
  42 000 000 / 4096 = 10253.90625 Hz   ← 4096 是固定的 12 位分频
  预分频 = DIV1（不再分频）
  → 计数频率 = 10253.90625 Hz
  → 每个计数 = 1 / 10253.90625 = 97.523 μs
```

> **`/4096` 是哪来的？** 窗口看门狗内部有一个**固定的 12 位分频器**（`2^12 = 4096`），它是硬件写死的，**你只能通过 `WWDGT_CFG_PSC_DIVx` 在它之后再分频**。

### 5.2 三个关键值

```c
wwdgt_config(0x7F, 0x50, WWDGT_CFG_PSC_DIV1);
//             ↑     ↑
//        counter   window
//        0x7F=127  0x50=80
```

| 值 | 含义 |
| --- | --- |
| `counter = 0x7F` | **重装载值**（初始计数值）。7 位递减计数器从 127 开始往下数 |
| `window = 0x50` | **窗口下限值**。喂狗时如果 `CNT > window`，直接复位 |
| 计数器「危险线」 | **`0x3F`**：CNT 数到 0x3F（即 `CNT[6]` 被清 0）时复位 |

### 5.3 喂狗窗口区间（本节核心）

```
CNT 的变化过程（从右往左递减）：

  CNT = 127 ──────────────────→ 80 ──────────→ 64 ──→ 63(0x3F) ─→ 复位
        ↑                        ↑              ↑        ↑
    刚喂完狗                 窗口下限 WIN    危险线    复位发生
        │                        │              │
        │◄─── 不合法区（太早） ──►│              │
        │                        │◄─ 合法窗口 ─►│
        │                        │              │
        时间起点              t=4.58ms       t=6.24ms
```

**两个时间怎么算出来**：

```
最短喂狗时间（不能早于它，否则 CNT 还在 80 以上）：
    (counter - window) × t_cnt = (127 - 80) × 97.523 μs
                               = 47 × 97.523 μs
                               ≈ 4583.6 μs ≈ 4.58 ms

最长喂狗时间（不能晚于它，否则 CNT 已经数到 0x3F）：
    (counter - 0x3F) × t_cnt  = (127 - 63) × 97.523 μs
                              = 64 × 97.523 μs
                              ≈ 6241.5 μs ≈ 6.24 ms
```

**和工程注释里的数字完全吻合**：

```c
// 最短喂狗时间   47*97.5us = 4582.5us
// 最长喂狗时间   64*97.5us = 6241.5us
```

### 5.4 喂狗时刻对照表

| 喂狗间隔 | 结果 | 原因 |
| --- | --- | --- |
| **< 4.58 ms** | ❌ **复位** | 喂得太早，CNT 还大于窗口值 |
| **4.58 ~ 6.24 ms** | ✅ 正常 | 落在窗口内 |
| **> 6.24 ms** | ❌ **复位** | 喂得太晚，CNT 已数到 0x3F |
| **完全不喂** | ❌ 6.24 ms 后复位 | 同上 |

**本工程选 5 ms（`delay_1ms(5)`），落在窗口中间偏早的位置**。

> **窗口宽度的意义**：本工程窗口只有 `6.24 - 4.58 = 1.66 ms`，**余量很窄**。
> 这意味着**主循环里绝对不能出现「偶尔耗时超过 1.66 ms」的操作**——包括一次 `printf` 长字符串（第 04 篇算过：100 字节要 8.7 ms，**直接超标 5 倍**）。
>
> **这就是「窗口看门狗逼着代码必须非阻塞」**：它把「不许偷懒」变成了硬件强制。和第 05 篇（流水灯的阻塞坑）、第 09 篇（数码管必须非阻塞扫描）是同一条线索。

## 六、为什么要有「窗口」——设计意图

看到「喂太勤也复位」这个规则，第一反应都是「这不是找麻烦吗」。它的真实意图是**抓住一类特定故障**：

```
假设程序被干扰后，跳进了一个「疯狂喂狗的死循环」：
    while (1) { fwdgt_counter_reload(); }     ← 狗永远不咬人
        ↓
   FWDGT 视角：一直在喂狗，系统「活着」→ 永不复位 → 设备彻底僵死

加了窗口之后：
    喂得太勤 → CNT 还没数下来 → CNT > WIN → 立即复位  ✅ 故障被抓出来了
```

**两种看门狗的「防故障类型」对照**：

| 看门狗 | 能抓到什么故障 | 抓不到什么 |
| --- | --- | --- |
| **FWDGT** | 程序卡死、完全不喂狗 | **程序跑飞但仍在喂狗** |
| **WWDGT** | 卡死（太晚喂）+ **跑飞但乱喂（太早喂）** | — |

**还有一个常见用途**：窗口看门狗可以**监控任务时序**。比如「每 5 ms 必须完成一轮采集」，把窗口设成 4.5~6 ms，就相当于**给主循环加了一个「节拍正确性」的硬件检查**。

> **教材的第三种说法**（很贴切）：「防止程序异常死循环提早跑完」——即**防止程序跑得比设计的快**。

## 七、喂狗位置：一个必须想清楚的工程问题

### 7.1 喂狗应该放哪

```c
    while (1)
    {
        delay_1ms(5);
        // 喂狗
        wwdgt_counter_update(0x7F);
        cnt++;
    }
```

**本工程的喂狗放在主循环里，且是「无条件喂」**。这在学习阶段没问题，但**真实项目里要注意一件事**：

> **喂狗的位置，决定了看门狗能保护到什么。**

对比三种放法：

| 放法 | 保护能力 | 代价 |
| --- | --- | --- |
| **主循环无条件喂**（本工程） | 只能发现「主循环整个卡死」 | 某个任务卡住但主循环还在转 → 抓不到 |
| **每个任务都检查一遍再喂** | 能发现「任何一个任务卡死」 | 代码复杂，需要任务健康标志 |
| **在中断里喂** | **几乎没保护作用**（中断往往还在跑） | ❌ 不要这么做 |

**推荐的进阶做法**（可以自己实现）：

```c
// 每个任务跑完置一个标志
volatile uint8_t task_ok_flags = 0;

// 喂狗前检查所有任务是否都正常
if (task_ok_flags == ALL_TASKS_MASK)
{
    wwdgt_counter_update(0x7F);
}
// 否则不喂 → 让狗复位重来
```

### 7.2 使能时机的三条规则

| 规则 | 原因 |
| --- | --- |
| **所有初始化做完之后再使能** | 初始化耗时不确定，可能在开狗后超时（`bbce6b7` 那句注释就是这条） |
| **使能之后立刻进入喂狗循环** | 中间不要插耗时操作 |
| **调试阶段先注释掉看门狗** | 打断点、单步都会让程序停下 → 狗一定咬人（**这是初学者最容易被坑的地方**） |

> **调试时的经典现象**：程序在调试器里单步走，走到一半突然复位、断点丢失、看起来像「芯片坏了」。**十有八九是看门狗**。

## 八、参数速查表

### 8.1 独立看门狗 FWDGT

```c
void msp_fwdgt_config(void)          // main.c 里（尚未封装到 Hardware/）
{
    rcu_osci_off(RCU_IRC32K); delay_1ms(1); rcu_osci_on(RCU_IRC32K);   // 重启振荡器
    if (rcu_osci_stab_wait(RCU_IRC32K) == ERROR) { printf(...); return; } // 等稳定

    fwdgt_write_enable();                            // ★ 解除写保护，必须
    fwdgt_prescaler_value_config(FWDGT_PSC_DIV32);   // 32kHz/32 = 1000 Hz → 1ms/计数
    fwdgt_reload_value_config(100);                  // 100 个计数
    fwdgt_counter_reload();                          // 装初值
    fwdgt_enable();                                  // 启动
}
// 喂狗：fwdgt_counter_reload();
```

| 项目 | 值 |
| --- | --- |
| 时钟源 | IRC32K（内部 32 kHz，**独立于系统时钟**） |
| 计数时钟 | 32000 / 32 = **1000 Hz** |
| 重装载值 | `100` |
| **超时时间** | **100 ms** |
| 喂狗函数 | `fwdgt_counter_reload()` |
| 写保护 | **必须先 `fwdgt_write_enable()`** |
| 特殊注意 | 计数溢出时**置位复位**（无需额外使能） |

### 8.2 窗口看门狗 WWDGT

```c
void msp_wwdgt_config(void)          // main.c 里（尚未封装）
{
    rcu_periph_clock_enable(RCU_WWDGT);                  // 打开时钟
    wwdgt_config(0x7F, 0x50, WWDGT_CFG_PSC_DIV1);        // counter=127, window=80, DIV1
    wwdgt_enable();                                      // 启动
}
// 喂狗：wwdgt_counter_update(0x7F);
```

| 项目 | 值 |
| --- | --- |
| 时钟源 | **APB1 = 42 MHz**（168 MHz ÷ 4） |
| 固定分频 | ÷ 4096（硬件固定） |
| 计数频率 | 10253.90625 Hz → **97.523 μs/计数** |
| `counter` | `0x7F`（127） |
| `window` | `0x50`（80） |
| 危险线 | `0x3F`（63） |
| **喂狗窗口** | **4.58 ms ~ 6.24 ms** |
| 当前喂狗 | `delay_1ms(5)` → 约 5 ms |
| 喂狗函数 | `wwdgt_counter_update(0x7F)` |
| 复位条件 | ① CNT 递减到 `0x3F` ② **在窗口外喂狗** |
| 提前唤醒中断 | CNT = `0x40` 时置 EWI 标志（**本工程未使用**） |

### 8.3 两个看门狗的选择建议

| 需求 | 选谁 |
| --- | --- |
| 只想兜底防死机 | **FWDGT**（简单、独立时钟源、不用管精确时间） |
| 主时钟可能失效（停振、改频率） | **FWDGT**（WWDGT 依赖 APB1） |
| 要监控任务时序 / 防「跑太快」 | **WWDGT** |
| 要长时间超时（> 32 s） | 都不用，考虑 RTC 唤醒定时器 |
| 学习/初学项目 | **建议先用 FWDGT**，理解了再上 WWDGT |

## 九、排查清单

| 现象 | 优先检查 |
| --- | --- |
| **程序跑一会儿就复位（周期固定）** | 喂狗间隔 > 超时时间；**或喂狗太勤 < 最短时间**（WWDGT 独有） |
| **一开始就反复复位** | 看门狗使能太早，后面的初始化超时了 → **挪到 `main()` 末尾** |
| **烧录后连 `printf` 都来不及输出就重启** | 同上，且 `printf` 本身耗时（100 字节 ≈ 8.7 ms） |
| **调试器里单步就复位** | **正常现象**——打断点/单步时程序停了，狗必然咬人。调试时先注释掉看门狗 |
| 配置了分频和重装载值但超时时间没变 | **FWDGT 忘了 `fwdgt_write_enable()`**（写保护导致配置静默失败） |
| 超时时间差一个数量级 | 预分频/时钟频率算错（IRC32K 按 32 000 算，不是 32 768） |
| WWDGT 时间怎么算都不对 | 别忘 `/4096` 这个固定分频；APB1 = 168/4 = 42 MHz |
| WWDGT 一启动就复位 | `window` 值取错：**窗口值必须小于 `counter`、大于 `0x3F`** |
| 改了主循环的延时后行为全变 | 喂狗节奏被改变了 —— **喂狗间隔是硬约束，不能随手改** |
| 加了新任务后开始复位 | 新任务耗时把喂狗间隔撑破了窗口/超时 → 让任务非阻塞 |
| 看门狗想关掉关不掉 | **设计如此**：使能位只能由复位清除。想「关」只能改代码重新烧录 |
| 复位原因不明 | 可以用备份寄存器（第 11 篇）记录复位前的状态，或读 `RCU_RSTSCK` 判断复位来源 |
