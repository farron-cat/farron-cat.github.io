## 知识点地图

```
矩阵键盘 4×4
├── 需求与接线        16 个按键；行 PE8~PE11（输出），列 PE12~PE15
├── 为什么要矩阵      16 键只需 8 个 IO（独立按键要 16 个）
├── 准双向口（核心）  输出 + 开漏 + 内部上拉 = 8051 那种「写 0 拉低 / 写 1 高阻」
├── 为什么要开漏      避免推挽输出「线与短路」；高阻态才能当输入用
├── 两相扫描          相位1：行全低+列高阻 → 读列；相位2：列全低+行高阻 → 读行
├── 稳定延时          KP_SETTLE_US = 20 μs（上拉电阻 × 寄生电容的上升时间）
├── 键值编码          (列位 << 4) | 行位，按下=0
├── 键值重映射        查表 0xEE→1 … 0x77→16，转成「第几个键」
├── 封装              16 个操作宏 + KP_ALL_PINS 一次配 8 个引脚
└── 应用层退化        main 里只剩「扫一次、不为 0xFF 就打印」
```

## 学习目标

- 说清矩阵键盘为什么能省引脚，以及代价是什么（扫描 vs 独立读取）
- **理解「输出 + 开漏 + 上拉」为什么能模拟 8051 的准双向口**，以及为什么不能用 `GPIO_MODE_INPUT`
- 掌握两相扫描法：为什么必须先读列再读行，两次相位各自怎么配引脚
- 会推导键值编码 `(col << 4) | row`，并看懂重映射表
- 理解「稳定延时」的物理来源（上拉电阻 × 寄生电容），知道为什么 2 μs 不够、20 μs 够

## 一、需求与接线

### 1.1 为什么用矩阵

4×4 = 16 个按键。

| 方案 | 需要 IO | 扫描复杂度 |
| --- | --- | --- |
| 16 个独立按键 | **16 个**（还得各自接上下拉，PC0~PC3 那样） | 简单，但要 16 根线 |
| **4×4 矩阵** | **8 个**（4 行 + 4 列） | 需要扫描两轮 |

**省了一半引脚**，代价是：
- 需要**两相扫描**（一次读不出全部按键）
- 引脚要能**在「输出」和「输入」之间切换**——这就是本篇的难点所在

### 1.2 接线

```
            列1     列2     列3     列4
           PE12    PE13    PE14    PE15
             │       │       │       │
   行1 PE8 ──┼───┬───┼───┬───┼───┬───┼
             │   │   │   │   │   │   │
   行2 PE9 ──┼───┼───┼───┼───┼───┼───┼
             │   │   │   │   │   │   │
   行3 PE10──┼───┼───┼───┼───┼───┼───┼
             │   │   │   │   │   │   │
   行4 PE11──┼───┼───┼───┼───┼───┼───┼
             │   │   │   │   │   │   │
            每两条线的交叉点放一个按键（共 16 个）
```

| 分组 | 引脚 | 驱动层代号 |
| --- | --- | --- |
| 行（Row） | **PE8 / PE9 / PE10 / PE11** | `KROW1_PIN` ~ `KROW4_PIN` |
| 列（Col） | **PE12 / PE13 / PE14 / PE15** | `KCOL1_PIN` ~ `KCOL4_PIN` |

**全部挂在 GPIOE**，所以可以用一个掩码一次配好 8 个引脚：

```c
#define KP_PORT GPIOE
#define KP_RCU  RCU_GPIOE

#define KP_ALL_PINS (KROW1_PIN | KROW2_PIN | KROW3_PIN | KROW4_PIN | \
                     KCOL1_PIN | KCOL2_PIN | KCOL3_PIN | KCOL4_PIN)
```

## 二、关键难点：引脚既要输出又要输入

### 2.1 扫描需要两种「相位」

```
相位 1（找列）：把 4 行全部拉低，然后读 4 列
    ┌─────────────────────────────┐
    │ 行1 ──── 0 (低)              │   ← 行是「输出」
    │ 行2 ──── 0 (低)              │
    │ 行3 ──── 0 (低)              │
    │ 行4 ──── 0 (低)              │
    │        ↓ 按键被按下就导通      │
    │ 列1 ──── 读！0 表示第1列有键按下 │   ← 列是「输入」
    └─────────────────────────────┘

相位 2（找行）：把 4 列全部拉低，然后读 4 行
    ┌─────────────────────────────┐
    │ 列1~4 ── 0 (低)              │   ← 列变成「输出」
    │        ↓ 按键导通             │
    │ 行1 ──── 读！0 表示第1行有键按下 │   ← 行变成「输入」
    └─────────────────────────────┘
```

**注意：同一个引脚在相位 1 是输出、在相位 2 是输入**（列与行互换角色）。

**如果每换一个相位就 `gpio_mode_set()` 重新配置一次模式会怎样？**

- 要调 8 次函数/相位
- 切换瞬间引脚状态不确定，可能有毛刺
- 慢

**8051 的解法：准双向口**——同一个配置下，写 0 就输出低电平，写 1 就变成「高阻 + 上拉」，**自然能当输入读**。**本工程就是把这套特性用 GD32 的开漏输出 + 内部上拉复刻出来。**

### 3.1 引脚操作宏：16 个

头文件把「拉低 / 拉高 / 读」三类操作全展开成宏：

```c
/* ---- 行操作：开漏输出，写 0 拉低、写 1 高阻（由内部上拉拉高） ---- */
#define KROW1_L() gpio_bit_reset(KP_PORT, KROW1_PIN)
#define KROW2_L() gpio_bit_reset(KP_PORT, KROW2_PIN)
#define KROW3_L() gpio_bit_reset(KP_PORT, KROW3_PIN)
#define KROW4_L() gpio_bit_reset(KP_PORT, KROW4_PIN)
#define KROW1_H() gpio_bit_set(KP_PORT, KROW1_PIN)
#define KROW2_H() gpio_bit_set(KP_PORT, KROW2_PIN)
#define KROW3_H() gpio_bit_set(KP_PORT, KROW3_PIN)
#define KROW4_H() gpio_bit_set(KP_PORT, KROW4_PIN)

/* ---- 列操作 ---- */
#define KCOL1_L() gpio_bit_reset(KP_PORT, KCOL1_PIN)
...
#define KCOL4_H() gpio_bit_set(KP_PORT, KCOL4_PIN)

/* ---- 读引脚电平 ---- */
#define KROW1_READ() gpio_input_bit_get(KP_PORT, KROW1_PIN)
...
#define KCOL4_READ() gpio_input_bit_get(KP_PORT, KCOL4_PIN)
```

**16 个宏看着笨，但换来的是「代码能直接对着硬件说明书写」**：

```c
KROW1_L();     // 读起来就是「行1拉低」
KCOL1_READ();  // 「读列1」
```

### 3.2 初始化（第一版）

```c
void bsp_keypad_init(void)
{
    rcu_periph_clock_enable(KP_RCU);

    gpio_mode_set(KP_PORT, GPIO_MODE_OUTPUT, GPIO_PUPD_PULLUP, KP_ALL_PINS);
    gpio_output_options_set(KP_PORT, GPIO_OTYPE_OD, GPIO_OSPEED_50MHZ, KP_ALL_PINS);

    /* 默认全部拉高（高阻 + 上拉） */
    gpio_bit_set(KP_PORT, KP_ALL_PINS);
}
```

**这三行的意思**：

| 行 | 配置 | 效果 |
| --- | --- | --- |
| `gpio_mode_set(..., GPIO_MODE_OUTPUT, GPIO_PUPD_PULLUP, ...)` | **输出模式 + 内部上拉** | 输出级可用，同时上拉电阻也打开 |
| `gpio_output_options_set(..., GPIO_OTYPE_OD, ...)` | **开漏输出** | 写 0 → 真拉低；写 1 → **高阻**（输出级关断） |
| `gpio_bit_set(KP_PORT, KP_ALL_PINS)` | 全部写 1 | 全部高阻，被内部上拉拉高 = **全部「释放」** |

**凑起来就是准双向口**（第六章展开）：

```
写 0  →  输出级导通到 GND  → 引脚是低电平（能「拉低」别人）
写 1  →  输出级关断，引脚高阻 → 由内部上拉拉高（能「读」别人）
```

### 3.3 扫描（第一版）

```c
unsigned char KeypadScanHex(void)
{
    unsigned char scaned_key_col;
    unsigned char scaned_key_row;
    unsigned char scaned_key_hex = 0xFF;

    /* ---- 列检测：行全低，列全高阻(上拉) ---- */
    KROW1_L();
    KROW2_L();
    KROW3_L();
    KROW4_L();
    KCOL1_H();
    KCOL2_H();
    KCOL3_H();
    KCOL4_H();

    KeypadDelayUs(2);              // ← 第一版的自定义延时

    scaned_key_col = ((unsigned char)KCOL1_READ() << 0) | ((unsigned char)KCOL2_READ() << 1)
                   | ((unsigned char)KCOL3_READ() << 2) | ((unsigned char)KCOL4_READ() << 3);

    if (scaned_key_col != 0x0F)    // 不是「全高」说明有键按下
    {
        /* ---- 行检测：列全低，行全高阻(上拉) ---- */
        KCOL1_L();
        KCOL2_L();
        KCOL3_L();
        KCOL4_L();
        KROW1_H();
        KROW2_H();
        KROW3_H();
        KROW4_H();

        KeypadDelayUs(2);

        scaned_key_row = ((unsigned char)KROW1_READ() << 0) | ((unsigned char)KROW2_READ() << 1)
                       | ((unsigned char)KROW3_READ() << 2) | ((unsigned char)KROW4_READ() << 3);

        scaned_key_hex = (scaned_key_col << 4) | scaned_key_row;
    }

    return scaned_key_hex;
}
```

### 3.4 扫描过程逐步推演

**先约定**：每个读回来的 bit **为 0 表示「被按下」**（因为按下会把该线拉低）。

**假设按下了「第 1 行第 2 列」那个键（下面记作 R1C2）**：

```
【相位 1：列检测】
   驱动：行1~4 = 低；列1~4 = 高阻（被上拉成高）
   此时 R1C2 按下 → 列2 通过按键连到「低电平的行1」 → 列2 被拉低

   读回来：列1=1  列2=0  列3=1  列4=1
           scaned_key_col = (1<<0)|(0<<1)|(1<<2)|(1<<3) = 0b1101 = 0x0D

   → 第 2 位（值 2）是 0 → 「是第 2 列」

【相位 2：行检测】
   驱动：列1~4 = 低；行1~4 = 高阻（被上拉成高）
   此时 R1C2 按下 → 行1 通过按键连到「低电平的列2」 → 行1 被拉低

   读回来：行1=0  行2=1  行3=1  行4=1
           scaned_key_row = 0b1110 = 0x0E

   → 第 0 位（值 1）是 0 → 「是第 1 行」

【合成键值】
   scaned_key_hex = (0x0D << 4) | 0x0E = 0xDE
```

**对照 `KeypadHexCodeRemap()` 的表**：

```c
case 0xDE:
    return 2;       // ← R1C2 是第 2 个键 ✅
```

### 3.5 为什么 `scaned_key_col != 0x0F` 就能判断「有键按下」

`0x0F` = `0b0000 1111` = **4 列全高**（没有任何一列被拉低）= 没有按键。

**这个判断还是一个重要的优化**：没有按键时**不做第二个相位**，直接返回 `0xFF`。因为相位 2（列输出低）会让整条列线灌电流，没必要白做。

## 四、提交 `b8ca018`：准双向口 + 修正稳定延时

**提交信息**：`[更新] 矩阵键盘 使用输出+开漏模式+开启内部上拉来模拟8051的准双向`

这次提交**没有改变扫描逻辑**，改的是三处「细节」，但每一处都很关键。

### 4.1 稳定延时：2 μs → 20 μs（并写清了原因）

```c
-    KeypadDelayUs(2);
+    delay_1us(KP_SETTLE_US);

/* 扫描相位后的稳定延时（us）
   行/列释放后要靠内部上拉（典型几十 kΩ）把线拉高，
   与排线+键盘的寄生电容（约 50~150pF）形成数 us 的上升时间，
   2us 往往还没越过输入门限，会把"未升上去的线"误判成按下。
   若后续在硬件上加了 4.7k~10k 外部上拉，可适当减小该值。 */
#define KP_SETTLE_US 20
```

**这段注释是本篇最有价值的内容之一**——它把「为什么要延时」这个玄学问题量化了：

```
上拉电阻 R ≈ 几十 kΩ（内部上拉典型 40 kΩ 左右）
走线 + 键盘的寄生电容 C ≈ 50 ~ 150 pF

RC 时间常数： τ = R × C = 40kΩ × 100pF = 4 μs
上升到门限（约 0.5×VDD 需要 0.7τ ≈ 2.8 μs；到 0.9×VDD 需要 2.3τ ≈ 9.2 μs）

所以：
   2 μs  → 线还没升到门限 → 读到「低」→ 误判成「按下」  ❌
   20 μs → 足够升到高电平 → 读数可信                    ✅
```

**这解释了一个很反直觉的现象**：**「没有按键」反而容易误报有按键**。因为「未被拉高的线」在读的时候还是低电平，看起来就像「被按键拉低了」。

| 硬件条件 | 建议的稳定延时 |
| --- | --- |
| 只有内部上拉（几十 kΩ） | **≥ 20 μs**（本工程取 20） |
| 加了 4.7 kΩ ~ 10 kΩ 外部上拉 | 可以适当减小（上升时间缩短约 10 倍） |

> 顺带一提，这次提交把延时函数从自定义的 `KeypadDelayUs(2)` 换成了第 01 篇就有的 **`delay_1us()`**（并 `#include "systick.h"`）——**用现成的基础设施，别自己造轮子**。

### 4.2 输出速度：50 MHz → 2 MHz

```diff
-    gpio_output_options_set(KP_PORT, GPIO_OTYPE_OD, GPIO_OSPEED_50MHZ, KP_ALL_PINS);
+    gpio_output_options_set(KP_PORT, GPIO_OTYPE_OD, GPIO_OSPEED_2MHZ, KP_ALL_PINS);
```

**键盘扫描是「人按一下才动」的低速信号**，2 MHz 远远够用。**速度配太高会带来**：

| 代价 | 说明 |
| --- | --- |
| EMI 变大 | 边沿越陡，高频谐波越强，辐射越大 |
| 振铃 / 过冲 | 快速边沿遇上长排线的寄生电感，波形会振铃，可能误触发 |
| 功耗变大 | 快速翻转的输入电容充放电电流更大 |

**和第 02 篇 LED 只配 2 MHz 是同一个道理**——「够用就好」是个工程原则。

### 4.3 类型统一：`unsigned char` → `uint8_t`

```diff
-unsigned char KeypadScanHex(void)
+uint8_t KeypadScanHex(void)
```

`unsigned char` 和 `uint8_t` 在 8 位机上通常等价，但**统一用 `<stdint.h>` 里的定长类型更明确**（表达「我就是要 8 位」「我就是要 16 位」），这在嵌入式里是标准做法。**这是「解决警告」类提交的常见内容**（第 04 篇的 `56609c3` 也是）。

### 4.4 新增 `KeypadScan()`：把两步合成一步

```c
unsigned char KeypadScan(void)
{
    uint8_t hex = KeypadScanHex();
    return KeypadHexCodeRemap(hex);
}
```

应用层从此只需调一个函数：

```c
int key = KeypadScan();
if (key != 255)                  // 0xFF = 没有按键
    printf("key: %d\n", key);    // 打印 1~16
```

**三个函数的分层很清楚**：

| 函数 | 层次 | 返回值 |
| --- | --- | --- |
| `KeypadScanHex()` | 硬件层 | 原始 hex（`0xEE`/`0xFF`） |
| `KeypadHexCodeRemap()` | 映射层 | 键号 1~16，或 `0xFF` |
| `KeypadScan()` | 应用层接口 | **同上**（把两步包起来） |

**为什么要分两层，不直接在 `KeypadScanHex()` 里返回 1~16？** 因为**保留 hex 便于调试**：

```
按同一个键，Hex 层告诉你「硬件读到的是 0xDE」，
   映射层告诉你「这是第 2 个键」。
     ↑ 如果键位对不上，看 hex 就知道是「接线错」还是「映射表错」
```

**不改扫描逻辑、只加一个包装函数**，是不破坏现有代码的扩展方式。

### 4.5 重映射表：从 hex 到键号

```c
uint8_t KeypadHexCodeRemap(uint8_t hex_code)
{
    switch (hex_code)
    {
    case 0xEE: return 1;     // 行1 列1
    case 0xDE: return 2;     // 行1 列2
    case 0xBE: return 3;     // 行1 列3
    case 0x7E: return 4;     // 行1 列4

    case 0xED: return 5;     // 行2 列1
    case 0xDD: return 6;
    case 0xBD: return 7;
    case 0x7D: return 8;

    case 0xEB: return 9;     // 行3 列1
    ...
    case 0xE7: return 13;    // 行4 列1
    case 0xD7: return 14;
    case 0xB7: return 15;
    case 0x77: return 16;

    default: return 0xFF;    // 没有按键 / 多键同按
    }
}
```

**编码规律（看懂这个规律，表就不用背）**：

```
hex 的高 4 位 = 列位图（0 表示该列被按下）
hex 的低 4 位 = 行位图（0 表示该行被按下）

0xEE = 0b 1110 1110
       └─列1─┘ └─行1─┘      → 第 1 行第 1 列
0xDE = 0b 1101 1110
       └─列2─┘ └─行1─┘      → 第 1 行第 2 列
0x7E = 0b 0111 1110
       └─列4─┘ └─行1─┘      → 第 1 行第 4 列
0x77 = 0b 0111 0111
       └─列4─┘ └─行4─┘      → 第 4 行第 4 列
```

**键号编号规则**：从左到右、从上到下 → `键号 = (行 - 1) × 4 + 列`。

| hex | 行 | 列 | 键号 |
| --- | --- | --- | --- |
| `0xEE` | 1 | 1 | 1 |
| `0xDE` | 1 | 2 | 2 |
| `0xBE` | 1 | 3 | 3 |
| `0x7E` | 1 | 4 | 4 |
| `0xED` | 2 | 1 | 5 |
| ... | | | |
| `0x77` | 4 | 4 | 16 |

**为什么用 `switch` 查表而不是用公式算？** 因为 `hex` 的位是「按下 = 0」的反向编码，要用公式算得先取反、再找最高位——**比查表麻烦且不易读**。**16 项的表换来「一眼看清每个键对应哪个 hex」，值。** 如果以后键位排列要改（比如变成电话键盘布局），**只改这张表**。

### 4.6 初始化：注释补全了「为什么必须用输出模式」

```c
void bsp_keypad_init(void)
{
    rcu_periph_clock_enable(KP_RCU);

    /* 准双向口：输出 + 开漏 + 内部上拉
       写 0 -> 输出级把引脚真正拉低
       写 1 -> 输出级关断（高阻），由内部上拉拉高
       注意：必须是 GPIO_MODE_OUTPUT，输入模式下输出级关闭，
             引脚只是悬空，写 0 拉不低、写 1 也拉不高。 */
    gpio_mode_set(KP_PORT, GPIO_MODE_OUTPUT, GPIO_PUPD_PULLUP, KP_ALL_PINS);
    gpio_output_options_set(KP_PORT, GPIO_OTYPE_OD, GPIO_OSPEED_2MHZ, KP_ALL_PINS);

    /* 默认全部释放（外部/内部上拉拉高） */
    gpio_bit_set(KP_PORT, KP_ALL_PINS);
}
```

**那句「必须是 `GPIO_MODE_OUTPUT`」是这次提交最值钱的一行注释**：

| 配置 | 写 0 | 写 1 | 能拉低列线吗 |
| --- | --- | --- | --- |
| `GPIO_MODE_INPUT`（错误直觉） | 输出级**关闭**，写不了 | 输出级关闭 | **不能**（引脚只是悬空） |
| `GPIO_MODE_OUTPUT` + 开漏（正确） | 输出级导通到 GND | 输出级关断，上拉生效 | **能** |

**很多人的第一反应是「要读引脚所以配输入模式」——这是错的**。准双向口的本质是「输出级可关断」，所以模式必须是**输出**，靠**开漏 + 上拉**来获得「可读」的能力。

## 六、专题：什么是「准双向口」

这是本篇的核心知识点，也是「一个 8051 老概念如何在 GD32 上复现」的完整案例。

### 6.1 8051 的准双向口是什么

在 8051 上，P1/P2/P3 这些口有个著名的特性：

```
写 0  →  引脚输出低电平（可以驱动别人）
写 1  →  引脚变成「弱上拉」，可以被外部拉低（可以读别人）

所以一个引脚不用切换方向，就能「一会儿输出、一会儿输入」。
```

这是 8051 时代省引脚、省配置的经典设计，**矩阵键盘、I²C 这类「双向总线」都靠它**。

### 6.2 GD32 没有准双向口，怎么复刻

GD32/STM32 的 GPIO 是「方向明确」的（要么输出要么输入），但**开漏输出 + 上拉**可以达到同样的效果：

```
GD32 的配置：GPIO_MODE_OUTPUT + GPIO_OTYPE_OD + GPIO_PUPD_PULLUP

写 0  →  开漏输出级的 NMOS 导通 → 引脚被拉到 GND        = 「强下拉」✅
写 1  →  开漏输出级的 NMOS 关断 → 引脚高阻 → 上拉电阻拉到高 = 「弱上拉」✅
                                     ↑
                          此时外部器件可以把这个高电平拉低
                          → 于是「读引脚」就能知道外部状态 ✅
```

**和 8051 的行为完全一致**。这就是提交信息里说的「模拟 8051 的准双向」：

| 行为 | 8051 准双向口 | GD32 开漏 + 上拉 |
| --- | --- | --- |
| 写 0 | 强下拉到 GND | 开漏输出拉低到 GND |
| 写 1 | 弱上拉（可被外部拉低） | 高阻 + 内部上拉（可被外部拉低） |
| 不用切方向就能读 | ✅ | ✅ |
| 需要额外硬件 | 无 | 无（用内部上拉） |

### 6.3 为什么不直接用推挽输出

**推挽输出（`GPIO_OTYPE_PP`）不能这么用**，原因有两层：

**① 推挽写 1 是「强上拉」——会打架**

```
如果两行两列都用推挽：
   行1 输出高（强）+ 列1 输出低（强）
   两者之间通过按键直接连通 → 一个强上拉 vs 一个强下拉 → 短路大电流

开漏写 1 是「高阻」，不会和别人的低电平打架 —— 这就是「线与」的前提。
```

**② 推挽写 1 时读回来永远是 1**

```
推挽输出高电平时，引脚被强制拉高，外部想拉低也拉不下去
→ 读回来永远是 1 → 判断不出「列有没有被按下」
```

**这就是「开漏输出」在 GPIO 那章里的典型用途之一**（另一个是 I²C 总线、电平转换）。参考笔记 `GPIO.md` 第 3.6 节和 7.x 节有更完整的开漏用途说明。

### 6.4 用开漏做矩阵键盘的完整时序图

```
【相位 1：行输出低，列当输入】

  PE8 (行1)  ──── 0 ──────────────────────
  PE9 (行2)  ──── 0 ──────────────────────
  PE10(行3)  ──── 0 ──────────────────────
  PE11(行4)  ──── 0 ──────────────────────
                          ↑ 20μs 稳定
  PE12(列1)  高阻 ── 上拉 ── 读到 1 或 0 ──
  PE13(列2)  高阻 ── 上拉 ── 读到 0（被按下的键拉低）← 命中！
  PE14(列3)  高阻 ── 上拉 ── 读到 1
  PE15(列4)  高阻 ── 上拉 ── 读到 1

【相位 2：列输出低，行当输入】

  PE12~PE15 ──── 全部 0 ──────────────────
                          ↑ 20μs 稳定
  PE8 (行1)  高阻 ── 上拉 ── 读到 0（被按下的键拉低）← 命中！
  PE9 (行2)  高阻 ── 上拉 ── 读到 1
  PE10(行3)  高阻 ── 上拉 ── 读到 1
  PE11(行4)  高阻 ── 上拉 ── 读到 1
```

| 现象 | 优先检查 |
| --- | --- |
| 完全读不到按键 | `bsp_keypad_init()` 没调；行/列引脚号接错；`GPIO_OTYPE_OD` 漏了 |

| 读到的键值全乱 / 每次不一样 | 用了 `GPIO_MODE_INPUT`（写 0 拉不低）；或没开内部上拉 |
| 按键发热 / 电流大 | 用了**推挽**输出（`GPIO_OTYPE_PP`）——必须开漏 |
| 只有部分键能读到 | 某一行/列的引脚号写错；排线接触不良 |
| 按下第 1 行读出来是第 2 行 | `KeypadHexCodeRemap()` 表里行/列搞反了 |

| 同一列的多个键互相影响 | 正常现象——**动态扫描每次只应有一个键被按下**，多键同按要靠软件约定 |
| 换了一块键盘就全不对 | 行/列接线顺序变了 → 只需改 `KeypadHexCodeRemap()` 的表，扫描逻辑不用动 |
| 编译报 `KeypadDelayUs` 未定义 | `b8ca018` 把它换成了 `delay_1us()`，要 `#include "systick.h"` |

| 稳定延时够不够 | ❌ 2 μs（可能误判） | ✅ 20 μs（附 RC 原理） |
| 输出速度合理吗 | ❌ 50 MHz（EMI 大） | ✅ 2 MHz |
| 类型是否规范 | ❌ `unsigned char` | ✅ `uint8_t` |
| 应用层接口 | ❌ 要调两步 | ✅ `KeypadScan()` 一步 |
