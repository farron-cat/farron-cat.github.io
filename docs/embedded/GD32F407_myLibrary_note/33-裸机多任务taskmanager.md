## 一、问题：主循环是怎么一步步变长的

### 1.1 从"一个 delay"到"一堆 if"

回顾本工程 `main.c` 的 `while(1)` 是怎么长起来的（每一篇都在往里加东西）：

| 阶段 | `while(1)` 里有什么 | 出处 |
| --- | --- | --- |
| 05 之前 | 只有一个流水灯，**里面全是 `delay_1ms()`** | 02 |
| 05 | 充电流水灯改成状态机 + `get_us_cnt()` 时间戳 | 05 |
| 09/26 | 数码管扫描被**塞进 SysTick 中断**（不敢放主循环，怕被 delay 拖慢） | 09 / 26 |
| 17/31 | 中断只置标志，**主循环里加两个 `if (g_xxx_int_flag)`** | 17 / 31 |
| 最终（`dcdda0d`） | 5 个"功能块"平铺在一个 `while(1)` 里，**谁快谁慢全靠注释说明** | 31 |

**`main.c` 的 `while(1)` 长成了这样**（`dcdda0d` 版本，缩略）：

```c
while (1)
{
    if (g_rtc_int_flag)        { g_rtc_int_flag = 0;       on_rtc_interrupt(); }   // 事件型
    if (g_touch_key_int_flag)  { g_touch_key_int_flag = 0; on_touch_key_interrupt(); } // 事件型

    bsp_188_leds_set_num(bsp_ntc_get_tem());   // 每次循环都做
    bsp_pcf8563_read_time(&time);              // 每次循环都做（I2C！）
    oled_show_rtc(&time);                      // 每次循环都做（刷 1024 字节 I2C，38 ms！）
    bsp_digital_leds_test_tick();              // 内部自己有 1 s 时间门
}
```

**问题一目了然**：

| 问题 | 表现 |
| --- | --- |
| **没有"周期"概念** | 谁想 10 ms 跑一次、谁想 1 s 跑一次，**只能各自在函数内部用 `get_us_cnt()` 判断** |
| **顺序固定** | OLED 刷屏（38 ms）在前，后面的任务全被推迟 38 ms |
| **想加一个功能就要改主循环** | 每加一个模块，`main.c` 就多一行，**越加越乱** |
| **看不出"谁多快跑一次"** | 只有读每个函数的内部实现才知道 |

### 1.2 教材给出的四级台阶

教材（`Textbook/MORE/裸机多任务.mhtml`）把这件事拆成四步，非常清楚：

| 台阶 | 做法 | 代码长相 | 解决了什么 |
| --- | --- | --- | --- |
| **① 阻塞延时** | `LED1_ON(); delay_1ms(250); LED1_OFF(); delay_1ms(250);` | 顺序执行 | 最直观，但**一件事占满 CPU** |
| **② 时间切片** | 定时器 1 ms 中断里 `count++` | 中断里只加一 | 有了"全局时间"的概念，**1 ms 是最小粒度** |
| **③ 分时调用** | 主循环里 `if (count % 500 == 0) led_logic();` | 按 tick 取模 | 多个任务"看起来同时在跑" |
| **④ 时间独立管理** | 每个任务函数内部自己判断时间 | 任务自己管自己 | **调度器不用知道每个任务要多久** |

**教材的"总结泛化"（这一步是精华）**：

> 抽象化具体任务特点：**`period`（任务执行周期）、`delay`（当前绝对时间）、`call`（任务逻辑函数）**
> 调度管理：**容器进行任务的注册和管理**、**全局计数改变状态**、**任务执行判断**
> 任务调度入口：**全局计数在定时器中断中进行，任务调度执行在主 while 中进行**

**本工程的 `taskmanager` 就是这段文字的直接翻译** —— 只不过它把 `delay`（绝对时间）换成了 `cnt`（倒计时），**这一步换得很关键**（见 2.3）。

### 1.3 本工程处在这一演进线的哪一格

```
02（delay 阻塞）→ 05（状态机 + 时间戳）→ 09/26（扫描进中断）→ ★ 33（任务表）→ 34（FreeRTOS）
                                                                ↑ 本篇
```

**注意 09/26 那一步是"绕过问题"而不是"解决问题"**：
数码管扫描不敢放主循环（怕被 delay 拖），就**塞进 SysTick 中断**。
结果 `SysTick_Handler()` 变成了"3 个扫描 + 1 个任务计数"的杂货铺（第 21 篇 §15 算过这笔账）。

**`taskmanager` 是第一次"正面解决"**：**把"什么时候该跑谁"从"中断里硬塞"变成"一张表 + 一个调度函数"**。

## 二、`taskmanager` 的设计（48 行）

### 2.1 `TASK` 结构体

```c
typedef void (*task_callback)(void);        // 任务函数：无参无返回

typedef enum {
    STOP,   // 停止（等待计数器到 0）
    START   // 执行（已被调度，等主循环来调）
} TASK_STATE;

typedef struct {
    task_callback func;   // 任务函数
    TASK_STATE    state;  // 任务状态
    uint64_t      period; // 任务执行周期  ← 单位是"节拍"，不是毫秒
    uint64_t      cnt;    // 任务执行时间计数器（倒计时）
} TASK;
```

**四个字段的关系**：

```
     SysTick 每 1 ms 调 task_switch()：
         cnt-- ；cnt 到 0 → state = START

     主循环调 task_schedule()：
         发现 state == START → 执行 func() → cnt = period，state = STOP
```

**画成时间轴**（以 `period = 3` 为例）：

```
t(ms)   0    1    2    3    4    5    6    7
cnt     3 →  2 →  1 →  0 →  (执行) → 3 →  2 →  1 ...
state   STOP STOP STOP START STOP   STOP STOP STOP
                     ↑              ↑
              主循环执行一次      重置为 period

→ 实际周期 = 3 个节拍 = 3 ms（前提：主循环能在 1 ms 内转一圈）
```

> **`period` 的单位是"节拍数"**，因为 `task_switch()` 是 **1 ms** 调一次（`SysTick_Handler` 里 `div >= 1000` 才调，而 SysTick 本身是 1 MHz → 1 ms 一次）。
> 所以 `period = 10` 就是 **10 ms**。**这个换算关系必须记牢**：换 SysTick 频率，整张表的周期全变。

### 2.2 `task_switch()`：在 SysTick 里倒计时

```c
void task_switch(void)
{
    for (uint8_t i = 0; i < tasks_len; i++)
    {
        if (tasks_list[i].cnt == 0)
            continue;                 // ★ 已经"待执行"，别再减（否则下溢）

        tasks_list[i].cnt--;          // 倒计时
        if (tasks_list[i].cnt == 0)
        {
            tasks_list[i].state = START;   // 到点，置"待执行"
        }
    }
}
```

**两个细节值得注意**：

| 细节 | 为什么 |
| --- | --- |
| **`cnt == 0` 就 `continue`** | 如果主循环还没来得及执行（state 还是 START），`cnt` 已经是 0。**再减一次就下溢成 `0xFFFFFFFF`**，这个任务**永远不再触发**。这一行是"防御性编程" |
| **只置 `state`，不执行 `func()`** | 中断里不能做重活（第 17/31 篇的教训）。**中断只负责"标记到点了"，执行留给主循环** |

> **这和第 31 篇的 `g_touch_key_int_flag` 是同一个思想**：
> **"上半部（中断）只做标记，下半部（主循环）做重活"**。
> 区别只是：一个是"某个事件发生了"，一个是"某个任务的周期到了"。

### 2.3 ★ 为什么是"倒计时"而不是"`count % period`"

教材的写法是：

```c
if (count % 500 == 0) { led_logic(); }    // 教材版
```

**本工程改成了倒计时**。这两者**在"每次都能准时检查"时等价**，但一旦主循环偶尔慢一拍，差别就出来了：

| 场景 | `count % period == 0` | **`cnt` 倒计时（本工程）** |
| --- | --- | --- |
| 正常（每 1 ms 转一圈） | ✅ 每 period ms 触发一次 | ✅ 一样 |
| **主循环这一圈用了 3 ms**（被 OLED 刷屏拖住） | ❌ **`count` 跳过了 500 这个值 → 这一拍永远丢失**（界面会"卡一下"） | ✅ `cnt` 到 0 后**一直保持 0**，主循环一来就执行 → **补上这一拍，只是晚了几毫秒** |
| 主循环连续卡 1 秒 | ❌ 丢掉 2 次（只执行最后落在整倍数上的一次） | ✅ 只执行 1 次（不堆积） |

**结论**：

```
取模法： "在时间轴的整点上执行"     → 依赖"每个整点都被检查到" → 会漏
倒计时： "距上次执行满 period 就执行" → 不依赖节拍对齐       → 最多晚，不会漏
```

> **这就是"事件式 vs 时刻式"的区别**：
> **`count % period` 是"时刻式"**（我要在 500、1000、1500 这些**绝对时刻**跑）；
> **`cnt` 倒计时是"间隔式"**（距上次跑完**至少** 500 ms 就跑）。
>
> **在会抖动的裸机环境里，"间隔式"永远比"时刻式"可靠** —— 这也是 RTOS 里 `vTaskDelay(500)` 的语义（延时 500 tick，不是"等到能被 500 整除"）。
> 所以**本工程这一步改动，实际上是在向 RTOS 的语义靠拢**。

### 2.4 `task_schedule()`：在主循环里执行

```c
void task_schedule(void)
{
    for (uint8_t i = 0; i < tasks_len; i++)
    {
        if (tasks_list[i].state == START)
        {
            tasks_list[i].func();            // 执行任务
            tasks_list[i].cnt = tasks_list[i].period;  // 重置倒计时
            tasks_list[i].state = STOP;      // 回到"等待"
        }
    }
}
```

**注意重置的顺序**：**先 `func()`，后重置 `cnt`**。

> 如果反过来（先重置再执行），执行期间如果又过了一个周期，`cnt` 会被中断再减一次 —— 但这里 `state` 已经是 STOP 了，中断会重新从 `period` 往下减，**不会出错**。
> 不过**先执行后重置**的语义更清楚：**"这一次的周期，从这次执行完开始算"**（周期性任务常见的定义）。

**还有一个隐含约束**：**`func()` 必须"短"**。

```
一个 tick 里可能同时有多个任务到点（比如 20 ms 时，10 ms 和 20 ms 的任务都会到）
→ task_schedule() 会依次执行它们
→ 如果第一个任务耗时 30 ms，第二个就被推迟 30 ms，而且这一整个 tick 的"1 ms 精度"全没了
```

本工程的做法是**错开相位**（见 2.5）来减少"同时到点"的概率。

### 2.5 任务表：6 个任务与它们的相位

```c
static TASK tasks_list[] = {
    {app_input_touch_key_task,   STOP, 10,   1},   // 触摸按键事件   10 ms，首次 1 ms 后
    {app_show_digital_leds_task, STOP, 10,   2},   // 74HC595 数码管 10 ms，首次 2 ms 后
    {app_show_dot_matrix_task,   STOP, 10,   3},   // 点阵屏          10 ms，首次 3 ms 后

    {app_show_188_leds_task,     STOP, 20,   5},   // 188 数码管      20 ms，首次 5 ms 后
    {app_show_iic_oled_task,     STOP, 100,  10},  // IIC OLED       100 ms，首次 10 ms 后

    {app_show_pcf8563_task,      STOP, 1000, 20},  // RTC 中断事件    1 s，  首次 20 ms 后
    // {app_show_ntc_task,       STOP, 500,  30},  // 串口打印温度（已注释）
};
```

**★ `cnt` 初值 `1, 2, 3, 5, 10, 20` 是干什么的？**

如果全部写 `0`（或全部写 `period`），那么在**第 10 ms、20 ms、100 ms、1000 ms 这些整点，会有多个任务同时到点**：

```
t=10ms：touch_key + digital_leds + dot_matrix  三个任务同时 START
t=100ms：上面三个 + iic_oled                  四个同时
t=1000ms：全部六个同时 ← 这一拍最重
```

**错开初值之后**，第一次触发被摊开（1/2/3/5/10/20 ms），之后虽然还会**周期性重合**（因为 10 和 20 的最小公倍数是 20），但**至少"上电第一轮"不会挤在一起**。

| 观察 | 说明 |
| --- | --- |
| 错开只能缓解、不能根治 | 10/20/100/1000 这些周期的最小公倍数是 1000 ms → **每 1 秒还是会有一次"六任务同拍"** |
| 真正的解法 | ① 把长任务切短；② **换成 RTOS 的独立任务**（各跑各的，由调度器按优先级抢） |
| 这就是 RTOS 要解决的问题之一 | **见第五章第 2 条** |

**另外注意被注释掉的 `app_show_ntc_task`**（500 ms 串口打印）—— 说明作者试过，**因为打印会阻塞（~2 ms）而关掉了**。这是"裸机调度里，一个慢任务拖全表"的直接证据。

```
│                              app_input_keypad_task()     ★ 扫矩阵键盘（但没注册）
├── app_show/                ← 显示：谁负责"把数据变成画面"
│   └── app_show.c             app_show_init()

                               app_test_pcf8563_set_time_alarm

```

**这个划分的好处**：

| 好处 | 说明 |
| --- | --- |
| **`main.c` 只剩"初始化 + 启动"** | 从 264 行降到 **约 170 行初始化清单**（`7163c92` 又删掉 87 行的测试代码） |
| **"输入 / 显示"职责分离** | 以后加一个输入（比如再加个摇杆），只动 `app_input/`；加一块屏，只动 `app_show/` |
| **测试代码集中** | `app_test_*` 一眼看完"上电都验了什么" |
| **为 RTOS 铺路** | 每个功能已经是一个 `xxx_task()` 函数 → 换 RTOS 时**直接 `xTaskCreate(xxx_task)` 就行** |

> **注意最后一条**：**`7f55853` 是 10-16，FreeRTOS 移植是 10-19。**
> **先"函数化"，再"任务化"** —— 这个顺序是对的：**如果 `main.c` 里还是一坨平铺代码，移植 RTOS 时无从下手**。

### 3.2 `app.h`：一个"总头文件"

```c
#ifndef APP_H
#define APP_H

#include "bsp_keys.h"        // ← 12 个 bsp 头
#include "bsp_adkey.h"
...
#include "bsp_touch_key.h"
#include "bsp_keypad.h"

#include "msp_exti.h"        // ← 还引了 Hardware 层
#include "systick.h"
#include "bmp.h"

extern Time_pcf time;        // ← 全局变量声明（定义在 app_test.c）
extern Alarm alarm;

void app_input_init(void);
... （所有 app_xxx_task 的声明）
#endif
```

**这个做法的取舍**：

| 优点 | 代价 |
| --- | --- |
| **每个 `app_*.c` 只需 `#include "app.h"` 一行** | **`app.h` 变成"上帝头"**：改任何一个 bsp 头，所有 app 文件全部重编 |
| 所有任务函数声明集中在一处，**一眼看清 App 层提供什么** | **依赖关系被隐藏**：打开 `app_show.c` 看不出它到底用了哪几个驱动 |
| 新手不容易漏 include | **`msp_exti.h` / `bmp.h` 这类"某一块专用"的头也被所有人看见** |

> **对比第 15/16 篇的教训**：那里强调"**分层要清楚、接口要统一**"。
> `app.h` 是"**用一个头文件换开发便利**"的典型做法 —— 小项目（20 个模块以内）非常划算，
> **模块再多就该拆成 `app_input.h` / `app_show.h` 了**（现在 `app.h` 已经把 3 个子目录的声明混在一起了）。

### 3.3 搬完之后 `main.c` 剩什么

```c
int main(void)
{
    nvic_priority_group_set(...);   // ① 系统级配置
    rcu_timer_clock_prescaler_config(...);
    systick_config();

    msp_uart_init();  msp_exti_init();  msp_rtc_init();   // ② 片上外设
    msp_iic_init();   msp_adc_init();   msp_spi_init();

    bsp_leds_config(); ...  bsp_dot_matrix_init();        // ③ 片外外设（十几行）

    app_input_init();  app_show_init();                   // ④ App 层初始化

    app_test_flash();  app_test_spi_oled(); ...           // ⑤ 上电自测
    // 看门狗（注释）

    while (1)
    {
        task_schedule();                                  // ⑥ 调度器：只剩这一行
    }
}
```

**★ 从"5 个功能块平铺"变成"1 行 `task_schedule()`"** —— 这是本篇最直观的收益。

**但也要看到代价**：**"什么时候跑谁"从"看代码"变成了"看表"**。
新来的人必须打开 `taskmanager.c` 才知道"OLED 每 100 ms 刷一次"。
所以**任务表必须有注释**（本工程的表只有 `period` 数字，没有注释说明每个任务干什么 —— 这是个可以改进的点）。

## 五、★ 这个框架的 6 条局限（为什么后来要上 FreeRTOS）

**这个框架已经很好用了**（6 个任务、精度 1 ms、代码 48 行）。但它有 6 条**结构性的**局限：

| # | 局限 | 现象 | 根因 |
| --- | --- | --- | --- |
| **1** | **不能抢占** | 一个任务跑 30 ms，后面所有任务全等它 | 所有任务在**同一个 `for` 循环里串行执行** |
| **2** | **没有优先级** | 按键响应（要快）和 OLED 刷屏（可以慢）**同权** | `TASK` 结构体里没有 `priority` 字段 |
| **3** | **长任务拖垮全表** | 那个被注释掉的 `app_show_ntc_task`（串口打印 2 ms）就是例子 | 调度器**没有"时间片"概念**，只有"顺序" |
| **4** | **没有同步机制** | 两个任务都想用 I2C/SPI → **只能靠"中断只置标志"这种手工约定**（第 31 篇） | **没有信号量/互斥量** |
| **5** | **任务表是编译期固定的** | 想"运行时动态加一个任务"做不到 | `tasks_list[]` 是 `static` 数组 |
| **6** | **没有栈隔离** | 一个任务栈溢出 → **踩坏别人的变量**，且**没有任何检查** | 所有任务共用一个主栈 |

**★ 这 6 条，恰好就是 RTOS 提供的 6 样东西**：

| 裸机的局限 | FreeRTOS 的答案 | 出处 |
| --- | --- | --- |
| 不能抢占 | **抢占式调度**（`configUSE_PREEMPTION = 1`） | 34 |
| 没有优先级 | `xTaskCreate` 的 `uxPriority` | 34 |
| 长任务拖全表 | **每个任务独立栈 + 时间片轮转**（同优先级） | 34 |
| 没有同步 | **信号量 / 互斥量 / 队列** | **35** |
| 表固定 | `xTaskCreate` 运行时创建 | 34 |
| 无栈隔离 | 每任务独立栈 + （可选）溢出检查 | 34 |

> **所以"为什么要上 RTOS"的答案不是"RTOS 更高级"，而是"这 6 条局限在项目变大后一定会撞上"。**
> 本工程撞上的顺序是：
>
> ```
> 10-16  自己写任务表（33 篇）        ← 解决"主循环太长"
> 10-19  移植 FreeRTOS（34 篇）       ← 解决"没有优先级/抢占"
> 10-20~21  一堆同步机制测试（35 篇） ← 解决"没有互斥量"
> ```
>
> **这三步的顺序非常典型**：**先自己造轮子理解问题，再用现成的轮子。**

## 六、四代调度方式对照

把本工程走过的四代调度放在一张表里（**这张表是本篇的"地图"**）：

| | **① 主循环 + delay** | **② 主循环 + 时间戳** | **③ 任务表（本篇）** | **④ FreeRTOS（34/35）** |
| --- | --- | --- | --- | --- |
| 代表 | `05` 之前的流水灯 | `05` 状态机、`28` ADKEY | `taskmanager.c` | `app_task` + 各任务 |
| 时间粒度 | 无（delay 多长就多长） | µs（`get_us_cnt()`） | **1 ms**（SysTick） | **1 ms**（tick） |
| 谁决定"下一个跑谁" | 代码顺序 | 代码顺序 | **任务表的顺序 + 相位** | **调度器（优先级）** |
| 能抢占吗 | —— | ❌ | ❌ | ✅ |
| 有优先级吗 | ❌ | ❌ | ❌ | ✅ |
| 同步机制 | 无 | 无 | 无 | **信号量/互斥量/队列** |
| 加一个任务要改哪 | 主循环 + 顺序 | 主循环 + 顺序 | **任务表加一行** | **`xTaskCreate` 一行** |
| 代码量 | 几行 | 几十行 | **48 行** | 内核 ~10 万行（但只需理解 5 个 API） |
| 适合什么规模 | 1~2 个功能 | 3~4 个功能 | **5~10 个功能** | **10 个以上 / 有实时性要求** |

> **一句话总结这条演进线**：
> **从"我按顺序做"→"我按时间做"→"我按表做"→"调度器替我按优先级做"。**
> **每一代都在把"决定权"从"人"移交给"机制"。**

### 7.1 参数速查

| 项目 | 值 | 出处 |
| --- | --- | --- |
| 调度节拍 | **1 ms**（`SysTick` 1 MHz ÷ 1000） | `gd32f4xx_it.c` |

| `task_schedule()` 调用点 | 主循环 / `app_task`（RTOS 下） | `main.c` |
| `period` 单位 | **节拍（1 tick = 1 ms）** | `taskmanager.h` |
| 任务数 | **6**（+1 个被注释的 NTC） | `tasks_list[]` |
| 最快周期 | **10 ms**（触摸/数码管/点阵） | 同上 |

| `tasks_len` | `sizeof(tasks_list)/sizeof(tasks_list[0])` ✅ 不是硬编码 | `.c` |

### 7.2 排查清单

| # | 现象 | 最可能的原因 | 怎么查 |
| --- | --- | --- | --- |
| **1** | **所有任务都不跑** | `task_switch()` 没被调（`SysTick_Handler` 里漏了） | 在 `task_switch()` 里加个计数器，串口打印看是否在涨 |
| **2** | **所有任务都不跑** | `task_schedule()` 没被调（主循环里漏了） | 同上 |
| **3** | **某个任务永远不跑** | 它的 `cnt` 被减成了 `0xFFFFFFFF`（早期版本没有 `cnt == 0 continue` 的保护） | 检查 `cnt` 的值；本工程已有保护 ✅ |
| **4** | **某个任务的频率不对** | `period` 写的是"毫秒"但实际是"节拍" | 检查 SysTick 是否真是 1 ms 一次 |
| **5** | **任务频率整体变慢** | 主循环一圈超过 1 ms → 有节拍被"跳过"（倒计时法会补，但整体延后） | 在主循环里翻转一个 GPIO，用示波器看周期 |
| **6** | **偶尔卡一下（周期性）** | 多个任务在同一 tick 到点（10/20/100/1000 的公约数时刻） | 错开 `cnt` 初值；或把长任务搬走 |
| **7** | **OLED 刷新很慢** | `app_show_iic_oled_task` 要 38 ms，占了 38 个 tick | 降刷新率（`period` 改大）或换 SPI 屏 |
| **8** | **加了新任务但不生效** | 忘了加进 `tasks_list[]`（**只写了函数，没注册**） | `grep` 函数名是否出现在 `tasks_list` 里 |
| **9** | **任务里改的全局变量别处读不到** | 缺 `volatile`（如果变量被中断改） | 同第 06/31 篇 |
| **10** | **矩阵键盘一直没反应** | `app_input_keypad_task()` **实现了但没注册**（§5 表下注） | 看 `tasks_list[]`；本工程是**故意不注册**（与 188 数码管抢引脚，第 10/26 篇） |

## 八、自测题 + 练习题

### 8.1 自测题

1. 裸机多任务的三要素是什么？本工程分别对应哪段代码？
2. `TASK` 结构体里 `period` 和 `cnt` 的区别是什么？为什么 `period` 的单位是"节拍"？
3. `task_switch()` 里 `if (cnt == 0) continue;` 去掉会发生什么？
4. **为什么"倒计时"比"`count % period == 0`"可靠？** 举一个"主循环慢了 3 ms"的例子说明。
5. 任务表里 `cnt` 初值为什么不是全 0？错开相位能彻底解决"多任务同拍"吗？为什么？
6. `task_schedule()` 为什么"先执行 func、后重置 cnt"？反过来行不行？
7. 为什么 `App/` 层要分 input / show / test 三块？这个划分对后来移植 RTOS 有什么帮助？
8. `app.h` 把所有 bsp 头都 include 进来，有什么好处和坏处？
9. `bmp.h` → `bmp.c` 的搬迁解决了什么问题？（提示：头文件里定义数组）
10. 列出这个框架的 6 条局限，并说明 FreeRTOS 分别用什么机制解决。
11. `app_input_keypad_task()` 有实现但没注册 —— 这是 bug 还是设计？为什么？
12. 为什么"先函数化（33 篇）再任务化（34 篇）"比"直接在 main.c 上改 RTOS"更好？

### 8.2 练习题

1. **加一个任务**：把被注释的 `app_show_ntc_task`（串口打印温度）注册成 500 ms 周期，观察它是否拖慢其他任务（打印约 2 ms）。
2. **测抖动**：在某个任务里翻转一个空闲 GPIO，用示波器测实际周期，和 `period × 1 ms` 比较，算出抖动范围。
3. **故意卡住**：在 `app_show_iic_oled_task` 里加 `delay_1ms(200)`，观察其他任务的表现——**这就是"不能抢占"的直接体验**。
4. **改成取模法**：把 `task_switch`/`task_schedule` 改成教材的 `if (count % period == 0)`，然后人为让主循环慢一拍，观察"漏拍"现象。
5. **加优先级**：给 `TASK` 加一个 `priority` 字段，让 `task_schedule()` 按优先级排序执行——**你会发现"这只是把顺序换了一下，还是不能抢占"**，从而真正理解抢占需要什么（上下文切换 + 栈）。
6. **拆头文件**：把 `app.h` 拆成 `app_input.h` / `app_show.h` / `app_test.h`，改完编译，看哪些文件的重编次数减少了。
7. **横向对照**：把本篇的 `TASK` 结构体和 FreeRTOS 的 `TCB_t`（`tasks.c` 里）对比，找出"一个裸机任务"缺了哪些字段（栈指针、优先级、状态链表……）。
