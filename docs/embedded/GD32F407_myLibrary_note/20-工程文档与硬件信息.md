## 一、为什么给文档单独开一篇

前面 19 篇讲的全是"怎么驱动外设"。这一篇讲的是另一个维度：**你怎么知道该驱动什么、接在哪个脚上**。

嵌入式开发里有类问题特别费时间：

```
现象：代码逻辑看着对，编译通过，烧进去就是不工作
原因：引脚不对 / 冲突 / 悬空 / 极性反了
排查：翻原理图 → 翻 PCB → 手工对一遍 → 才发现问题
```

**这类问题的成本几乎全在"查资料"上**，而不是"改代码"上。所以：

> **把硬件信息整理成"可检索的文本"，是这个工程做的一件很聪明的事。**

它相当于给项目加了一份**"硬件 API 文档"**——写驱动前先查一遍，能省掉大量试错。

## 二、`e2d7adf`：文档是怎么生成的

**提交信息**：`[文档]: 使用jlceda-mcp查看原理图与pcb生成的文档`（+862 行，两个 md 文件）

**生成方式**：工具通过 **嘉立创 EDA（JLCEDA）的接口**读取工程文件，把**原理图 + PCB 网表**转成 Markdown 文档。

**读取优先级（文档里写得很清楚）**：

```
① PCB 焊盘级网表（pcb_PrimitiveComponent.pads.net）  ← 权威
② 用原理图的 pinName 做第二次确认
③ 原理图 sch_Net.* 在本环境返回空、getNetlist() 超时，且**原理图与 PCB 网络名不同步**
⇒ 结论：以 PCB 为准
```

**这份文档在"可信度"上的自我标注很值得学**：

| 做法 | 说明 |
| --- | --- |
| **标明数据来源** | "所有引脚结论均来自 PCB 焊盘级网表" |
| **标明局限** | "原理图与 PCB 不同步，建议以 PCB 为准" |
| **标明推断与实测的区别** | "LED 极性的判断是基于驱动拓扑推导的……如需 100% 断言，可用万用表在实物上验一次" |
| **标明没做什么** | "只读取了数据、切换了活动文档，**没有修改任何原理图/PCB**" |

> **这是"技术文档该有的样子"**：**结论 + 依据 + 局限 + 待验证项**。
> 反例就是本书里反复提到的那些"注释与代码不符"（第 07 篇软 PWM、第 15 篇 I2C 延时）——**没有标依据和局限的结论，时间一长就没人敢信**。

## 四、三个真实的冲突（本篇核心）

`Doc/引脚检查测试.md` 里发现了 3 个 **P（Problem）**，每一个都值得记住。

### 4.1 🔴 P1：`PB10` 被代码当 `USART2_TX`，硬件上是 **LCD 背光**

**代码侧**（`Hardware/msp_uart/msp_uart.c`）：

```c
USART_HandleTypeDef husart2 = {
    .usartx_tx_rcu  = RCU_GPIOB,
    .usartx_tx_port = GPIOB,
    .usartx_tx_pin  = GPIO_PIN_10,       // ← PB10
    .usartx_tx_af   = GPIO_AF_7,
    ...
};
```

**硬件侧**：

```
PCB：U9.23 (=PB10) → net LCD_BLK → CN20.7 + U10.7   （LCD 排线的背光脚）
```

**后果**（这条推理很值得学）：

```
msp_uart_init() 一执行 → PB10 被配成 AF7 推挽输出
                      → 串口空闲电平是"高"
                      → 这个"高"会持续驱动 LCD 背光网络
⇒ 背光常亮 / 常灭，甚至被串口数据"闪灯"
```

**为什么第 04 篇看不出问题？** 因为**串口本身工作正常**（USART2 的 TX 确实从 PB10 出去了）——**问题不在"串口通不通"，而在"这个引脚还被别人用着"。**

**处理建议（文档给了现实主义的答案）**：

```
先看 GD32F407 的复用表：USART2_TX 只能落在 PA2 / PD5 / PB10 / PC10 等**固定复用脚**上
⇒ 不能"随便挪到哪个空闲脚"（这一点文档特意提醒了，很专业）
⇒ 最现实的方案：① 改硬件（把 LCD_BLK 换到别的脚）② 干脆不用 USART2（板载 USB-TTL 走的是 USART0/PA9/PA10）
```

> **⚠️ 一个可以延伸思考的点**：文档在"最小修改清单"里先写了个示例（把 TX 挪到 PD3），**紧接着自己指出这是错的**（PD3 没有 USART2_TX 复用）。**这个"先给方案、再自我否决"的过程，比一个"完美的结论"更有教学价值**——它演示了"提方案时必须回来查表验证"。

### 4.2 🔴 P2：`PC3` 同时是 `KEY4` 和 `EXTI3`

**代码侧**（两处都用了 PC3）：

```c
// Hardware/msp_exti/msp_exti.h
#define USE_EXTI3 1
#define EXTI3_PORT GPIOC
#define EXTI3_PIN  GPIO_PIN_3

// Driver/bsp_keys/bsp_keys.c
{RCU_GPIOC, GPIOC, GPIO_PIN_3}, // KEY4
```

**硬件侧**：`U9.57 (=PC3) → KEY4 → SW20 → R14 → GND`——**只有一个物理按键**。

**后果**：

```
msp_exti_init() 先把 PC3 配成输入（带 EXTI3 线）
bsp_keys_config() 又把它配成输入（EXTI 线由 SYSCFG 决定，不会被关掉）
⇒ 按 KEY4 会**同时**产生 EXTI3 中断 和 key 事件（第 03 篇的轮询也会扫到）
⇒ 同一个按键被两套机制处理 → 业务逻辑可能执行两次
```

> **回顾第 06 篇**：那里讲 `EXTI0`（PA0）和 `EXTI3`（PC3）的配置时，从没提"PC3 同时也是 KEY4"。**这就是"只看代码"和"对着硬件看代码"的差别**——代码里两处都自洽，冲突只在硬件层面显现。

**处理建议**：如果 KEY4 兼任唤醒/中断键，**这是有意设计，应该补注释**；否则关掉 `USE_EXTI3`。

> **"要么改代码，要么写注释澄清"**——**这是一个很好的工程习惯**：冲突本身不一定要消除，但**必须有人知道它存在**。

### 4.3 🔴 P3：`EXTI0` 用的 `PA0` 在板上没有任何上下拉

**代码侧**：

```c
#define EXTI0_PUPD      GPIO_PUPD_NONE     // ← 无上下拉
#define EXTI0_TRIG_TYPE EXTI_TRIG_BOTH     // ← 双边沿
```

**硬件侧**：PA0 只引到 P3.3 排针，**悬空**。

**后果**：

```
浮空输入 + 双边沿触发
⇒ 引脚电平不确定、极易被干扰
⇒ 产生大量伪中断（第 06 篇中断服务函数里的 printf 会被疯狂触发）
```

**处理建议**：改成 `GPIO_PUPD_PULLUP`（或 PULLDOWN），并把触发改成单边沿；或确认排针确实接了外部信号。

> **这一条正好和第 03 篇的按键对照**：那里 PC0~PC3 用了 `GPIO_PUPD_PULLUP`（因为确认接 GND），而 PA0 用的是 `GPIO_PUPD_NONE`（注释写"外部接了下拉"）——**但硬件核对显示 PA0 并没有外部下拉**。**注释里的假设是错的，而代码跟着这个错误假设走。**
> **教训**：**注释里的"外部已经接了下拉"这类断言，必须对着原理图核实**（第 01 篇讲过"注释可能是错的"，这是又一个实例）。

这是一次"练习性质"的提交，做了两件事。

### 7.1 `bsp_leds_flow()`：非阻塞流水灯

```c
static uint8_t flag = 0;

void bsp_leds_flow()
{
    if (flag > 0) bsp_leds_open(LED2); else bsp_leds_close(LED2);
    if (flag > 1) bsp_leds_open(LED4); else bsp_leds_close(LED4);
    if (flag > 2) bsp_leds_open(LED6); else bsp_leds_close(LED6);
    if (flag > 3) bsp_leds_open(LED8); else bsp_leds_close(LED8);

    flag++;
    if (flag > 4)
        flag = 0;
}
```

**注意三点**：

| 点 | 说明 |
| --- | --- |
| **只控制 LED2/4/6/8**（偶数灯） | 和 LED1/3/5/7 交替点亮，只剩一半灯在流水——**这是"隔一个亮一个"的效果**，也可能只是想少写几个 `if` |
| **没有延时** | 它是个"状态推进函数"，**调用一次推进一格**——和 `bsp_battery_flows` 的 `process()` 是同一个套路（第 05 篇） |
| **状态变量是 `static`** | 只在函数内部可见，外部改不了（第 06 篇 EXTI 的 `pre_sta` 也是这个思路） |

**调用方负责节拍**（`practice` 分支的 `main.c`）：

```c
uint64_t now = get_us_cnt();
uint64_t last_time = now;
while (1)
{
    now = get_us_cnt();
    if (now - last_time >= 1000000)     // 每 1 秒推进一格
    {
        bsp_leds_flow();
        last_time = now;
    }
}
```

**这是本工程"非阻塞定时"的标准写法**（`get_us_cnt()` 时间戳 + 无符号减法），和第 09 篇数码管扫描、第 01 篇 SysTick 一脉相承。

> **和第 05 篇的对照**：第 05 篇的流水灯用"主循环 20 ms × 25 = 500 ms"的计数法，这里用"时间戳差 ≥ 1000000 μs"的差值法。**差值法更好**——不依赖主循环周期，主循环里插入别的耗时任务也不会改变节拍。

### 7.2 `bsp_vibration_motor`：用 PWM 驱动振动马达

```c
// bsp_vibration_motor.c
// AF3 TIMER9 CH0
static void GPIO_config(void)
{
    rcu_periph_clock_enable(RCU_GPIOB);
    gpio_mode_set(GPIOB, GPIO_MODE_AF, GPIO_PUPD_NONE, GPIO_PIN_8);   // PB8
    gpio_af_set(GPIOB, GPIO_AF_3, GPIO_PIN_8);                        // AF3
}

#define PRESCALER (168 - 1)          // → 1 MHz（1 μs/tick）

static void TIMER9_config(void)
{
    rcu_periph_clock_enable(RCU_TIMER9);

    timer_parameter_struct timer_init_struct;
    timer_struct_para_init(&timer_init_struct);
    timer_init_struct.prescaler = PRESCALER;
    timer_init_struct.period = 0;                    // ← 先给 0，占空比由 set_duty 决定
    timer_init(TIMER9, &timer_init_struct);

    timer_oc_parameter_struct ocpara;
    timer_channel_output_struct_para_init(&ocpara);
    ocpara.outputstate = (uint16_t)TIMER_CCX_ENABLE;
    ocpara.ocpolarity = TIMER_OC_POLARITY_HIGH;
    ocpara.ocidlestate = TIMER_OC_IDLE_STATE_LOW;
    timer_channel_output_config(TIMER9, TIMER_CH_0, &ocpara);
    timer_channel_output_mode_config(TIMER9, TIMER_CH_0, TIMER_OC_MODE_PWM0);
    timer_channel_output_pulse_value_config(TIMER1, TIMER_CH_0, 0);   // ⚠️ 写的是 TIMER1！
    timer_enable(TIMER1);                                             // ⚠️ 写的是 TIMER1！
}

void bsp_vibration_motor_init(void)  { GPIO_config(); TIMER9_config(); }
void bsp_vibration_motor_set_duty(uint16_t duty) { timer_channel_output_pulse_value_config(TIMER9, TIMER_CH_0, duty); }
```

**⚠️ 这里有一个真实的复制粘贴 bug**：

```c
timer_channel_output_pulse_value_config(TIMER1, TIMER_CH_0, 0);   // 应该是 TIMER9
timer_enable(TIMER1);                                             // 应该是 TIMER9
```

**后果分析**（这个推理过程值得自己走一遍）：

| 代码 | 实际效果 |
| --- | --- |
| `timer_enable(TIMER1)` | **使能的是 TIMER1**，而 TIMER9 从来没被使能 → **TIMER9 不输出任何波形** |
| `timer_channel_output_pulse_value_config(TIMER1, TIMER_CH_0, 0)` | 改的是 TIMER1 的通道 0 比较值（TIMER1 在本工程里被蜂鸣器用着 CH1，所以 CH0 是空闲的）→ 属于"改错了对象但没造成可见破坏" |
| 但后面的 `bsp_vibration_motor_set_duty()` 用的是 **TIMER9** | 所以"设占空比"改的是 TIMER9，**而 TIMER9 根本没使能** → 马达不会转 |

**结论**：**马达根本不会转**（TIMER9 未被使能）。

> **这类 bug 的通用特征**：**复制改漏了"定时器名"**。定时器配置代码有 6~7 行，每行都带定时器名，**漏改一两个不会编译报错**（TIMER1 是合法标识符），只会"没反应"。
> **这就是第 07 篇反复强调的那个坑**："引脚 / 通道 / AF / 定时器号 要成套核对"——**这次漏的是"定时器号"**。
> **防呆办法**：把定时器**做成参数**（像第 04 篇串口句柄那样），一套参数只写错一次；或者干脆**用 `#define`/宏把 `TIMER9` 抽出来**，只在一个地方写。

**这个 bug 还给我们一个提醒**：**这是 `practice` 分支（未合并）**——**未合并的分支里可能藏着这类未修的问题**。回顾第 10 篇的 `digital_led` 分支也有下标不一致的问题。**合并前必须重新过一遍代码**，不能默认"分支上的代码是验过的"。

### 14.3 ⚠️ 新增的第四个引脚冲突：188 数码管 × 矩阵键盘

`硬件信息汇总.md` 的"速查：三个必须处理的问题"（P1/P2/P3）是在 `e2d7adf` 时写的。

| --- | --- | --- | --- |
| `bsp_188_leds`（第 26 篇） | `PE15` `PE13` `PE11` `PE9` `PE7` | `KCOL_4` / `KCOL_2` / `KROW_4` / `KROW_2` / 空闲 | ★ **前 4 个与 20 键矩阵键盘（`SW1~SW16`）共用同一批网络** |

**后果**（详见第 26 篇 §7）：188 扫描与矩阵键盘扫描**不能同时进行**；而且**按键被按下的那一瞬间物理上就是短接**，

**这件事说明"代码↔硬件核对"不是一次性动作**：文档写完的那一刻是对的，

（另一个例子：`bsp_ntc` 用 **PA1**、`msp_adc` 也用 **PA1**——但这两个不冲突，因为 NTC 就是那颗接到 PA1 的器件。**"同一个引脚出现在两个模块里"必须先分清是"冲突"还是"同一条链路"。**）

> **这是"文档时效性"的又一个例子**（和 §15.3 的"文档缺口"是一对）：
> **写了但没同步 = 比没写更危险**，因为读者会**相信**它。
> 缓解办法只有一条：**改代码时顺手改 README**（或者把 README 里易变的部分（任务表）改成"自动生成"的）。

### 16.3 ★ 一个"正面案例"：`PA8` 是第一个"选对了"的引脚

前面 P1~P9 全是冲突（PB10 抢背光、PB8 抢马达、PB13 抢 CAN_TX、PB0 抢 LCD_CS…）。
**点阵屏（第 32 篇）第一次做到了"先查文档再选脚"**：

代码：
#define GPIO_MAX7219_CS GPIO_PIN_8   // ← 选了一个"确定空闲"的脚 ✅
