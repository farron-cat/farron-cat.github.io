## 知识点地图

```
数码管（74HC595 动态扫描）
├── 硬件              两片 74HC595 级联；SER=PD0 / RCLK=PD1 / SRCLK=PD4；8 位共阳数码管
├── 74HC595           移位寄存器（8 位串入）+ 锁存寄存器（并出）
├── 三条控制线        数据 SER、移位时钟 SRCLK（上升沿移入）、锁存时钟 RCLK（上升沿输出）
├── 段码（字型码）     点亮哪些段 → SEG_0~SEG_9 / SEG_A~SEG_H 等；共阳时 0=亮
├── 位码（位选码）     点亮哪一位 → DIG_1~DIG_8（独热码）
├── 级联顺序          先发段码、后发位码（先发的会被挤到第二片）
├── 动态扫描           一次只亮一位，靠人眼视觉暂留「看起来都亮」
├── 显示缓冲区         displayBuffer[8]，业务写缓冲、扫描读缓冲（关注点分离）
├── 非阻塞扫描         get_us_cnt() 时间戳，1 ms 刷新一位 → 一帧 8 ms ≈ 125 Hz
└── 测试工具           is_1s() / show_number() / test_tick()
```

## 一、需求与硬件

### 1.1 要做什么

在扩展板上显示数字（先做 0~9999 的计数测试）。硬件是**8 位共阳数码管**，但**不是**8 个独立器件——它是通过两片 74HC595 驱动的。

### 1.2 为什么需要 74HC595

要显示 8 位数字，每位数码管有 8 段（7 段 + 小数点），也就是 **8 × 8 = 64 个 LED**。如果每段一根线，需要 64 个引脚——显然不现实。

**74HC595 是「串行输入、并行输出」的移位寄存器**：你用 3 根线串行送 8 位数据，它就并行输出 8 位。两片级联 = 控制 16 位输出。

```
单片机只出 3 根线：
    PD0  ──→ SER    （数据）
    PD1  ──→ RCLK   （锁存时钟）
    PD4  ──→ SRCLK  （移位时钟）
                    │
                    ▼
              ┌──────────┐   ┌──────────┐
         ────→│  595 #1  │──→│  595 #2  │
              │ 8 位输出 │   │ 8 位输出 │
              └────┬─────┘   └────┬─────┘
                   │              │
                位码（选哪一位）  段码（显示什么字型）
```

**关键点：两片 595 分别负责「选位」和「选段」**，这就是动态扫描能省引脚的根本原因——**一次只亮一位**。

| 项目 | 值 | 说明 |
| --- | --- | --- |
| 数据线 SER | **PD0** | 一位一位送数据 |
| 锁存时钟 RCLK | **PD1** | 上升沿 → 把移位寄存器的内容输出到引脚 |
| 移位时钟 SRCLK | **PD4** | 上升沿 → 把 SER 上的数据移进寄存器 |
| 位数 | 8 位（`DIG_NUM`） | 两片 595 各 8 位，共 16 位 |
| 数码管类型 | **共阳** | **段码 0 = 亮**（和 LED 一样是「反的」） |

### 1.3 74HC595 的两级结构

595 内部有两个寄存器，理解这两个是理解整个驱动的钥匙：

```
      SER ──┐
            ▼
    ┌───────────────┐   移位时钟 SRCLK 上升沿
    │  移位寄存器    │←── 一位一位往里挤，最先进入的会被挤到最后
    │   （8 位）     │
    └───────┬───────┘
            │  锁存时钟 RCLK 上升沿：一次性「拍照」搬过去
            ▼
    ┌───────────────┐
    │  锁存寄存器    │──→ 8 个输出引脚（Q0~Q7）
    │   （8 位）     │
    └───────────────┘
```

| 阶段 | 什么时候发生 | 效果 |
| --- | --- | --- |
| **移位** | 每来一个 SRCLK 上升沿 | 数据进入移位寄存器，**引脚输出不变**（所以移位过程中不会花屏） |
| **锁存** | 来一个 RCLK 上升沿 | 移位寄存器的内容**一次性**搬到输出引脚 |

> **这就是为什么可以「移完 16 位再锁存」**：移位过程中输出保持旧值不变，等全部数据到位了，一个锁存脉冲让所有引脚同时更新——**避免看到「中间状态」的闪烁**。

## 二、两个核心概念：段码与位码

### 2.1 位码：选哪一位（独热码）

位码就是「8 位里选 1 位」，所以是一个**只有一个 bit 为 1** 的值（独热码）：

```c
#define DIG_1      0x01
#define DIG_2      0x02
#define DIG_3      0x04
#define DIG_4      0x08
#define DIG_5      0x10
#define DIG_6      0x20
#define DIG_7      0x40
#define DIG_8      0x80
```

注意 **`DIG_1` 是 `0x01`**（第 0 位），`DIG_8` 是 `0x80`（第 7 位）——**编号从 1 开始，但位从 0 开始**，这是数码管驱动里最容易搞错的映射关系。

驱动里用一张表把它变成「数组下标 → 位码」：

```c
#define DIG_NUM 8
unsigned char displayBuffer[DIG_NUM];
const unsigned char digCodeTable[DIG_NUM] =
    {
        DIG_1, /* position 0 → 第 1 位 */
        DIG_2, /* position 1 → 第 2 位 */
        DIG_3, /* position 2 → 第 3 位 */
        DIG_4, /* position 3 → 第 4 位 */
        DIG_5, /* position 4 → 第 5 位 */
        DIG_6, /* position 5 → 第 6 位 */
        DIG_7, /* position 6 → 第 7 位 */
        DIG_8, /* position 7 → 第 8 位 */
    };
```

**下标 0~7 是软件概念，位码 `0x01~0x80` 是硬件概念**，这张表就是两者的翻译。

### 2.2 段码：显示什么字型

每一位数码管的 8 段（a~g + dp）对应段码的 8 个 bit。**共阳数码管：位为 0 时那一段亮**。

```c
#define SEG_CLR 0xFF        // 全灭
#define SEG_0   0xC0
#define SEG_1   0xF9
#define SEG_2   0xA4
#define SEG_3   0xB0
#define SEG_4   0x99
#define SEG_5   0x92
#define SEG_6   0x82
#define SEG_7   0xF8
#define SEG_8   0x80
#define SEG_9   0x90
```

**验算一下 `SEG_0 = 0xC0`**：

```
0xC0 = 0b 1100 0000
       │││││││└─ a 段  0 → 亮
       ││││││└── b 段  0 → 亮
       │││││└─── c 段  0 → 亮
       ││││└──── d 段  0 → 亮
       │││└───── e 段  0 → 亮
       ││└────── f 段  0 → 亮
       │└─────── g 段  1 → 灭      （中间那一横不亮）
       └──────── dp   1 → 灭

a~f 全亮、g 和 dp 灭 → 显示 「0」  ✅
```

**再看 `SEG_1 = 0xF9`**：

```
0xF9 = 0b 1111 1001
              └─ b、c 两段为 0 → 亮

只有右半边两段亮 → 显示 「1」  ✅
```

**除了数字，头文件还准备了字母段码**：

```c
#define SEG_A   0x88
#define SEG_B   0x83
#define SEG_C   0xC6
...
#define SEG_R   0xCE
#define SEG_S   0x92
#define SEG_O   0x8C
#define SEG_N   0xAB
#define SEG_L   0xC7
#define SEG_H   0x89
#define SEG_G   0x82
```

**连起来能拼单词**：`SEG_R` `SEG_S` `SEG_O` `SEG_N` `SEG_L` `SEG_H` `SEG_G` —— `RSONLH G`？其实这些字母是**给「显示状态字」用的**（比如 `ON` / `Err` / `SEG` 之类），说明作者当时就想好了「不止显示数字」。**预留字母段码不是过度设计，8 位显示里显示一两个字母是很常见的需求**。

**还有一组「边缘段码」**：

```c
// 边缘段码（共阳，0=亮）
#define SEG_EDGE_A 0xFE // 上边
#define SEG_EDGE_B 0xFD // 右上
#define SEG_EDGE_C 0xFB // 右下
#define SEG_EDGE_D 0xF7 // 下边
#define SEG_EDGE_E 0xEF // 左下
#define SEG_EDGE_F 0xDF // 左上
```

**看出来了吗**：`SEG_EDGE_A` 就是「只点亮 a 段」，`SEG_EDGE_B` 就是「只点亮 b 段」。这组常用于**跑马灯式动画**（8 位数码管上跑一圈边框）。

### 2.3 段码 / 位码对照总结

| | 段码 | 位码 |
| --- | --- | --- |
| 决定 | 这一位**显示什么** | **哪一位**被点亮 |
| 谁提供 | 段码表（SEG_x） | 位码表（digCodeTable） |
| 送进哪片 595 | 后送 → 留在第一片 | 先送 → 被挤到第二片（见 4.3） |
| 在缓冲区里的表示 | `displayBuffer[i]` 的内容 | 数组下标 `i` |

## 三、提交 `69cc768`：封装驱动

**提交信息**：`[更新] 数码管 封装`（新建 `Driver/bsp_digital_leds/`，`.eide/eide.yml` 加路径）

### 3.1 初始化：三个引脚，一次配好

```c
void bsp_digital_leds_init(void)
{
    rcu_periph_clock_enable(DIGLED_RCU);
    gpio_mode_set(DIGLED_PORT, GPIO_MODE_OUTPUT, GPIO_PUPD_NONE, SER_PIN | RCLK_PIN | SRCLK_PIN);
    gpio_output_options_set(DIGLED_PORT, GPIO_OTYPE_PP, GPIO_OSPEED_2MHZ, SER_PIN | RCLK_PIN | SRCLK_PIN);

    SER_L();
    RCLK_L();
    SRCLK_L();
}
```

| 点 | 说明 |
| --- | --- |
| 三个引脚都在 **GPIOD**（PD0 / PD1 / PD4） | 所以可以一次配完，`GPIO_PIN_0 \| GPIO_PIN_1 \| GPIO_PIN_4` |
| `GPIO_OSPEED_2MHZ` | 595 是慢速器件，2 MHz 足够，且 EMI 更小 |
| **初始化后三根线都拉低** | 让 595 处于确定的初始状态，避免上电乱闪 |

**用宏封装引脚操作**（这是本模块的一个亮点）：

```c
#define DIGLED_PORT GPIOD
#define DIGLED_RCU RCU_GPIOD

#define SER_PIN GPIO_PIN_0
#define RCLK_PIN GPIO_PIN_1
#define SRCLK_PIN GPIO_PIN_4

/* 便捷操作宏 */
#define SER_H() gpio_bit_set(DIGLED_PORT, SER_PIN)
#define SER_L() gpio_bit_reset(DIGLED_PORT, SER_PIN)
#define RCLK_H() gpio_bit_set(DIGLED_PORT, RCLK_PIN)
#define RCLK_L() gpio_bit_reset(DIGLED_PORT, RCLK_PIN)
#define SRCLK_H() gpio_bit_set(DIGLED_PORT, SRCLK_PIN)
#define SRCLK_L() gpio_bit_reset(DIGLED_PORT, SRCLK_PIN)
```

**6 个宏换来什么？** 看下面的代码就有感觉了——**时序逻辑一眼可读**，而且想换引脚只改最上面的 `_PIN` 定义。

### 3.2 移位：一位一位挤进去

```c
void bsp_digital_leds_send_byte(uint8_t dat)
{
    uint8_t i;

    for (i = 0; i < 8; i++)
    {
        /* 先发送 bit7，再 bit6 ... 最后 bit0 */
        if ((dat >> (7 - i)) & 0x01)
        {
            SER_H();
        }
        else
        {
            SER_L();
        }

        /* 产生移位时钟上升沿，数据被移入 */
        SRCLK_L();
        SRCLK_H(); /* 上升沿移入 */
    }
}
```

**时序拆解**（这是「写时序」的标准姿势）：

```
每个 bit：
  ① 准备数据     SER = 0 或 1                    ← 先把数据摆好
  ② 时钟拉低     SRCLK_L()                       ← 先归零，保证下一步是「上升沿」
  ③ 时钟拉高     SRCLK_H()                       ← 上升沿！595 在这个沿采样 SER 上的数据
```

| 细节 | 为什么 |
| --- | --- |
| **`dat >> (7 - i)`，从 bit7 开始发** | 因为 595 是「先进后出」——**最先发进去的位最终跑到最远的输出**。要让它和输出引脚顺序对齐，就必须高位先发 |
| **先 `SRCLK_L()` 再 `SRCLK_H()`** | 确保一定是「上升沿」。如果 595 上次结束时 SRCLK 已经是高，直接 `SRCLK_H()` 不会产生沿，数据就丢了 |
| 用 `if/else` 而不是直接 `SER = bit` | 因为宏只能整体赋值（没有「写一个 bit」的库函数），所以用分支 |

**「先发高位」还是「先发低位」这件事，必须和硬件接线对齐**，接反了的现象是「显示的字型完全对不上」（比如要显示 0 却显示成别的东西）。

### 3.3 发送一组（段码 + 位码）并锁存

```c
void bsp_digital_leds_send_code(unsigned char segCode, unsigned char digCode)
{
    /* 段码：先发，移完 8 位后会落到第二片 595 */
    bsp_digital_leds_send_byte(segCode);

    /* 位码：后发，移完 8 位后留在第一片 595 */
    bsp_digital_leds_send_byte(digCode);

    /* 所有位移完后，产生锁存脉冲 */
    RCLK_L();
    RCLK_H();
}
```

**「先发段码」的顺序推理**（这是级联 595 的核心理解点）：

```
假设要送 段码=0xC0, 位码=0x01

第 1 步：送 8 位段码
    595#1 的移位寄存器：[0xC0]        595#2 移位寄存器：[空]
    接着继续送位码时，段码会被「挤」出去：

第 2 步：送 8 位位码
    595#1 的移位寄存器：[0x01]        595#2 移位寄存器：[0xC0]
    ↑ 位码在第一片                     ↑ 段码被挤到第二片

第 3 步：RCLK 上升沿，两片同时锁存
    595#1 输出 0x01  → 选中第 1 位
    595#2 输出 0xC0  → 显示字型 "0"

最终：第 1 位数码管显示 "0"  ✅
```

**「后进先出」是移位寄存器的天性**：后进去的留在最近的一级，先进的被推到更远的级。**所以级联时，「离单片机最远的器件」收到的是「最先发的数据」。**

### 3.4 显示缓冲区：业务与显示的桥梁

```c
void send_code_to_buffer(unsigned char segCode, unsigned char pos)
{
    if (pos < DIG_NUM)
    {
        displayBuffer[pos] = segCode;
    }
}

void clear_buffer(void)
{
    unsigned char i;
    for (i = 0; i < DIG_NUM; i++)
    {
        displayBuffer[i] = SEG_CLR;
    }
}
```

**`displayBuffer[8]` 是这套驱动的精髓**：

```
应用层                          驱动层
┌──────────────┐              ┌──────────────┐
│ 想显示 "1234" │──写缓冲──→  │ displayBuffer│──扫描──→ 数码管硬件
│ 卖代码只改这里│              │ [8]          │
└──────────────┘              └──────────────┘
```

| 好处 | 说明 |
| --- | --- |
| **应用层不用管扫描** | 想把第 5 位改成"8"，只写 `send_code_to_buffer(SEG_8, 5)`，**扫描逻辑自动会把它显示出来** |
| **天然支持多任务** | 主循环随时可以改缓冲区，扫描在自己的节奏里读 |
| **闪烁/动画容易做** | 改缓冲区 = 改显示内容；想闪烁就定时把某位清成 `SEG_CLR` 再写回 |
| `pos < DIG_NUM` 做了边界检查 | 防止越界写坏别的变量（**缓冲区溢出是嵌入式里最难查的 bug 之一**） |

### 3.5 动态扫描：一次亮一位

```c
/* 刷新周期：1ms / 位；8 位 → 一帧 8ms → 约 125Hz，无可见闪烁 */
#define DIG_SCAN_INTERVAL_US (1000U)

/**
 * @brief 数码管扫描，需在主循环或周期性任务中反复调用
 * @note  用 get_us_cnt() 做非阻塞定时，每次调用最多刷新一位
 * @note  调用频率越高，时间抖动越小；建议 ≥ 10kHz（即每 100us 调一次）
 */
void bsp_digital_leds_scan(void)
{
    static uint64_t last_refresh_us = 0;
    static unsigned char position = 0;

    uint64_t now = get_us_cnt();

    if (now - last_refresh_us >= DIG_SCAN_INTERVAL_US)
    {
        last_refresh_us = now;

        /* 段码 + 位码 */
        bsp_digital_leds_send_byte(displayBuffer[position]);
        bsp_digital_leds_send_byte(digCodeTable[position]);

        /* 锁存上升沿 */
        RCLK_H();
        RCLK_L();

        position = (position + 1) % DIG_NUM;
    }
}
```

**动态扫描的原理**：

```
时间 →
第 1ms：只亮第1位    第 2ms：只亮第2位    ...    第 8ms：只亮第8位    第 9ms：回到第1位
 (其他 7 位全灭)      (其他 7 位全灭)             (其他 7 位全灭)

人眼有「视觉暂留」（约 1/24 秒 = 41.7ms）：
    只要一帧时间 < 41.7ms，人眼就会把 8 次闪烁「糊」成「同时亮」
```

**本工程的参数**：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 每位刷新间隔 | 1000 μs = **1 ms** | `DIG_SCAN_INTERVAL_US` |
| 一帧 | 8 × 1 ms = **8 ms** | 一帧刷完所有 8 位 |
| 刷新率 | 1/8ms ≈ **125 Hz** | 远高于人眼临界 24 Hz → **完全看不到闪烁** ✅ |

**如果刷新间隔取太大呢？** 比如 10 ms/位 → 一帧 80 ms → 20 ms，**就会看到明显的闪烁和「拖影」**（因为人眼开始分辨出「这一刻只有这一位亮着」）。

**「非阻塞」是这次封装的关键**：

```c
static uint64_t last_refresh_us = 0;      // static：跨调用保持状态
```

| 对比 | 阻塞写法 | 本工程写法 |
| --- | --- | --- |
| 代码 | `delay_1ms(1)` 然后刷新一位 | 比较时间戳，到了才刷新 |
| 调用方 | 被强制卡在函数里 | **随时调用，没到时间立刻返回** |
| 多个任务 | 谁也干不了 | 互不影响 |

**函数注释里那句「需在主循环或周期性任务中反复调用」非常重要**：这个函数**不会自己跑**，必须有人不停地调它。而「调得越勤，时间抖动越小」——因为时间戳比较是「到了就走」，如果调用间隔本身是 20 ms，那刷新间隔就不是 1 ms 而是「至少 1 ms，实际约 20 ms」，一帧变 160 ms → **会闪**。

> **这是一个容易被忽略的耦合**：`bsp_digital_leds_scan()` 的效果**取决于调用频率**。本项目在 `main.c` 里**无延时地空转调用**（`while(1) { ... bsp_digital_leds_scan(); }`），所以实际刷新率约等于「循环一圈的耗时」——每圈远小于 1 ms，于是**真实刷新间隔就是 1 ms**，指标达成。

## 四、提交 `339dab3`：加上测试函数

**提交信息**：`[更新] 数码管测试函数：按秒计数`

这次提交给驱动加了三个工具函数（严格说「测试代码」不该放进驱动，但作为学习阶段的自测工具很方便）。

### 4.1 `is_1s()`：非阻塞的一秒节拍

```c
// 每 1 秒返回一次 1
uint8_t bsp_digital_leds_is_1s(void)
{
    static uint64_t last_cnt = 0;
    uint64_t cnt = get_us_cnt();

    if (cnt - last_cnt >= 1000000ULL) // 1,000,000 us = 1 s
    {
        last_cnt = cnt;
        return 1;
    }
    return 0;
}
```

**和 `delay_1ms(1000)` 的区别**：

| | `delay_1ms(1000)` | `is_1s()` |
| --- | --- | --- |
| 行为 | **死等 1 秒** | 立刻返回（0 或 1） |
| 期间能刷新数码管吗 | 不能 → **数码管会灭/卡住** | 能 |
| 用的是什么 | `delay` 变量 | `get_us_cnt()` 时间戳 |

**为什么这里必须用 `is_1s()`？** 因为数码管是**动态扫描**的——**只要主循环停 1 秒，8 位数码管就有 1 秒没人刷新，屏幕上只会有 1 位亮着**。这是「阻塞式延时」在显示场景下最直观的破坏。

> **800 万次机会**：`get_us_cnt()` 每 1 μs 加一，所以 `is_1s()` 每秒钟有 100 万次机会被命中检查——**精度只取决于你调用的频率**。

### 4.2 显示缓冲区操作 + 数字拆位

```c
// 共阳段码表，索引 0~9
const uint8_t seg_tab[10] =
    {
        SEG_0, SEG_1, SEG_2, SEG_3, SEG_4,
        SEG_5, SEG_6, SEG_7, SEG_8, SEG_9};

// 把 0~9999 的数字显示到 4 位数码管
void bsp_digital_leds_show_number(uint16_t num)
{
    if (num > 9999)
        num = 9999;

    send_code_to_buffer(seg_tab[(num / 1000) % 10], 4); // 千位
    send_code_to_buffer(seg_tab[(num / 100) % 10], 5);  // 百位
    send_code_to_buffer(seg_tab[(num / 10) % 10], 6);   // 十位
    send_code_to_buffer(seg_tab[num % 10], 7);          // 个位
}
```

**「拆位」的四种写法**（这是个经典小技巧）：

| 位 | 取法 | 原理 |
| --- | --- | --- |
| 千位 | `(num / 1000) % 10` | 除到千位单位，再取余 10 剥掉更高位 |
| 百位 | `(num / 100) % 10` | 同上 |
| 十位 | `(num / 10) % 10` | 同上 |
| 个位 | `num % 10` | 直接取余 |

**注意 `num` 是 `uint16_t` 而 `num / 1000` 最大只是 9**——这里的 `% 10` 是**防御性写法**（如果哪天传进来超过 9999 的值，也不会越界访问 `seg_tab`）。配合开头的 `if (num > 9999) num = 9999;`，**双重保护**。

**`seg_tab[]` 是一张「数字 → 段码」的查表**：

```
seg_tab[3] → SEG_3 → 0xB0 → 送进 595 → 显示 "3"
```

**注意这里用下标 4~7**（而不是 0~3）来显示四位数字：

```c
send_code_to_buffer(seg_tab[...], 4);  // 千位
send_code_to_buffer(seg_tab[...], 5);  // 百位
send_code_to_buffer(seg_tab[...], 6);  // 十位
send_code_to_buffer(seg_tab[...], 7);  // 个位
```

而 `main.c` 里手动写的那段用的是下标 0~3：

```c
    clear_buffer();
    send_code_to_buffer(seg_tab[0], 0); // 千位
    send_code_to_buffer(seg_tab[0], 1); // 百位
    send_code_to_buffer(seg_tab[0], 2); // 十位
    send_code_to_buffer(seg_tab[0], 3); // 个位
```

**同一个项目里两处用了不同的下标区间**——这说明「哪 4 位是有效显示位」这件事**还没有固化成常量**。应该定义个 `#define DIG_BASE 4` 之类的，或者统一成 0~3。**这是可以自己动手清理的一处不一致**。

### 4.3 组合成一个自测任务

```c
// 数码管测试：每 1 秒加 1
void bsp_digital_leds_test_tick(void)
{
    static uint16_t number = 0;

    if (bsp_digital_leds_is_1s())
    {
        number++;
        if (number > 9999)
        {
            number = 0;
        }
        bsp_digital_leds_show_number(number);
    }
}
```

**`main.c` 里的调用结构**（`digital_led` 分支）：

```c
    // 先刷新一次缓冲区，让数码管上电就显示 0000
    clear_buffer();
    send_code_to_buffer(seg_tab[0], 4); // 千位
    send_code_to_buffer(seg_tab[0], 5); // 百位
    send_code_to_buffer(seg_tab[0], 6); // 十位
    send_code_to_buffer(seg_tab[0], 7); // 个位

    while (1)
    {
        // 呼吸灯：算 CCR 改占空比（第 07 篇遗留的阻塞写法）
        uint16_t ccr = (uint16_t)(((uint32_t)(PERIOD + 1) * duty_percent) / 100);
        timer_channel_output_pulse_value_config(TIMER3, TIMER_CH_0, ccr);

        uint64_t cnt = get_us_cnt();
        if (cnt - last_cnt >= 10000)    // 10 ms 改一次占空比（已非阻塞化）
        {
            last_cnt = cnt;
            duty_percent += step;
            if (duty_percent <= 10) { duty_percent = 10; step = 1; }
            else if (duty_percent >= 100) { duty_percent = 100; step = -1; }
        }

        bsp_digital_leds_scan();        // 刷数码管
        bsp_digital_leds_test_tick();   // 每秒 +1
    }
```

**这次主循环的变化很值得注意**：第 07 篇的呼吸灯用的是 `delay_1ms(10)`（阻塞），**这次换成了 `get_us_cnt()` 时间戳比较（非阻塞）**。

> **因为阻塞式写法在这里彻底行不通了**：如果主循环里有一个 `delay_1ms(10)`，数码管扫描就会被拖慢 10 ms 一次 → 一帧 8 位要 80 ms → **数码管会明显闪烁**。
>
> **「数码管扫描」这个需求倒逼代码走向非阻塞**——这是本工程里「架构被真实需求推着进化」的又一个例子。

**`main.c` 里还有一段「上电就显示 0000」的预处理**，它解决了什么问题？**上电时缓冲区是随机值**（全局变量未显式初始化时为 0，但 `0x00` 在共阳数码管上表示「全亮」！），所以必须先 `clear_buffer()` 把 8 位全设成 `SEG_CLR (0xFF)`，再写入要显示的内容。**这一步不做，上电会看到一个「8888」之类的乱码**。

**③ 最大的变化：扫描改由 `SysTick_Handler` 每 1 ms 调用**

```c
// User/gd32f4xx_it.c（合并后）
void SysTick_Handler(void)
{
    static uint16_t div = 0;
    delay_decrement();
    if (++div >= 1000)              // 1 ms
    {
        div = 0;
        bsp_188_leds_scan();        // 188 数码管（第 26 篇）
        bsp_adkey_scan();           // AD 按键（第 28 篇）
        bsp_digital_leds_scan();    // ★ 本篇的 74HC595 数码管
    }
}
```

**⚠️ 两个"扫描节拍"叠加了**：中断已经是 **1 kHz**，而 `bsp_digital_leds_scan()` 内部**又有一道 1 ms 的时间门**：

```c
#define DIG_SCAN_INTERVAL_US (1000U)
void bsp_digital_leds_scan(void)
{
    static uint64_t last_refresh_us = 0;
    static unsigned char position = 0;
    uint64_t now = get_us_cnt();
    if (now - last_refresh_us >= DIG_SCAN_INTERVAL_US)   // ← 第二道门
    { ... 刷一位 ... }
}
```

**结果**：调用频率 1 kHz、门限 1 ms → 由于抖动，实际是"**有时 1 ms 刷一位、有时 2 ms 刷一位**"，
一帧 8 位 ≈ **8~16 ms** → 刷新率 **60~125 Hz**，**仍远高于闪烁临界（41.7 ms）**，所以看不出问题。
但**两道门只该留一道**（要么中断换成 100 µs，要么去掉函数内的门）。

**④ 注释与调用点矛盾**（值得记一笔）：

```c
/**
 * @brief 数码管扫描，需在主循环或周期性任务中反复调用
 * @note  调用频率越高，时间抖动越小；建议 ≥ 10kHz（即每 100us 调一次）
 */
```

**实际调用点是 1 kHz（每 1 ms）**，与注释里"建议 ≥10 kHz"差 10 倍。
**它恰好还能工作**（因为函数内部有 1 ms 门，1 kHz 调用已经够触发）——
但**注释写的是一个"假的建议值"**，照着改反而会变成"每 100 µs 刷一位"→ 一帧 0.8 ms → **刷新率 1.25 kHz**（闪烁倒是没有，但白占 CPU）。

**⑤ ★ `bsp_digital_leds_all_zero()` 的下标错了一个**

```c
void bsp_digital_leds_all_zero(void)          // 上电让数码管显示 "0000 0000"
{
    send_code_to_buffer(segCodeTable[0], 0);
    send_code_to_buffer(segCodeTable[0], 1);
    send_code_to_buffer(segCodeTable[0], 2);
    send_code_to_buffer(segCodeTable[0], 3);
    send_code_to_buffer(segCodeTable[0], 5);   // ★ 跳到 5 了，漏了 4！
    send_code_to_buffer(segCodeTable[0], 6);
    send_code_to_buffer(segCodeTable[0], 7);
    send_code_to_buffer(segCodeTable[0], 8);   // ★ 8 越界（被函数内的 pos < DIG_NUM 挡住，静默忽略）
}
```

| 问题 | 后果 |
| --- | --- |
| **漏了 position 4** | 第 5 位不会被清零，保持 `clear_buffer()` 给的 `0xFF`（空白）→ 只要 `main()` 里先调了 `clear_buffer()`，现象上看不出来 |
| **多写了 position 8** | **下标 8 对 `displayBuffer[8]` 是越界的**，但 `send_code_to_buffer()` 里有 `if (pos < DIG_NUM)` 守卫 → **静默忽略，不写坏内存** |
| 为什么"看起来没关系"其实很危险 | 这个函数的**语义是"把 8 位都显示 0"**，实际只写了 0~3、5~7 共 7 位。**它现在"看起来对"完全依赖调用方先 `clear_buffer()`**——这就是一种"隐式契约"（第 26 篇 §3.3 刚讲过这类问题） |

**正确写法**：

```c
void bsp_digital_leds_all_zero(void)
{
    for (uint8_t i = 0; i < DIG_NUM; i++)       // 用宏循环，不手写 8 行
        send_code_to_buffer(segCodeTable[0], i);
}
```

**⑥ 有效显示位仍然没有固化成常量（老问题复现）**

| 函数 | 用的下标 | 语义 |
| --- | --- | --- |
| `bsp_digital_leds_show_number()` | **4、5、6、7** | 千、百、十、个 |
| `bsp_digital_leds_all_zero()` | 0、1、2、3、5、6、7（+8） | "全部显示 0" |
| `bsp_digital_leds_scan()` | 0~7 循环 | 逐位扫描 |

三处对"哪些位是有效显示位"的理解**不一致**。
**第 09 篇原版就指出过这个"下标不一致"**（当时是 `main.c` 用 0~3、`show_number()` 用 4~7），
**合并之后换了个形式又出现了**。修法是把它们固化成常量：

```c
#define DIG_FIRST   4
#define DIG_COUNT   4          // 只用 4~7 这四位显示数字
```

**⑦ 命名不一致**：`clear_buffer()` / `send_code_to_buffer()` **没有 `bsp_digital_leds_` 前缀**。
它们是从测试代码直接提上来的，**接口统一命名这一步没做**（对比第 15/16 篇里 IIC/SPI 都做过"统一命名"）。

**⑧ 一处细节：`RCLK` 的静止电平不同**

| 函数 | 锁存序列 | 结束后 RCLK |
| --- | --- | --- |
| `bsp_digital_leds_send_code()` | `RCLK_L(); RCLK_H();` | **停在高** |
| `bsp_digital_leds_scan()`（实际在用） | `RCLK_H(); RCLK_L();` | **停在低** |

**两者都会产生一个上升沿**（74HC595 在 RCLK 上升沿锁存），所以**都能工作**；
但**静止电平不同**——实际只用 `scan()` 的那一路（停在低）是对的。若哪天有人改成调 `send_code()`，
**得先确认 RCLK 的初始电平**，否则可能"少一个上升沿"（一次不锁存）。

## 五、整体数据流

```
应用层                       缓冲区                    驱动层                   硬件
─────────                 ─────────                 ─────────                ─────
show_number(1234)
   │
   └─ 拆位 + 查表
        │
        └──────────→ displayBuffer[4..7] = {SEG_1, SEG_2, SEG_3, SEG_4}
                          │
                          │  （随时可改，改完自动生效）
                          ▼
                   bsp_digital_leds_scan()  ← 每 1 ms 被调用一次
                          │
                          ├─ position = 4 → 送 displayBuffer[4] + digCodeTable[4]
                          ├─ position = 5 → 送 displayBuffer[5] + digCodeTable[5]
                          ├─ ... 循环 8 位
                          │
                          └──→ send_byte(段码) → send_byte(位码) → RCLK 脉冲
                                                                        │
                                                                        ▼
                                                              595 输出 → 数码管亮
```

**这套「缓冲区 + 后台扫描」的设计可以照搬到**：

| 器件 | 应用层写什么 | 后台扫描做什么 |
| --- | --- | --- |
| LED 灯组（第 02 篇） | 直接调 `bsp_leds_open()` | 不需要扫描 |
| **数码管** | 写 `displayBuffer[]` | 逐位刷新 + 锁存 |
| 矩阵键盘（第 10 篇） | 读键值 | **反过来**：逐行扫描 + 逐列读回 |
| LCD / OLED | 写显存 | 定期刷新 |

> **规律**：**只要「屏幕内容」比「硬件能同时显示的」多，就需要「缓冲区 + 扫描」**。数码管就是个微缩版的「显示屏」。

## 七、排查清单

| 现象 | 优先检查 |
| --- | --- |
| 数码管完全没反应 | 595 供电/共地；`SER/RCLK/SRCLK` 三个引脚号接错；`bsp_digital_leds_init()` 没调用 |
| 上电显示乱码（如 8888） | 上电没有 `clear_buffer()`；`SEG_CLR` 应为 `0xFF`（共阳） |
| 显示的字型错乱 | 段码表错；或**先发/后发的顺序反了**（段码与位码互换）；或 bit 发送顺序反了（应 bit7 先行） |
| 只有一位亮，其他都不亮 | `bsp_digital_leds_scan()` **没有被反复调用**；或在主循环里被 `delay` 卡住了 |
| 数码管闪烁 / 有拖影 | 扫描间隔太长（应 1 ms/位）；或主循环里有阻塞延时把刷新率拖低了 |
| 某一位一直不亮 | `digCodeTable` 那一项写错；该位硬件虚焊 |
| 显示的数字和要显示的错位 | `show_number()` 用的下标（4~7）和 `clear_buffer()`/业务代码用的下标（0~3）不一致 |
| 显示的位数不对 | `DIG_NUM` 与实际硬件位数不符；`digCodeTable` 少了一项 |
| 改缓冲区后不生效 | 缓冲区改对了但 `scan()` 没被调；或改的是别的下标 |
| 一位特别暗 | 该位扫描占空比低（比如两位同时被选中）；位码不是独热码 |
| 多个数码管显示同样的内容 | 位码没跟着变，还停留在上一位 |

2. 写一个 `bsp_digital_leds_show_hex(uint16_t num)`，把数字显示成 4 位十六进制（0~9 A~F），用上现成的 `SEG_A` ~ `SEG_F`。
3. 加一个「闪烁」接口：`bsp_digital_leds_blink(uint8_t pos, uint8_t enable)`，让某一位以 2 Hz 闪烁。
4. 用 `SEG_R` / `SEG_S` / `SEG_O` / `SEG_N` / `SEG_L` / `SEG_H` / `SEG_G` 拼出 `SEG_ON` / `SEG_OFF` 之类的状态提示。
5. 把「有效显示位从哪一位开始」抽成 `#define DIG_BASE`，统一 `show_number()` 和 `main.c` 里的下标。
6. 把这个驱动改造成**只用一片 595 的 8 段一位**版本（只用位码不选位），体会「级联」和「单片的差异」。
