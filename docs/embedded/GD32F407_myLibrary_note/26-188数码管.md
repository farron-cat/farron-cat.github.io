## 一、它是什么

"188" 这个名字描述的是**它能显示的字形**：`1 8 8` —— 也就是**三位**，其中：
- **第一位只能显示 "1"**（硬件上只有两段：B1、C1，即 "1" 的两根竖笔）；
- **后两位是完整的 7 段**（A2~G2、A3~G3）；
- 外加 **两个图标**：`K1`、`K2`（常见是"充电/百分比"之类）。

所以可显示的数值范围是 **0 ~ 199**（第一位只有 0 或 1），这和 `bsp_188_leds_set_num()` 里那句 `if (num > 199) return;` 完全对应。

**段数清点**（这是理解后面映射表的关键）：

| 组 | 段 | 位数 |
| --- | --- | --- |
| 第一位 | B1、C1 | 2 |
| 第二位 | A2、B2、C2、D2、E2、F2、G2 | 7 |
| 第三位 | A3、B3、C3、D3、E3、F3、G3 | 7 |
| 图标 | K1、K2 | 2 |
| **合计** | | **18** |

**可只有 5 根 GPIO**（`PIN1~PIN5`）：`PE15`、`PE13`、`PE11`、`PE9`、`PE7`。

> 正常思路：18 个段至少 18 根线（共阳）或 5+7=12 根（扫描）。
> 这里用的是**更狠的一招**：5 根线**互相充当公共端和段线**，用"**时间 × 引脚配对**"来区分 18 个段——
> 5 根线两两组合有 5×4 = **20 种有向配对**，刚好够 18 个段用。

## 二、★ 5 根线怎么点 18 个段

### 2.1 先看数据结构：一个 32 位的位图

代码没有"段数组"，而是**一个 32 位变量当位图**，18 个段各占一位：

```c
// K2 K1 C1 B1 G2 F2 E2 D2 C2 B2 A2 G3 F3 E3 D3 C3 B3 A3   ← 注释按高位→低位写
#define A3 (1 << 0)      // 个位 a 段
#define B3 (1 << 1)
...
#define G3 (1 << 6)
#define A2 (1 << 7)      // 十位 a 段 —— 注意：正好比 A3 高 7 位！
...
#define G2 (1 << 13)
#define B1 (1 << 14)     // 百位 "1" 的两笔
#define C1 (1 << 15)
#define K1 (1 << 16)     // 图标
#define K2 (1 << 17)

static uint32_t leds_status = 0x0;   // ← 这就是"帧缓冲"
```

**要点**：

1. **位图 = 帧缓冲**：上层只改位图（"我要显示 123"），下层（扫描）负责把位图"翻译"成引脚动作。上层和硬件完全解耦——这是第 09 篇（74HC595 数码管）已经确立的模式。
2. **`A2` 恰好比 `A3` 高 7 位**，于是十位的码表可以直接由个位码表左移 7 位得到（提交里把重复的 `ten_digit_nums[]` 整段注释掉了）：

```c
// 优化掉 十位数字码表 由个位<<7得到
leds_status |= (one_digit_nums[num % 100 / 10] << 7);
```

> ⚠️ 这里有个容易被误会的细节：`one_digit_nums[]` 是 `uint8_t`，但 `one_digit_nums[x] << 7` **不会截断**——
> C 在移位前会把它**整型提升为 `int`**，所以 `0x7F << 7 = 0x3F80` 完整保留。
> 如果写成 `(uint16_t)(one_digit_nums[x]) << 7` 结果一样，但若反过来先截断再移位就会全错。**"整型提升救了这个技巧"。**

### 2.2 5 步扫描表（代码的核心）

每个扫描步长做两件事：**① 让某一根引脚输出高电平（当"公共端"）② 把需要亮的段的另一根引脚拉低；其余引脚全部置为高阻（输入）**。

| 步 | 公共端（输出高） | 拉低的引脚 → 对应段 |
| --- | --- | --- |
| 0 | **PIN1**(PE15) | PIN2→A3、PIN3→C3、PIN4→E3 |
| 1 | **PIN2**(PE13) | PIN1→B3、PIN3→A2、PIN4→C1、PIN5→K2 |
| 2 | **PIN3**(PE11) | PIN1→D3、PIN2→B2、PIN4→B1、PIN5→K1 |
| 3 | **PIN4**(PE9) | PIN1→F3、PIN2→D2、PIN3→C2 |
| 4 | **PIN5**(PE7) | PIN1→G3、PIN2→E2、PIN3→F2、PIN4→G2 |

把这张表"反过来读"就是**每个段的两根引脚**，例如：

```
A3（个位 a 段）= (PIN1 高, PIN2 低) → 只在第 0 步点亮
B3（个位 b 段）= (PIN2 高, PIN1 低) → 只在第 1 步点亮
B1（百位 "1"）= (PIN3 高, PIN4 低) → 只在第 2 步点亮
K2（图标）    = (PIN2 高, PIN5 低) → 只在第 1 步点亮
```

代码就是这张表的直译（`bsp_188_leds_scan()` 的 5 个 `case`）：

```c
case 0:
    PIN_ALL_IN;                  // ① 先把 5 根线全部置高阻（"清场"）
    PIN_OUT(PIN1, 1);            // ② 公共端输出高
    if (leds_status & A3) PIN_OUT(PIN2, 0);   // ③ 位图里这一位是 1，才把对应段拉低
    if (leds_status & C3) PIN_OUT(PIN3, 0);
    if (leds_status & E3) PIN_OUT(PIN4, 0);
    break;
```

### 2.3 为什么"其余引脚必须高阻"

因为**任意一根输出高的线 和 任意一根输出低的线 之间，都会亮一颗 LED**。
如果第 0 步把 PIN3、PIN4 也都主动拉低（而不是只拉该亮的段、其余高阻），
那么 `(PIN1 高, PIN3 低)`、`(PIN1 高, PIN4 低)` 这些**本不该亮的配对就会跟着亮**——这叫"**鬼影**"（ghosting）。

所以这条规则必须记住：

> **每一步：1 根输出高 + 若干根输出低（只拉需要亮的）+ 其余全部高阻。**
> 高阻（`GPIO_MODE_INPUT` + `GPIO_PUPD_NONE`）就是"我退出这条线，别把我算进去"。

`PIN_ALL_IN` 的写法也就有了意义——**每步开头先让所有引脚"退场"，再点名让两根上场**：

```c
#define PIN_IN(pin)                                                                         \
    do                                                                                      \
    {                                                                                       \
        gpio_mode_set(pins[pin].port, GPIO_MODE_INPUT, GPIO_PUPD_NONE, pins[pin].gpio_pin); \
    } while (0)

#define PIN_ALL_IN    \
    do                \
    {                 \
        PIN_IN(PIN1); PIN_IN(PIN2); PIN_IN(PIN3); PIN_IN(PIN4); PIN_IN(PIN5); \
    } while (0)

#define PIN_OUT(pin, val)                                                                    \
    do                                                                                       \
    {                                                                                        \
        gpio_mode_set(pins[pin].port, GPIO_MODE_OUTPUT, GPIO_PUPD_NONE, pins[pin].gpio_pin); \
        gpio_bit_write(pins[pin].port, pins[pin].gpio_pin, val);                             \
    } while (0)
```

> **`do { } while (0)` 的来历**：第一次提交（`f6129e4`）里 `PIN_ALL_IN` 是一串**裸宏**（用 `;` 分隔），
> 一旦写成 `if (x) PIN_ALL_IN; else ...` 就会展开成两条语句 → `else` 找不到 `if` → 编译错误或逻辑错乱。
> `c630553` 把它全部包进 `do { } while (0)`，这才是**宏的正确写法**。
> 这类"看起来多余的包装"是 C 语言里少数**必须做**的防御。（本项目共出现 3 处：`PIN_IN` / `PIN_ALL_IN` / `PIN_OUT`。）

### 3.2 `c630553`（10-10 16:40）：码表 + 扫描 + SysTick 节拍

这一版把 `.c` 从 43 行扩到约 260 行，做了 4 件事：

| 动作 | 内容 |
| --- | --- |
| **① 加入码表** | `one_digit_nums[10]`（0~9 的 7 段码），十位表**用 `<<7` 复用** |
| **② 加 `show()`（阻塞版）** | 5 步 + 每步 `delay_1ms(1)`，整帧 5 ms |
| **③ 加 `scan()`（非阻塞版）** | 一次只走一"步"，用 `static uint8_t scan_step` 记忆状态 |
| **④ 挂到 SysTick** | `gd32f4xx_it.c` 里每 1 ms 调一次 `bsp_188_leds_scan()` |
| **⑤ 宏加 `do{}while(0)`** | 见 §2.3 |
| **⑥ 删掉 `bsp_188_leds_test()`** | 临时验证代码不留在工程里（**好习惯**） |
| **⑦ 把 `clear` 收进 `set_num`** | 见 §3.3 |

`gd32f4xx_it.c` 的改动（**这是本工程第一次把"用户代码"放进 SysTick**）：

```c
void SysTick_Handler(void)
{
    static uint16_t div = 0;

    delay_decrement();               // 原有的 1 µs 递减（第 01 篇）

    // 每1ms扫描一次188数码管
    if (++div >= 1000)               // 1 µs × 1000 = 1 ms
    {
        div = 0;
        bsp_188_leds_scan();
    }
}
```

**刷新的账要算清**：SysTick 是 **1 µs** 节拍 → `div` 数到 1000 才调用一次 → **1 ms 走一步**；
一帧 5 步 → **帧周期 5 ms，刷新率 200 Hz**，每个段的占空比 **1/5 = 20%**。

> 200 Hz 远高于人眼闪烁临界（约 50 Hz，见第 13 篇"视觉暂留 41.7 ms"），所以不闪；
> 20% 占空比意味着**峰值电流要够**（5 段平均分摊），亮度也比直流驱动低——这是"省引脚"要付的代价。

### 3.3 `7230a95`（10-10 17:18）：把"隐式约定"收进函数内部

`c630553` 的调用方长这样（**主人必须自己记住两件事**）：

```c
num = get_us_cnt();
bsp_188_leds_clear();                       // ← 必须先清！（否则上次的数字残留）
bsp_188_leds_set_num(num / 1000000 % 1000); // ← 而且 num 可能 > 199，函数会直接 return
```

`7230a95` 改成了：

```c
num = get_us_cnt() / 1000000 % 1000;
if (num > 199)
    num = 199;                              // ← 调用方自己夹紧
bsp_188_leds_set_num(num);                  // ← 内部已经会 clear
```

以及函数内部的收拢：

```c
void bsp_188_leds_set_num(uint8_t num)
{
    if (num > 199) return;

    // 清除原有的数字显示状态，只保留 K1 和 K2 的状态
    bsp_188_leds_clear();      // ★ 从"调用方负责"变成"函数自己负责"
    ...
}

void bsp_188_leds_clear()
{
    leds_status &= K1 | K2;    // ★ 只清数字，保留 K1/K2 图标
}
```

这次提交还有两个看点：

| 变化 | 为什么重要 |
| --- | --- |
| `clear()` 从 `leds_status = 0` 改成 `&= K1 \| K2` | **清数字不该连带清图标**——一次"作用范围"的修正（和第 05 篇 `stoping_cnt` 被两个状态共用是同一类问题） |
| 新增 `set_charge()` / `set_percent()` | 把 K1/K2 也纳入**同一个位图**统一管理，而不是各写各的 |

> **这一版其实是一个"接口契约"的经典修复**：
> `set_num()` 既然语义是"让显示器显示 num"，那么"清掉旧的"就是它**份内的事**。
> 让调用方必须先 `clear()` 是**把内部状态泄漏给了使用者**——这种"得记住先调 A 再调 B"的约定，
> 一旦漏掉就会出 bug（比如显示 "123" 后改成 "7"，会变成 "723"）。
> **凡是"必须先做 X 才能调 Y"的约定，都应该想办法塞进 Y 里面。**

## 四、最终代码逐段解读

### 4.1 引脚参数表与索引枚举

```c
static LED188_PIN_PARAM pins[] = {          // 参数表（第 02 篇 leds[] 的同一手法）
    {PIN1_RCU, PIN1_PORT, PIN1_PIN},        // PE15
    {PIN2_RCU, PIN2_PORT, PIN2_PIN},        // PE13
    {PIN3_RCU, PIN3_PORT, PIN3_PIN},        // PE11
    {PIN4_RCU, PIN4_PORT, PIN4_PIN},        // PE9
    {PIN5_RCU, PIN5_PORT, PIN5_PIN},        // PE7
};

typedef enum { PIN1 = 0, PIN2, PIN3, PIN4, PIN5, LED188_PIN_NUM } LED188_PIN_INDEX;
```

- **表 + 枚举**：把"引脚号"这种硬件细节集中到一处，宏（`PIN_OUT`）里就能用 `pins[pin]` 索引——**改板子只改这张表**。
- `LED188_PIN_NUM = 5` 放在枚举最后，既是"个数"也是"边界"，`for (i = 0; i < LED188_PIN_NUM; i++)` 用它循环不会越界。

### 4.2 初始化

```c
void bsp_188_leds_init()
{
    for (uint8_t i = 0; i < LED188_PIN_NUM; i++)
    {
        rcu_periph_clock_enable(pins[i].rcu);                                        // 开时钟（5 个都是 GPIOE，重复开无害）
        gpio_output_options_set(pins[i].port, GPIO_OTYPE_PP, GPIO_OSPEED_MAX, pins[i].gpio_pin);
    }
}
```

**注意它没有调用 `gpio_mode_set()`** —— 这是**故意**的：

- GPIO 复位后的默认模式是**输入（高阻）**，也就是我们想要的"退场"状态；
- `gpio_output_options_set()` 只是把**输出相关的配置**（推挽、速度）先写好，等 `GPIO_MODE_OUTPUT` 被设上就立即生效。

**结果**：初始化之后五根线全是高阻，**一个段都不亮**，然后由扫描逐步点亮 —— 既安全（不会上电乱亮），又省事。

### 4.3 位图 → 引脚：`scan()` 的 5 个 case

见 §2.2 的扫描表。每个 case 的三段式结构固定：

```
PIN_ALL_IN;                          // 1. 全部退场
PIN_OUT(公共端, 1);                   // 2. 点名一根当阳极
if (leds_status & 段) PIN_OUT(段脚, 0);// 3. 按位图点亮对应的段
```

`scan_step` 是 `static`（**状态留在函数外面**，让每次调用"记得上次走到哪"——和 `bsp_keys` 的位图、呼吸灯的计数是同一手法）：

```c
static uint8_t scan_step = 0;
...
scan_step++;
if (scan_step >= 5) scan_step = 0;
```

### 4.4 显示一个数

```c
void bsp_188_leds_set_num(uint8_t num)
{
    if (num > 199) return;              // 超出量程直接不动（保留上一次显示）

    bsp_188_leds_clear();               // 清数字、留图标

    if (num > 99)
        leds_status |= B1 | C1;                          // 百位：只有"1"
    if (num > 9)
        leds_status |= (one_digit_nums[num % 100 / 10] << 7);  // 十位：个位码表 << 7
    leds_status |= one_digit_nums[num % 10];                // 个位
}
```

三个技巧一次说完：

| 代码 | 作用 | 等价写法 |
| --- | --- | --- |
| `num % 100 / 10` | 取十位 | `num / 10 % 10`（对本例都行，前者在 >99 时也正确） |
| `one_digit_nums[x] << 7` | 个位码表当十位码表用 | 另写一张 `ten_digit_nums[10]`（表更大、易写错） |
| `if (num > 9)` / `if (num > 99)` | **前导零消隐** | 显示 "007" 而不是 "7"，一般不是想要的 |

**为什么 `num > 199` 要 return 而不是钳位**：函数是"设置"语义，参数非法时**不动状态**是合理约定；
但代价是**调用方拿到的是一个"没有反应"的函数**——所以 `main.c` 里主动做了钳位（§3.3）。
**"函数保持沉默、调用方负责夹紧"是常见的分工，但一定要在头文件注释里写清楚。**

## 五、扫描节拍：谁来调用 `scan`

本模块给了**两个入口**，用途完全不同：

| | `bsp_188_leds_show()` | `bsp_188_leds_scan()` |
| --- | --- | --- |
| 一次调用做什么 | **一整帧**（5 步） | **一步** |
| 是否阻塞 | 是：5 × `delay_1ms(1)` = **5 ms** | 否：纯 GPIO 操作，约几 µs |
| 谁调用 | 自测/独占场景 | **`SysTick_Handler`，每 1 ms 一次** |
| 适合场景 | "我就想显示一下，别的不干" | 主循环还有别的活（读时间、刷 OLED、读 NTC） |

**这和第 09 篇（74HC595 数码管）、第 05 篇（充电流水灯）的结论完全一致**：

> **只要"显示"要和"业务"并行，就必须把"一整帧"拆成"一步一次"。**
> 而拆开之后必须有个**固定节拍**来推进它——本工程用过两种节拍源：
> ① 定时器中断（第 07/09 篇的 TIMER）；② **SysTick**（本篇）。

**把用户代码放进 SysTick_Handler 的代价**（值得知道的权衡）：

| 优点 | 代价 |
| --- | --- |
| 节拍天然精确（1 µs 基准，软件分频） | SysTick 优先级固定为**最高**（异常号 -1），会**抢占**所有外设中断 |
| 不用配定时器、不占额外外设 | Handler 里做的事越多，**`delay_1us()` 的时基精度越差**（`delay_decrement()` 被推后） |
| 与 `delay_1ms/1us` 共用同一个计数器 | 一旦将来在 `scan()` 里加入耗时操作（IIC/printf），会**连锁影响所有延时** |

> 本篇的 `scan()` 只做 GPIO 操作，**只有几微秒**，所以放在 SysTick 里是安全的；
> 而 `c630553` 之前的 `show()` 里有 `delay_1ms()`，**绝对不能**放进中断（会死锁式地卡死 SysTick 时基）。
> 这也正是第 12 篇"中断里不要做耗时操作"的同一条规则的又一次体现。

## 七、⚠️ 引脚复用：和矩阵键盘抢线

把代码里的 5 个引脚，对照 `Doc/硬件信息汇总.md` 的权威引脚表：

| 代码里 | MCU 引脚 | 板上的网络名 | 板上连到哪里 |
| --- | --- | --- | --- |
| PIN1 | **PE15** | `KCOL_4` | **矩阵键盘第 4 列**（SW4/8/12/16） |
| PIN2 | **PE13** | `KCOL_2` | **矩阵键盘第 2 列**（SW2/6/10/14） |
| PIN3 | **PE11** | `KROW_4` | **矩阵键盘第 4 行**（SW13~SW16） |
| PIN4 | **PE9** | `KROW_2` | **矩阵键盘第 2 行**（SW5~SW8） |
| PIN5 | **PE7** | `PE7` | P3.13 排针（**板上空闲**） |

也就是说：**188 数码管用掉了 4 根"矩阵键盘的行列线" + 1 根空闲脚**。这带来三个必须知道的结论：

1. **188 数码管是外接模块**（插在 P3 排针上），因为板上 BOM 里的数码管 `LED11/LED12` 是另一套（12 脚 4 位 7 段，经 74HC595 → `PD0/PD1/PD4`）。
   —— **两种数码管、两种驱动方式，代码里都在，别搞混**（第 09 篇讲的是 74HC595 那套）。
2. **当 188 模块在用的时候，矩阵键盘不能同时扫描**：
   两边都在"驱动同一批引脚"，会互相干扰（显示乱、读键错乱），严重时一边输出高、一边输出低形成**短路**。
   > 目前工程里矩阵键盘在未合并的 `keypad` 分支（第 10 篇），**当前不会同时跑**——但只要将来合并进来，就必须做"**二选一**"或"分时复用"。
3. **按下键盘按键 = 把两根线短接**：即使键盘模块没在跑，**物理按键按下**也会把 `KROW_x` 和 `KCOL_y` 短接。
   如果此刻 188 正在扫描，就会出现"某根公共端把电流灌进另一根"的情况 → **段亮度异常**。
   实际使用中要**避开**按键动作与显示刷新重叠，或者干脆接受"按键时显示微抖"。

> **这正是第 20 篇"代码 ↔ 硬件 校验"的价值所在**：只看代码是发现不了这个冲突的，
> 必须把"代码用哪些引脚"和"板上这些引脚接到了什么"对起来看。
> （顺带一提：`Doc/引脚检查测试.md` 的"三个必须处理的问题"里没有这一条——**它是在 188 模块写出来之后才产生的新冲突**。）

### 7.x 预言兑现：冲突被官方承认了（2026-10-10 / 10-12）

上面那张表写于 2026-10-10 上午。**当天晚上和两天后的两次提交，把这段推断一步步证实了**：

| 时间 | 提交 | 对 188 与键盘的处置 | 说明 |
| --- | --- | --- | --- |
| 10-10 22:16 | `c4a098e`【合并】 | **关掉 188、启用矩阵键盘** | **合并提交的信息就是一句警告**：「矩阵键盘与 188 数码管引脚冲突，不能同时使用」。`main.c` 里 `// bsp_188_leds_init();`、`// bsp_188_leds_set_num(...)`、以及 SysTick 里的 `// bsp_188_leds_scan();` 全被注释 |
| 10-12 12:13 | `0d729ce`【更新 ADKEY】 | **反过来：启用 188、关掉键盘** | 188 的调用全部恢复；`// bsp_keypad_init();`、`// int key = KeypadScan();` 被注释；按键输入改由 **AD 按键**承担（第 28 篇，它只用 `PB0` 一根线） |

**这条链是"引脚不够时怎么做取舍"的完整案例**：

```
PE 口被 188 数码管占用（PE15/13/11/9）
    → 4×4 矩阵键盘用不了（它要 PE8~PE11 + PE12~PE15）
        → 但用户还需要按键
            → 换成"1 根 ADC 线接 3 个键"的 AD 按键（PB0，第 28 篇）
```

**三点结论**（比"改引脚"更重要）：

1. **笔记里"只看代码发现不了"的那条判断是对的**——作者自己也把"不能同时使用"写进了提交信息；
2. **代码里留一条解释**（`// 矩阵键盘扫描 与188数码管引脚冲突，不能同时使用`）比"留一行注释掉的调用"有价值得多，
   它让**两年后读代码的人**（包括自己）立刻明白"为什么这里被注掉了"；
3. **"合了但先不启用"是一种成熟的合并策略**：`c4a098e` 把键盘驱动合进 `main`（代码入库、随时可用），
   **但把调用点关掉**——**"合并"和"启用"是两件独立的事**（第 10 篇 §4.7 有完整记录）。

> **所以本篇 §7 的结论升级为**：**这个模块不是"不能和键盘同时用"，而是"必须显式二选一，并把选择写进代码注释里"。**

### 练习题

1. **算一遍刷新账**：把 SysTick 分频从 1000 改成 2000（每 2 ms 一步），帧周期和刷新率各是多少？还会闪吗？
2. **加小数点/冒号**：如果模块还有一个 DP 段没有用到（位图里空着某个 bit），请补上点亮的代码。
3. **做"亮度分级"**：把 5 步里的某一步跳过（不点亮），观察对应段变暗——理解"占空比 = 亮度"。
4. **用定时器替换 SysTick**：用 TIMER5（第 07 篇）产生 1 ms 中断来调 `scan()`，把 SysTick 还给纯时基，对比两者对 `delay_1us()` 精度的影响。
