## 一、WS2812 是什么

**WS2812（也叫 NeoPixel）是一颗"把控制芯片和 RGB 三色 LED 封装在一起"的智能灯珠**：

| 特性 | 说明 |
| --- | --- |
| 接口 | **单根数据线（DIN → DOUT 级联）**，**没有时钟线** |
| 供电 | +5 V（逻辑电平按 5 V 器件算） |
| 数据格式 | **每颗 24 位 = `G7..G0 + R7..R0 + B7..B0`（GRB 顺序！）** |
| 级联 | 第 1 颗吃掉 24 位，剩下的**透传**给下一颗 → **N 颗灯 = N × 24 位** |
| 编码 | 靠**高电平持续时间**区分 0 和 1（**没有时钟，靠"位内定时"**） |
| 复位 | 数据线**连续低电平 > 50 µs**（WS2812B）／ **> 280 µs**（WS2812B-V5）视为一帧结束 |

### 1.1 0 和 1 怎么区分

| 位 | 高电平 T_H | 低电平 T_L | 位周期 |
| --- | --- | --- | --- |
| **`'0'`** | **400 ns ± 150**（250~550） | 850 ns ± 150 | 1.25 µs |
| **`'1'`** | **800 ns ± 150**（650~950） | 450 ns ± 150 | 1.25 µs |

**注意窗口只有 ±150 ns** —— 这是本篇所有麻烦的来源：
**MCU 必须把 400 ns 和 800 ns 这两档"做准"，误差超过了芯片的判决窗口，灯就会认错位。**

### 1.2 为什么"没有时钟线也能同步"

因为**约定死了位周期（1.25 µs）**：芯片在每个位的**上升沿**重置内部计时器，
然后在**大约 0.5~0.6 µs** 处采样数据线的电平——

```
       ┌──────┐        ┌──────────────┐
       │ T_H  │  T_L   │     T_H      │
───────┘      └────────┘              └──────
       ↑上升沿                ↑上升沿     ← 每个上升沿"重新计时"
          ↑采样点(~0.5us)         ↑采样点
```

**采样点在高电平出现后约 0.5~0.6 µs**：如果那时线还是高 → 读到 `'1'`；已经变低 → 读到 `'0'`。
所以 **T_H 必须明显分居采样点两侧**：400 ns（在采样点前变低 → `'0'`）和 800 ns（在采样点后才变低 → `'1'`）。

> **位周期和采样点的存在，解释了两件事**：
> ① 为什么"空闲电平"很重要（一个长高电平会被当成一个 `'1'`，第四章根因②）；
> ② 为什么"位流中间被打断"会翻位（某个位的高电平被拉长 → `'0'` 被判成 `'1'`，第六章）。

## 二、★ 用 SPI 位流模拟单总线

### 2.1 思路

WS2812 要的是"**精确到几百纳秒的高低电平序列**"。用 GPIO 翻转 + `delay_1us`（1 µs 精度）**根本做不到**。
所以本工程用了一个很巧的办法：

> **用硬件 SPI 的 MOSI 当数据线，用"多个 SPI 位"拼出 1 个 WS2812 位。**

因为 SPI 的移位是**硬件分频产生**的，位宽精度取决于 APB 时钟（几十 ns 级），比软件翻转精确得多。

```
1 个 WS2812 位  =  N 个 SPI 位
   '0' → 前几个 SPI 位发 1，其余发 0   （高电平短）
   '1' → 更多个 SPI 位发 1，其余发 0   （高电平长）
```

**关键公式**（**改 SPI 时钟必须重算 N**）：

$$N \times \frac{1}{f_{SPI}} = 1.25\ \mu s$$

### 2.2 本工程最终的编码：N = 13

SPI1 实际跑 **10.5 MHz**（= APB1 42 MHz ÷ 4，§4.2 会讲这个数是怎么算错的），所以：

$$N = \frac{1.25\ \mu s}{1/10.5\ \text{MHz}} = 13.1 \Rightarrow N = 13,\quad 13 \times 95.24\ ns = 1238\ ns \approx 1.25\ \mu s\ (\text{误差 } 1\%)$$

| 位 | 13 个 SPI 位 | 掩码 | 高/低 | 实际时间 | 规格 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| `'0'` | `1111 0000 0000 0` | `0x1E00` | 4 高 / 9 低 | **381 ns / 857 ns** | 400±150 / 850±150 | ✅ 正中 |
| `'1'` | `1111 1111 0000 0` | `0x1FE0` | 8 高 / 5 低 | **762 ns / 476 ns** | 800±150 / 450±150 | ✅ 正中 |

**字节账**（这一步很关键，否则会算错缓冲区大小）：

```
1 个 WS2812 位   = 13 个 SPI 位
1 个颜色字节     = 8 位        = 8 × 13 = 104 个 SPI 位 = 104/8 = 13 字节（104 正好被 8 整除 ✅）
1 颗灯（GRB）    = 3 个颜色字节 = 3 × 13 = 39 字节
4 颗灯一帧       = 4 × 39      = 156 字节 → 156 × 8 / 10.5 MHz = 118.9 µs
```

### 2.3 一个漂亮的实现技巧：不用预生成表

传统写法会为 256 种颜色字节**各生成一张 13 字节的表**（256 × 13 = 3328 字节）。
本工程改成**现场展开**：把 8 个"13 位单元"依次拼进一个 32 位累加器，每凑满 8 位就吐出一个字节。

```c
static void ws2812_pack_byte(uint8_t dat, uint8_t *out)
{
    uint32_t acc  = 0;   // 位累加器
    uint8_t  bits = 0;   // acc 里的有效位数
    uint8_t  n    = 0;   // 已输出的字节数

    for (int8_t i = 7; i >= 0; i--)                      // 高位先行
    {
        acc = (acc << 13) | ((dat & (1 << i)) ? WS2812_CELL_1 : WS2812_CELL_0);
        bits += 13;
        while (bits >= 8)
        {
            bits -= 8;
            out[n++] = (uint8_t)((acc >> bits) & 0xFF);
        }
    }
}
```

**零存储、任意颜色**，而且代码里给了**自检值**（第六章会用来验证）：

```
pack(0x00) → F0 07 80 3C 01 E0 0F 00 78 03 C0 1E 00
pack(0xFF) → FF 07 F8 3F C1 FE 0F F0 7F 83 FC 1F E0
```

> **这个函数本身就是"位运算 + 流式打包"的绝好练习**：
> 8 × 13 = 104 位**正好**是 8 的整数倍 → 循环结束时 `bits` 恰好为 0，**不需要收尾 flush**。
> （如果 N 不是"能让 8N 被 8 整除"的数——其实 8N 永远能被 8 整除——但**如果不是"8 位一组"而是"7 位一组"就不一定了**，比如第 4.4 节的备选方案 N=7。）

## 四、★ "只亮第 1 颗"破案记

> 本节的内容来自工程内文档 `Doc/WS2812只亮第1颗灯的问题分析与修复.md`（在 `ws2812_ai` 分支上）。
> **这篇文档值得整篇读一遍**——它把"用现象反推寄存器里的位模式"这件事做到了教科书级别。

### 4.1 现象的三个阶段

| 阶段 | 代码状态 | 现象 |
| --- | --- | --- |
| ① 初始 | **10 位/位**的编码表 + `SPI_PSC_4`，无帧前复位 | **第 1 颗红，第 2~4 颗全黑** |
| ② 改编码后 | **13 位/位**（时序对了），仍无帧前复位 | 4 颗都亮，但**第 1 颗橙黄**，其余红 |
| ③ 修复后 | 13 位/位 + 帧前/帧尾 SPI 复位 | **4 颗全红** ✅ |

**第一眼的关键线索**：**4 颗灯送的是完全相同的数据**，
所以"**只有第 1 颗错**"这件事本身就指向**帧头（时间起点）**，而不是数据内容。

### 4.2 根因①：编码表是照 8 MHz 做的，实际跑 10.5 MHz

**那张 10 位/位的表是这样设计的**：

| 位 | 编码（10 bit） | 高电平 | 在 **8 MHz** 下 |
| --- | --- | --- | --- |
| `'0'` | `1110000000` | 3 位 | T0H = 375 ns ✅（规格 400） |
| `'1'` | `1111111000` | 7 位 | T1H = 875 ns ✅（规格 800） |

**10 位 × 125 ns = 1250 ns = 1.25 µs** —— 说明**这张表就是照 8 MHz 算的**。

**但代码实际配的是 SPI1 + `SPI_PSC_4`**，而 SPI1 挂在 **APB1**：

```c
spi_struct.prescale = SPI_PRES;   // SPI时钟预分频  84M/4 = 21M     ← ★ 这句注释错了
```

**那句注释是错的，而且错了两层**：

| 依据 | 结论 |
| --- | --- |
| `system_gd32f4xx.c`：`APB2 = AHB/2`、`APB1 = AHB/4` | AHB=168 M → **APB2 = 84 M、APB1 = 42 M** |
| `gd32f4xx_rcu.h`：`RCU_APB1EN_SPI1EN = BIT(14)`、`RCU_APB2EN_SPI0EN = BIT(12)` | **SPI1 在 APB1（42 M）**，SPI0 才在 APB2（84 M） |
| `gd32f4xx_spi.h`：`SPI_PSC_4` = ÷4 | 分频系数 **÷4** |

$$\text{SPI1} = 42\ \text{MHz} / 4 = \mathbf{10.5\ MHz}\quad(\text{不是 } 21\ \text{MHz})$$

**"84 M ÷ 4 = 21 M" 是 SPI0 的账**，被抄过来了（第 16/24 篇的 SPI0 确实是 21 MHz）。

**数值后果**（表是按 8 MHz 设计的，却跑在 10.5 MHz → **整条时序短 24%**）：

| 参数 | 表的设计值(8 MHz) | 实际值(10.5 MHz) | 规格 | 判定 |
| --- | --- | --- | --- | --- |
| 1 个 SPI 位 | 125 ns | **95.2 ns** | — | 短 24% |
| 位单元（10 位） | 1250 ns | **952 ns** | 1250 ns | 短 24% |
| T0H | 375 ns | 286 ns | 250~550 | 勉强过 |
| **T1H** | 875 ns | **667 ns** | 650~950 | **只高 17 ns，贴着下限** |

**为什么"第 1 颗亮、后 3 颗不亮"**：芯片在上升沿后约 0.5~0.6 µs 采样。
`T1H = 667 ns` 已经压着下限，而**不同芯片的内部振荡器和判决门限有离散性**：

| 芯片 | 对 `0xFF`（8 个连续 `'1'`）的判决 | 结果 |
| --- | --- | --- |
| 第 1 颗（门限偏低） | 判成 `1` → R = 0xFF | 红 ✅ |
| 第 2~4 颗（门限偏高） | 判成 `0` → R = **0x00** | 该通道全灭 → **黑** |

而 G、B 本来就是 `0x00`，即使判错也看不出来 → 现象就是"**第 1 颗红、其余三颗干脆不亮**"。

> **这是"数据速率超出器件接收窗口"的典型症状**：**前级勉强能认、后级认不出来**。
> 相似的例子在第 23 篇的"典型值 vs 保证值"里也出现过——**时序参数要留裕量，不能踩下限**。

### 4.3 根因②：帧头"多吃"了 1 个数据位（第 1 颗变橙黄）

时序修对之后，4 颗都亮了，但第 1 颗颜色不对。**这次靠反推就直接定位了**：

$$\text{第 1 颗} = (G, R, B) = (\mathbf{0x80},\ \mathbf{0xFF},\ \mathbf{0x00}) \Rightarrow \text{橙黄}$$

`G = 0x80` 只可能是"**`'1'` + 后面 7 个 `'0'`**" → **第 1 颗的 G 前面多了一个数据位**。

**那个多余的高电平从哪来**：

| 环节 | 事实 |
| --- | --- |
| SPI 空闲（已使能、但没在发数据）时 | **MOSI 不驱动 → 高阻** |
| 板上 PB15 网络 | `DH`（DHT11 的数据脚），挂着 **`R6` = 10 kΩ 上拉到 +5 V** |
| 高阻 + 10 kΩ 上拉 → | **线被拉高** |
| 持续多久 | `bsp_ws2812_rgb_leds_init()` 到 `send()` 之间隔了 printf、IIC OLED 刷屏、flash 测试 ≈ **1.5 秒** |

WS2812 靠**上升沿**给位定界：这段 1.5 s 的长高电平没有新上升沿，但**芯片的采样时刻看到的是高电平** → 被记成 **1 个数据位 `'1'`**。

**为什么正好是 `G = 0x80`**（把位单元编号为 `c0~c155`，每颗灯 24 个单元，`c0~c7`=G、`c8~c15`=R、`c16~c23`=B）：

| 接收方的位 | 对应波形 | 说明 |
| --- | --- | --- |
| `bit0` | 帧前的长高电平 | 被记成 `'1'`（**多余的那一位**） |
| `bit1` | `c1` | `c0` 的高电平接在长高电平后面 → **不产生新上升沿 → 被吞掉** |
| `bit k` | `c(k)` | 之后逐位对齐 |

于是第 1 颗的窗口 = `bit0~bit23` = `['1'] + c1~c23`：

| 通道 | 窗口 | 位模式 | 值 |
| --- | --- | --- | --- |
| **G** | `bit0~bit7` = `'1'` + `c1~c7` | `1000 0000` | **0x80** |
| R | `bit8~bit15` = `c8~c15`（8 个 `'1'`） | `1111 1111` | 0xFF |
| B | `bit16~bit23` = `c16~c23`（8 个 `'0'`） | `0000 0000` | 0x00 |

→ `(G,R,B) = (0x80, 0xFF, 0x00)` = **R 满 + G 一半 = 橙黄**，**与现象完全一致** ✅

**为什么第 2~4 颗没事**：错位只有 1 个单元，而每颗灯是 **24 个单元的整数块**，
`c24` 恰好又是第 2 颗灯的块边界 → **块边界自动重新对齐**：

| 灯 | 接收窗口 | 解出的 GRB | 结果 |
| --- | --- | --- | --- |
| 第 1 颗 | `bit0~bit23` = `'1'` + `c1~c23` | (0x80, 0xFF, 0x00) | 橙黄 ❌ |
| 第 2 颗 | `bit24~bit47` = `c24~c47` | (0x00, 0xFF, 0x00) | 红 ✅ |
| 第 3、4 颗 | 同理 | (0x00, 0xFF, 0x00) | 红 ✅ |

多出来的那 1 位把最后一格 `c155` 挤给了"第 5 颗芯片"（不存在）→ **无副作用**。

> ★ **"只有第 1 颗对/错"是帧头类问题的指纹**——这条可以直接背下来：
> 因为多颗灯送同一数据、且周期是 24 的整数倍，**位单元整体错 1 位时块边界会重新对齐**。
> 看到这个现象优先查帧头（时间起点），而不是数据内容。

### 4.4 为什么不能"直接把 SPI 改成 8 MHz"（以及备选方案）

既然表是照 8 MHz 做的，那把时钟改成 8 MHz 不就行了？**不行**：

> APB1 = 42 MHz，而 SPI 的分频系数**只能是 2 的幂**（`SPI_PSC_2/4/8/16/...`）
> → 可得 **21 / 10.5 / 5.25 / 2.625 MHz**，**没有 8 MHz**。

所以正确做法是：**时钟保持 10.5 MHz，改"1 位用几个 SPI 位"**（10 → 13）。

**备选解**（文档里也记了）：降到 `SPI_PSC_8`（5.25 MHz）+ **7 位/位**：
$7/5.25\text{M} = 1333\ ns$，`'0'` = 2 高 5 低 = 381 ns、`'1'` = 4 高 3 低 = 762 ns —— **同样合规**，但帧更长。
**两档都在规格正中，选 13 位/位是因为帧更短。**

### 4.5 顺手排除掉的三个"看起来很像"的原因

| 候选原因 | 为什么不是它 |
| --- | --- |
| **3.3 V 逻辑电平不够**（WS2812B $V_{IH} = 0.7 \times 5 = 3.5\ V$） | 第 2~4 颗的 DIN 来自前一颗**5 V 摆幅的 DOUT**，电平只会更好；若真是电平问题，第 1 颗会**最先**出错，而不是"只多 1 位"。何况 R6 上拉到 5 V 已把高电平抬到 ~3.9 V |
| **复位时间不足**（>50 µs） | 复位是 4 颗芯片**公共**的动作，不可能只让第 1 颗多一位 |
| 数据顺序写错（RGB vs GRB） | 那会**4 颗全错**，不会只有第 1 颗 |

> **"排除法"也是排查的一部分**：把"能解释现象但与细节不符"的候选一个一个排除，
> 比"猜一个改一个"快得多。

## 五、最终代码逐段解读

### 5.1 复位：必须由 SPI 自己产生低电平

```c
#define SPI_ONEWIRE_RESET_BYTES 400          // 400 × 762 ns = 304.8 µs

void msp_spi_onewire_reset(void)
{
    for (uint16_t i = 0; i < SPI_ONEWIRE_RESET_BYTES; i++)
        hard_spi_write_byte(0x00);           // 0x00 的 8 个位全是 0 → 整字节连续低电平
}
```

- `0x00` 的每一位都是 0 → **整个字节期间数据线都是低** → 400 字节 = **304.8 µs 连续低电平**，
  同时满足 WS2812B（>50 µs）与 WS2812B-V5（>280 µs）；
- **帧前、帧尾各调一次**：帧前保证第 1 个数据位有干净的前导低电平（治 §4.3），帧尾让 4 颗灯一起锁存。

**❌ 为什么"切 GPIO 拉低 300 µs"的写法没用**（第一版就是这么做的，失败了）：

```
   ┌── AF 输出（SPI 驱动）──┐  ┌ 切 GPIO 输出 → 拉低 300µs ┐  ┌ 切回 AF ─┐
DIN ───────── 数据 ────────   └────── 0V ──────┘   ↑高阻！   ── 数据 ──
                                                   │
                                 R6(10k→+5V) 用几百 ns 就把线又拉高了
```

**切回 AF、SPI 刚使能的瞬间 MOSI 又是高阻** → R6 立刻把线拉高 → "长高电平"照样出现在第 1 个数据位之前。
**所以低电平必须由 SPI 全程推挽驱动**（R6 抬不动推挽输出）。

> **对比：原代码末尾那 110 个 `0x00` 根本不是"复位"**
> 在 10 位/位的表里 `0x00` = `1110000000`，**每个字节仍有 3/10 的高电平**；
> 那 110 个字节其实等价于 **88 个多余的 `'0'` 数据位**，
> 真正的复位纯属"**发完之后 MOSI 恰好停在最后一个 `'0'` 上**"的**运气**
> （只要换个结尾字节，一颗都不会亮）。
> **教训**：**"复位"要看得见**——不能靠"最后一个位恰好是低"这种巧合。

### 5.2 发送：帧前复位 → 关中断发送 → 帧尾复位

```c
void bsp_ws2812_rgb_leds_send(void)
{
    msp_spi_onewire_reset();        // ① 帧前复位（低电平 ≥300 µs）

    __disable_irq();                // ② 数据位流期间不能被打断（见第六章）
    for (uint16_t i = 0; i < sizeof(buff); i++)   // 156 字节
        msp_spi_onewire_write_byte(buff[i]);
    __enable_irq();

    msp_spi_onewire_reset();        // ③ 帧尾复位 → 4 颗灯一起锁存
}
```

**为什么只有数据段关中断、复位段不用关**：
复位时中断只会让低电平**更长**（无害）；而数据段被插入一次几微秒的中断
→ 那一位的高电平被拉长 → `'0'` 被判成 `'1'` → **位翻转 / 颜色乱**。

### 5.3 分层与命名

| 文件 | 职责 |
| --- | --- |
| `Hardware/msp_spi/msp_spi_onewire.c/h` | **片上外设层**：SPI1 的初始化 + 单总线收发原语（`write_byte` / `read_byte` / `reset`） |
| `Driver/bsp_ws2812_rgb_leds/bsp_ws2812_rgb_leds.c/h` | **器件层**：编码表、`buff`、`set_color()` / `send()` |

**分层是清楚的**（片上 vs 片外），而且**编码表放在器件层、时钟参数放在片上层**，
两边各自都在文件头写明了"**编码与 SPI 时钟绑死，改时钟必须重算**"（这条注释写得非常好）。

**遗留的小问题**：

| 位置 | 问题 |
| --- | --- |
| `msp_spi_onewire.c` 里 `hard_spi_init()` 上面的注释 | 写成 "**IIC**初始化"、"**IIC**写入Nbyte"（从 `msp_iic.c` 复制过来忘改） |

## 六、★ "关中断"在这里为什么必须（与第 17 篇对照）

第 17 篇 §5.5 里，"传输期间 `__disable_irq()`"这个方案被**明确否掉了**，理由是：

> `delay_1us()` 依赖 **SysTick 中断**做递减，关中断 → `while (delay)` **死锁**。

而本篇却**必须**关中断。**差别在哪？**

| | 第 17 篇（软件 IIC 打断） | 本篇（WS2812 位流） |
| --- | --- | --- |
| 被保护的代码靠什么推进 | **靠 SysTick 中断递减**（`delay_1us`） | **靠 SPI 硬件移位** |
| 关中断会怎样 | 延时函数**死锁** ❌ | SPI 照常移位 ✅ |
| 所以 | **不能用关中断** → 改成"中断只置标志" | **必须用关中断** → 位流不能被插入 |

> **判据一句话**：**"关中断"只对"不依赖中断就能推进"的代码安全。**
> 依赖中断的（软件延时、软件 IIC/SPI 时序）→ 关中断 = 自杀；
> 靠硬件外设推进的（SPI 移位、DMA 搬运）→ 关中断是**最省事且正确**的保护。

**但也别把关中断当免费**：

| 代价 | 数值 / 说明 |
| --- | --- |
| 数据段关中断时长 | 156 字节 × 8 / 10.5 MHz = **118.9 µs** |
| 期间 SysTick 无法执行 | `delay_decrement()` 被推后；**若 SysTick 在此期间触发多次，挂起位只记一次 → 软件时基会少计**（建议实测 `get_us_cnt()` 的漂移） |
| 期间 EXTI（旋钮/按键/RTC 闹钟）被延后 | 118.9 µs 内到达的边沿要等发送结束才处理 |

**要彻底解决**（文档里也给了方向）：用 **TIMER + DMA** 让硬件自动发位流
（PWM 方式：用 DMA 把 CCR 值流式写进定时器），CPU 全程不参与 → 既不关中断、也不占 CPU。

## 七、引脚问题（"引脚冲突"要分两层看）

**软件层：全工程只有 `msp_spi_onewire.c` 碰 PB13/PB14/PB15** → 没有别的模块抢这三个脚。
**但硬件层有 3 处问题**（依据 `Doc/硬件信息汇总.md` 的 PCB 网表）：

| 引脚 | 原代码 | 板上实际网络 | 处理 |
| --- | --- | --- | --- |
| **PB13** | 配成 **SPI1_SCK（AF 推挽输出）** | `CAN_TX :: P3.25, TJA1050-1.2(TXD), U9.25` | ★ **删掉配置**：10.5 MHz 方波会被 TJA1050 直接搬到 CANH/CANL → **CAN 总线被垃圾帧占死** |
| **PB14** | 配成 SPI1_MISO | `PB14 :: P3.28`（只到排针，没接器件） | 删掉配置 |
| **PB15** | SPI1_MOSI ✅ | `DH :: P3.27, R6.1(10k→+5V), U6.2(DHT11), U9.27` | 保留；但 **`DH` 就是 DHT11 的数据脚** → **以后写 DHT11 驱动会和 WS2812 硬冲突** |

**这就是"引脚冲突要分两层查"的完整示例**：

1. **软件层**：全工程搜一遍这个引脚被谁初始化（`grep` 引脚宏名）；
2. **硬件层**：查 PCB 网表这个引脚在板上接了谁（**PB13 就这样被发现它通往 CAN 收发器的 TXD**）。

> **第二层是本篇的价值所在**：**WS2812 甚至连 SCK 都不需要**（它只有一根数据线），
> 但"顺手把 SCK 也配了"这个动作，**会把 10.5 MHz 的方波送进 CAN 收发器**。
> **外设不用某根线 ≠ 配它无害**——**"多余的配置"本身就是风险**。

### 练习题

1. **验算编码表**：用 Python 复刻 `ws2812_pack_byte()`，验证 `pack(0x00)` / `pack(0xFF)` 与代码注释里的自检值一致，并对 256 个值做往返校验。
