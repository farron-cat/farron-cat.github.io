## 知识点地图

```
独立按键驱动
├── 硬件接线            KEY1~KEY4 接 PC0~PC3，按下为低电平，内部上拉
├── 输入模式            GPIO_MODE_INPUT + GPIO_PUPD_PULLUP
├── 电平 / 事件         电平是「此刻状态」，事件是「状态发生了变化」
├── 边沿检测            对比上次电平 → 下降沿=按下，上升沿=松开
├── 状态存储（v1）      FlagStatus key_preSta[KEY_MAX]，4 个按键 4 个字节
├── 状态存储（v2）      uint8_t preStas 位图 + GET_STA/SET_HIGH/SET_LOW 宏，1 个字节
├── 回调机制            on_key_press / on_key_release（__weak 弱定义）
└── 扫描接口            bsp_key_scan(单个) 与 bsp_keys_scan(全部)
```

## 一、按键比 LED 难在哪

点灯是**输出**：你写什么，引脚就是什么，说一不二。
按键是**输入**：引脚的状态由**外面的手**决定，程序只能被动地「读」。

| | LED（输出） | 按键（输入） |
| --- | --- | --- |
| 数据方向 | 程序 → 引脚 | 引脚 → 程序 |
| 关键配置 | 输出模式 + 推挽 | **输入模式 + 上下拉** |
| 核心问题 | 初始化顺序、有效电平 | **悬空、抖动、边沿判断** |

**三个必须想清楚的问题**：

| 问题 | 本工程的答案 |
| --- | --- |
| 松开时引脚是几伏？ | 不接按键时引脚**悬空**，电压不确定 → 必须**内部上拉**，松开读到高电平 |
| 「按下」怎么判断？ | 按下时引脚被按键短到 GND，读到**低电平**（`RESET`） |
| 「按了一下」怎么表示？ | 不能只看电平！要对比**上次**电平，检测**变化**（边沿） |

## 二、硬件与概念

### 2.1 接线

```
        VCC
         │
        [内部上拉]  ← GPIO_PUPD_PULLUP，芯片内部约 40 kΩ
         │
PC0 ─────┼──── KEY1 ──── GND
```

- **不按时**：引脚被内部上拉电阻拉到高电平 → 读到 `SET`
- **按下时**：引脚直接接地，上拉电阻被短路 → 读到 `RESET`

```c
// 内部GPIO初始化函数
static void GPIO_config(rcu_periph_enum rcu, uint32_t port, uint32_t pin)
{
    rcu_periph_clock_enable(rcu);
    gpio_mode_set(port, GPIO_MODE_INPUT, GPIO_PUPD_PULLUP, pin);
}
```

> **对比核心板的 PA0**：那颗按键外部已经接了**下拉**电阻，按下为高电平，所以初始化时用的是 `GPIO_PUPD_NONE`——**上下拉由外部决定，内部就不要再开**（两套同时上拉/下拉会在按下时白白消耗电流，也可能改变门限）。第 06 篇的 `EXTI0` 就是这种情况。

### 2.2 参数表：沿用 LED 那一套

```c
// 抽取出按键引脚参数便于修改
KEY_PARAM keys[] = {
    {RCU_GPIOC, GPIOC, GPIO_PIN_0}, // KEY1
    {RCU_GPIOC, GPIOC, GPIO_PIN_1}, // KEY2
    {RCU_GPIOC, GPIOC, GPIO_PIN_2}, // KEY3
    {RCU_GPIOC, GPIOC, GPIO_PIN_3}, // KEY4
};
```

和 `LED_PARAM` 一模一样的结构体三件套（`rcu` / `port` / `pin`）。**这就是第 02 篇那个模式的价值**：写第二个驱动时可以直接照抄。

和 LED 不同的是：**这里的下标从 0 开始就是 KEY1**（LED 的 `[0]` 被总开关占了），所以 `KEY_NUM` 枚举也从 0 开始：

```c
typedef enum {
    KEY1 = 0,
    KEY2,
    KEY3,
    KEY4,
    KEY_MAX // KEY_MAX 放最后正好是按键总数4
} KEY_NUM;
```

**`KEY_MAX` 这个小技巧很实用**：它永远等于按键个数，代码里这么写就不用担心加按键时漏改数字：

```c
for (uint8_t i = 0; i < KEY_MAX; i++)   // 不用写 i < 4
{
    GPIO_config(keys[i].rcu, keys[i].port, keys[i].pin);
}
```

### 2.3 电平 vs 事件（本模块最重要的概念）

```c
// 获取按键状态
FlagStatus bsp_keys_get_state(KEY_NUM key)
{
    return gpio_input_bit_get(keys[key].port, keys[key].pin);
}
```

这个函数返回的是**电平**——「此刻按键是松着还是按着」。

但业务代码真正关心的是**事件**——「**刚刚**发生了一次按下 / 松开」：

| | 电平（Level） | 事件（Event） |
| --- | --- | --- |
| 回答的问题 | 现在按着吗？ | 刚发生了什么？ |
| 例子 | `RESET` | 「按下了一次」 |
| 长按 3 秒会发生什么 | 一直读到 `RESET` | **只报 1 次按下**（边沿只出现一次） |
| 主循环调 100 次 | 读到 100 次电平 | 只有真正的边沿那一次才返回事件 |

后者才是应用层想要的东西。这也解释了枚举为什么这样定义：

```c
typedef enum {
    KEY_EVENT_NONE = 0, // 无事件
    KEY_EVENT_PRESSED,  // 下降沿 按下
    KEY_EVENT_RELEASED  // 上升沿 松开
} KEY_EVENT;
```

`NONE = 0` 放在第一个，好处是「没有按键动作」时返回 0，用 `if (event)` 就能判断，不用写比较。

## 三、提交 `40817c5`：第一版（数组存状态）

**提交信息**：`[更新] 封装KEY独立按键，抽取KEY引脚参数便于适配，使用key_preSta数组记录上一次电平，根据当前和上次电平返回KEY_EVENT按键事件枚举`

核心就一句话：**记住上一次的电平，和这一次比**。

```c
// 保存每个按键上一次的电平状态，默认为高电平
static FlagStatus key_preSta[KEY_MAX] = {SET, SET, SET, SET};

// 扫描按键，返回事件枚举
KEY_EVENT bsp_keys_scan(KEY_NUM key)
{
    FlagStatus curSta = bsp_keys_get_state(key);
    KEY_EVENT event = KEY_EVENT_NONE;

    // 下降沿 按下
    if (key_preSta[key] == SET && curSta == RESET)
    {
        event = KEY_EVENT_PRESSED;
        key_preSta[key] = curSta;      // 更新历史状态
    }
    // 上升沿 松开
    else if (key_preSta[key] == RESET && curSta == SET)
    {
        event = KEY_EVENT_RELEASED;
        key_preSta[key] = curSta;
    }

    return event;
}
```

### 3.1 关键点：`key_preSta` 必须只在边沿处更新

很多人会这样写（错）：

```c
key_preSta[key] = curSta;      // ← 无论有没有事件，每次扫描都更新
if (key_preSta[key] == SET && curSta == RESET) ...
```

这样写**永远不会触发**，因为电平刚被更新成当前值，条件立刻不成立。

**正确写法有两条路**：

| 写法 | 说明 |
| --- | --- |
| 本工程的做法：**只在边沿发生时更新** | 状态变化本身就是事件，更新即记录 |
| 另一种：每次扫描都更新，但**先把旧值存到局部变量**再比较 | 适用于需要「任意时刻都知道上次电平」的场合 |

本项目选的是一种，**两种都对，但要保持前后一致**。

### 3.2 三个初始值为什么是 `SET`

```c
static FlagStatus key_preSta[KEY_MAX] = {SET, SET, SET, SET};
```

因为按键**松手时是高电平**。初始假设「都是松开的」，这样如果上电时手正好按着，第一次扫描会正确识别成「按下」事件；如果初始值写成 `RESET`，上电时手按着反而检测不到，松手时还会误报一次「按下」。

### 3.3 这一版的缺点

| 缺点 | 说明 |
| --- | --- |
| 占 4 个字节存 4 个 bit 的信息 | `FlagStatus` 是枚举（底层 `int`），一个按键一个变量太浪费 |
| 每加一个按键要手动改初始值列表 | `{SET, SET, SET, SET}` 得跟着数 |
| 应用层必须自己判断事件类型 | `if (event == KEY_EVENT_PRESSED) ...` 写起来啰嗦，而且**每个使用者都要写一遍** |

## 四、提交 `9daeced`：加回调 + 位图压缩

**提交信息**：`[优化] 优化bsp_keys，添加按下松开回调函数处理方式。优化preStas空间占用`

这次提交同时解决了上面三个缺点。改动分两块：**状态存储**和**对外接口**。

### 4.1 状态存储：4 字节 → 1 字节

```c
// 用一个字节的位图保存所有按键的历史状态，0xFF 表示默认高电平
static uint8_t preStas = 0xFF;

#define GET_STA(i) ((preStas >> i) & 0x01)
#define SET_HIGH(i) (preStas |= (0x01 << i))
#define SET_LOW(i) (preStas &= ~(0x01 << i))
```

**位图长这样**（1 个字节 = 8 个 bit，够存 8 个按键）：

```
preStas = 0xFF = 0b 1111 1111
                     │││└─ bit0 = KEY1 的历史电平（1=松开/高电平）
                     ││└── bit1 = KEY2
                     │└─── bit2 = KEY3
                     └──── bit3 = KEY4
```

| 宏 | 展开 | 作用 |
| --- | --- | --- |
| `GET_STA(i)` | `(preStas >> i) & 0x01` | 把第 i 位挪到最低位再取出来 → 读状态 |
| `SET_HIGH(i)` | `preStas \|= (0x01 << i)` | 把第 i 位置 1 → 记成「松开」 |
| `SET_LOW(i)` | `preStas &= ~(0x01 << i)` | 把第 i 位清 0 → 记成「按下」 |

**为什么 `0xFF` 是默认值？** 8 个 bit 全 1，正好表示「所有按键都是松开的（高电平）」，不需要再写 `{SET, SET, SET, SET}` 这种列表——**加按键也不用改这一行**。

> **注意一个命名细节**：宏名是 `SET_HIGH(i)` 而不是 `SET_PRESSED(i)`，意思是「把第 i 位记成高电平」。**它描述的是电平，不是按键动作**——因为按下其实是低电平，叫 `SET_PRESSED` 反而容易绕晕。

### 4.2 回调：让驱动层不认识应用层

```c
#ifndef __weak
#define __weak __attribute__((weak)) // GCC / armclang
#endif

// 按键按下回调
// 弱引用  可以被其他文件重定义
__weak void on_key_press(KEY_NUM key)
{
}

// 按键松开回调
__weak void on_key_release(KEY_NUM key)
{
}
```

配套在头文件里声明：

```c
// 按键按下回调
extern void on_key_press(KEY_NUM key);

// 按键松开回调
extern void on_key_release(KEY_NUM key);
```

**`__weak`（弱符号）到底做了什么？**

```
链接器看到两个同名的 on_key_press：
  ├── bsp_keys.c 里的（__weak，弱）  ← 有它程序也能过，为空实现
  └── main.c   里的（普通，强）      ← 有它就优先用这个
链接规则：有强符号就用强符号，没有就用弱符号
```

**这套机制换来了什么？**

| 谁 | 职责 | 变化频率 |
| --- | --- | --- |
| `bsp_keys.c`（驱动） | 扫描引脚、判边沿、调回调 | **几乎不变** |
| `main.c`（应用） | 决定「按 KEY1 干什么」 | 天天改 |

驱动层不需要 `#include "main.h"`，也不需要知道 KEY1 是启动充电还是点亮灯——**依赖方向反过来了：应用依赖驱动，驱动不认识应用**。这就是「回调」在裸机工程里的作用。

### 4.3 扫描函数：一次调用 vs 一次扫全部

```c
// 扫描按键，返回事件枚举
KEY_EVENT bsp_key_scan(KEY_NUM key)      // 注意：单数 key
{
    FlagStatus curSta = bsp_keys_get_state(key);
    KEY_EVENT event = KEY_EVENT_NONE;

    // 下降沿 按下
    if (GET_STA(key) == SET && curSta == RESET)
    {
        on_key_press(key);                // ← 新增：自动触发回调
        event = KEY_EVENT_PRESSED;
        SET_LOW(key);
    }
    // 上升沿 松开
    else if (GET_STA(key) == RESET && curSta == SET)
    {
        on_key_release(key);
        event = KEY_EVENT_RELEASED;
        SET_HIGH(key);
    }

    return event;
}

void bsp_keys_scan()
{
    bsp_key_scan(KEY1);
    bsp_key_scan(KEY2);
    bsp_key_scan(KEY3);
    bsp_key_scan(KEY4);
}
```

**两个细节值得单独说**：

**① 为什么同时保留「返回值」和「回调」两种方式？**
因为这两种使用场景都真实存在：

```c
// 场景 A：业务上需要立刻知道结果（比如做组合键）→ 用返回值
if (bsp_key_scan(KEY1) == KEY_EVENT_PRESSED) { ... }

// 场景 B：主循环里无脑刷一遍，动作写在回调里 → 用 bsp_keys_scan()
while (1) { bsp_keys_scan(); }      // 本工程 main.c 就是这么用的
```

**② 双数/单数的命名**：`bsp_keys_scan()` 扫全部，`bsp_key_scan(key)` 扫单个。这个命名是**后续 `1aee946` 提交才调整的**——原来单数复数都是 `bsp_keys_scan`，一个带参数一个不带，靠参数区分，容易看错。改成单数 `bsp_key_scan(KEY_NUM)` 之后，看名字就知道粒度。

> **顺便记住这个坑**：C 语言不支持函数重载，同名函数要么参数不同要么直接报错。用「单数/复数」区分粒度是个实用约定（`bsp_leds_open_all()` 那套也是一样的思路）。

### 4.4 应用层怎么写（真实例子）

`1aee946` 提交里，`main.c` 就写了这么一个回调：

```c
// 按键按下回调
void on_key_press(KEY_NUM key)
{
    if (key == KEY1)
    {
        bsp_battery_flow_start();     // KEY1：开始充电
    }
    else if (key == KEY2)
    {
        bsp_battery_flow_update();    // KEY2：电量 +1
    }
    else if (key == KEY3)
    {
        bsp_battery_flow_stop();      // KEY3：停止充电
    }
}
```

**应用层的写法极其干净**：它只表达「按哪个键 → 干什么」，里面**一个引脚号都没有**。而这个业务（充电流水灯）的完整实现，就是第 05 篇要讲的内容。

## 五、最终代码速查

```c
// 初始化：使能 4 个按键引脚，输入 + 内部上拉
void bsp_keys_config();

// 读电平：SET = 松开(高)，RESET = 按下(低)
FlagStatus bsp_keys_get_state(KEY_NUM key);

// 扫单个按键，返回本轮的按键事件
KEY_EVENT bsp_key_scan(KEY_NUM key);

// 扫全部 4 个按键（内部依次调用 bsp_key_scan）
void bsp_keys_scan();

// 弱回调，由应用层重定义
extern void on_key_press(KEY_NUM key);
extern void on_key_release(KEY_NUM key);
```

**参数速查表**：

| 项目 | 值 |
| --- | --- |
| 引脚 | KEY1~KEY4 = PC0~PC3 |
| 模式 | `GPIO_MODE_INPUT` |
| 上下拉 | `GPIO_PUPD_PULLUP`（内部上拉） |
| 按下电平 | 低（`RESET`） |
| 松开电平 | 高（`SET`） |
| 历史状态存储 | `uint8_t preStas`，初值 `0xFF` |
| 按键总数 | `KEY_MAX`（= 4） |

**版本对照**：

| 项目 | `40817c5`（v1） | `9daeced`（v2） |
| --- | --- | --- |
| 历史状态 | `FlagStatus key_preSta[KEY_MAX]`（4 字节） | `uint8_t preStas`（1 字节） |
| 状态读写 | 数组下标 | `GET_STA`/`SET_HIGH`/`SET_LOW` 宏 |
| 应用层通知 | 只能靠返回值 | 返回值 + `on_key_press/release` 回调 |
| 扫描接口 | `bsp_keys_scan(KEY_NUM)` | `bsp_key_scan(KEY_NUM)` + `bsp_keys_scan()` |
| main.c 里的变化 | 拿到事件后自己 `if` 判断 | 回调里直接写业务，主循环只调 `bsp_keys_scan()` |

## 六、还没做的两件事（引出后续提交）

### 6.1 消抖

真实按键在按下/松开的瞬间，金属触点会弹跳几毫秒，产生**一串快速的通断**。如果每 20 ms 扫一次，绝大多数抖动会被自然过滤掉——**本工程就是用「扫描周期」当消抖的**。

但如果用**中断**读按键，抖动就会变成一次按下触发好几次中断。所以消抖被放到了 `00d0615`（EXTI）那次提交里，做法是「时间戳 + 电平去重」，见第 06 篇。

### 6.2 阻塞与扫描周期

按键扫描必须**周期性**调用，否则会漏事件。本工程最初是这么写的：

```c
uint8_t cnt = 0U;
while (1)
{
    bsp_keys_scan();
}
```

无延时地空转，扫描频率极高——**能工作，但 CPU 100% 在扫按键**。后续 `1aee946` 之后变成「20 ms 扫一次 + 500 ms 处理一次状态机」的调度结构，这部分在第 05 篇展开。

## 七、排查清单

| 现象 | 优先检查 |
| --- | --- |
| 按键完全没反应 | 引脚号/端口时钟写错；接了外部下拉却开了内部上拉 |
| 按键随机触发、手一碰就触发 | 引脚悬空——忘了开内部上拉；或该用外部电路的地方没接 |
| 按一下，触发了十几次 | 在**中断**里读按键但没消抖；或扫描周期远大于抖动时间 |
| 长按一直触发「按下」 | 判成了电平而不是边沿；检查 `preStas` 是不是在每次扫描都被无条件更新 |
| 上电瞬间误报一次按下 | `preStas` 初值写错（应为 `0xFF`），或上电时手按着键 |
| 松开时误报「按下」 | 按下/松开对应的高低电平搞反了（本板：按下=低） |
| 加了第 5 个按键后数组越界 | `preStas` 是 8 位位图，最多 8 个按键；超过要用 `uint16_t` |
| 应用层改了业务逻辑，驱动要跟着改 | 说明没走回调——应该重定义 `on_key_press` 而不是改 `bsp_keys.c` |
| 回调写了但没被调用 | 函数名拼错（弱符号会被静默忽略）；或漏了 `bsp_keys_scan()` 的周期调用 |

## 八、自测题

1. 「电平」和「事件」的区别是什么？为什么应用层更该用事件？长按 3 秒时两者分别表现如何？
2. `preStas` 为什么初值必须是 `0xFF` 而不是 `0x00`？分别会导致什么现象？
3. 为什么 `key_preSta` 只在检测到边沿时才更新？如果每次扫描都更新会怎样？
4. `GET_STA(2)` 展开后是什么？如果 `preStas = 0xFB`，它返回什么？表示 KEY3 处于什么状态？
5. `__weak` 弱符号的链接规则是什么？如果不加 `__weak`，只写一个空的 `on_key_press` 会出什么问题？
6. 用了 `1` 个字节存 4 个按键状态，最多能支持几个按键？要支持 20 个该怎么办？
7. 本工程单靠「扫描周期」当消抖，但如果按键扫描被其他任务阻塞了 500 ms，会发生什么？（提示：第 05 篇的阻塞版流水灯）
8. 为什么 `bsp_keys_scan()`（扫全部）和 `bsp_key_scan()`（扫单个）要起不同的名字？

## 九、练习题

1. 给按键驱动增加「长按」事件：按住超过 1 秒触发 `KEY_EVENT_LONG_PRESSED`（提示：用 `get_us_cnt()` 记录按下时刻，注意第 06 篇讲的「无符号减法」）。
2. 增加「双击」检测：300 ms 内连续两次按下视为双击。
3. 把 `on_key_release` 用起来：按下 KEY1 点亮 LED1、松开熄灭（原来注释里那句 `bsp_leds_close(key + 1)` 的思路）。
4. 把 `preStas` 换成 `uint16_t`，支持 8 个以上按键，并思考 `GET_STA` 宏要不要跟着改。
