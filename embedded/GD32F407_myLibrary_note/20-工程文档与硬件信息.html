一、为什么给文档单独开一篇 ​

前面 19 篇讲的全是"怎么驱动外设"。这一篇讲的是另一个维度：你怎么知道该驱动什么、接在哪个脚上。

嵌入式开发里有类问题特别费时间：

现象：代码逻辑看着对，编译通过，烧进去就是不工作
原因：引脚不对 / 冲突 / 悬空 / 极性反了
排查：翻原理图 → 翻 PCB → 手工对一遍 → 才发现问题
1
2
3

这类问题的成本几乎全在"查资料"上，而不是"改代码"上。所以：

把硬件信息整理成"可检索的文本"，是这个工程做的一件很聪明的事。

它相当于给项目加了一份**"硬件 API 文档"**——写驱动前先查一遍，能省掉大量试错。

二、e2d7adf：文档是怎么生成的 ​

提交信息：[文档]: 使用jlceda-mcp查看原理图与pcb生成的文档（+862 行，两个 md 文件）

生成方式：工具通过 嘉立创 EDA（JLCEDA）的接口读取工程文件，把原理图 + PCB 网表转成 Markdown 文档。

读取优先级（文档里写得很清楚）：

① PCB 焊盘级网表（pcb_PrimitiveComponent.pads.net）  ← 权威
② 用原理图的 pinName 做第二次确认
③ 原理图 sch_Net.* 在本环境返回空、getNetlist() 超时，且**原理图与 PCB 网络名不同步**
⇒ 结论：以 PCB 为准

4

这份文档在"可信度"上的自我标注很值得学：

做法说明
标明数据来源"所有引脚结论均来自 PCB 焊盘级网表"
标明局限"原理图与 PCB 不同步，建议以 PCB 为准"
标明推断与实测的区别"LED 极性的判断是基于驱动拓扑推导的……如需 100% 断言，可用万用表在实物上验一次"
标明没做什么"只读取了数据、切换了活动文档，没有修改任何原理图/PCB"

这是"技术文档该有的样子"：结论 + 依据 + 局限 + 待验证项。 反例就是本书里反复提到的那些"注释与代码不符"（第 07 篇软 PWM、第 15 篇 I2C 延时）——没有标依据和局限的结论，时间一长就没人敢信。

处理建议：改成 GPIO_PUPD_PULLUP（或 PULLDOWN），并把触发改成单边沿；或确认排针确实接了外部信号。

这一条正好和第 03 篇的按键对照：那里 PC0~PC3 用了 GPIO_PUPD_PULLUP（因为确认接 GND），而 PA0 用的是 GPIO_PUPD_NONE（注释写"外部接了下拉"）——但硬件核对显示 PA0 并没有外部下拉。注释里的假设是错的，而代码跟着这个错误假设走。教训：注释里的"外部已经接了下拉"这类断言，必须对着原理图核实（第 01 篇讲过"注释可能是错的"，这是又一个实例）。

这类 bug 的通用特征：复制改漏了"定时器名"。定时器配置代码有 6~7 行，每行都带定时器名，漏改一两个不会编译报错（TIMER1 是合法标识符），只会"没反应"。 这就是第 07 篇反复强调的那个坑："引脚 / 通道 / AF / 定时器号 要成套核对"——这次漏的是"定时器号"。 防呆办法：把定时器做成参数（像第 04 篇串口句柄那样），一套参数只写错一次；或者干脆用 #define/宏把 TIMER9 抽出来，只在一个地方写。
