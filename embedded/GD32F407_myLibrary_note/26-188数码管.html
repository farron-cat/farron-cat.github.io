学习目标 ​

  1. 说清"5 个 IO 驱动 18 个发光段"的原理，以及为什么每次只能点亮一组、其余引脚必须置高阻。
  2. 会算这个显示器的刷新率与占空比（1 ms/步 × 5 步）。
  3. 看懂 leds_status 位图与引脚动作之间的对应关系（位图 → 段 → 引脚的三级映射）。
  4. 记住本模块的隐式约定是怎么被消除的（"先 clear 再 set" → 收进 set_num 内部）。
  5. 说清它与**矩阵键盘（PE9~PE15）**的引脚冲突及后果。

一、它是什么 ​

"188" 这个名字描述的是它能显示的字形：1 8 8 —— 也就是三位，其中：

  • 第一位只能显示 "1"（硬件上只有两段：B1、C1，即 "1" 的两根竖笔）；
  • 后两位是完整的 7 段（A2~G2、A3~G3）；
  • 外加 两个图标：K1、K2（常见是"充电/百分比"之类）。

所以可显示的数值范围是 0 ~ 199（第一位只有 0 或 1），这和 bsp_188_leds_set_num() 里那句 if (num > 199) return; 完全对应。

段数清点（这是理解后面映射表的关键）：

组段位数
第一位B1、C12
第二位A2、B2、C2、D2、E2、F2、G27
第三位A3、B3、C3、D3、E3、F3、G37
图标K1、K22
合计18

可只有 5 根 GPIO（PIN1~PIN5）：PE15、PE13、PE11、PE9、PE7。

正常思路：18 个段至少 18 根线（共阳）或 5+7=12 根（扫描）。 这里用的是更狠的一招：5 根线互相充当公共端和段线，用"时间 × 引脚配对"来区分 18 个段—— 5 根线两两组合有 5×4 = 20 种有向配对，刚好够 18 个段用。

二、★ 5 根线怎么点 18 个段 ​

要点：

  1. 位图 = 帧缓冲：上层只改位图（"我要显示 123"），下层（扫描）负责把位图"翻译"成引脚动作。上层和硬件完全解耦——这是第 09 篇（74HC595 数码管）已经确立的模式。
  2. A2 恰好比 A3 高 7 位，于是十位的码表可以直接由个位码表左移 7 位得到（提交里把重复的 ten_digit_nums[] 整段注释掉了）：
c
// 优化掉 十位数字码表 由个位<<7得到
leds_status |= (one_digit_nums[num % 100 / 10] << 7);

⚠️ 这里有个容易被误会的细节：one_digit_nums[] 是 uint8_t，但 one_digit_nums[x] << 7 不会截断—— C 在移位前会把它整型提升为 int，所以 0x7F << 7 = 0x3F80 完整保留。 如果写成 (uint16_t)(one_digit_nums[x]) << 7 结果一样，但若反过来先截断再移位就会全错。"整型提升救了这个技巧"。

2.2 5 步扫描表（代码的核心） ​

每个扫描步长做两件事：① 让某一根引脚输出高电平（当"公共端"）② 把需要亮的段的另一根引脚拉低；其余引脚全部置为高阻（输入）。

步公共端（输出高）拉低的引脚 → 对应段
0PIN1(PE15)PIN2→A3、PIN3→C3、PIN4→E3
1PIN2(PE13)PIN1→B3、PIN3→A2、PIN4→C1、PIN5→K2
2PIN3(PE11)PIN1→D3、PIN2→B2、PIN4→B1、PIN5→K1
3PIN4(PE9)PIN1→F3、PIN2→D2、PIN3→C2
4PIN5(PE7)PIN1→G3、PIN2→E2、PIN3→F2、PIN4→G2

把这张表"反过来读"就是每个段的两根引脚，例如：

A3（个位 a 段）= (PIN1 高, PIN2 低) → 只在第 0 步点亮
B3（个位 b 段）= (PIN2 高, PIN1 低) → 只在第 1 步点亮
B1（百位 "1"）= (PIN3 高, PIN4 低) → 只在第 2 步点亮
K2（图标）    = (PIN2 高, PIN5 低) → 只在第 1 步点亮

2.3 为什么"其余引脚必须高阻" ​

因为任意一根输出高的线 和 任意一根输出低的线 之间，都会亮一颗 LED。 如果第 0 步把 PIN3、PIN4 也都主动拉低（而不是只拉该亮的段、其余高阻）， 那么 (PIN1 高, PIN3 低)、(PIN1 高, PIN4 低) 这些本不该亮的配对就会跟着亮——这叫"鬼影"（ghosting）。

所以这条规则必须记住：

每一步：1 根输出高 + 若干根输出低（只拉需要亮的）+ 其余全部高阻。 高阻（GPIO_MODE_INPUT + GPIO_PUPD_NONE）就是"我退出这条线，别把我算进去"。

PIN_ALL_IN 的写法也就有了意义——每步开头先让所有引脚"退场"，再点名让两根上场：

c
#define PIN_IN(pin)                                                                         \
    do                                                                                      \
    {                                                                                       \
        gpio_mode_set(pins[pin].port, GPIO_MODE_INPUT, GPIO_PUPD_NONE, pins[pin].gpio_pin); \
    } while (0)

#define PIN_ALL_IN    \
    do                \
    {                 \
        PIN_IN(PIN1); PIN_IN(PIN2); PIN_IN(PIN3); PIN_IN(PIN4); PIN_IN(PIN5); \
    } while (0)

#define PIN_OUT(pin, val)                                                                    \
    do                                                                                       \
    {                                                                                        \
        gpio_mode_set(pins[pin].port, GPIO_MODE_OUTPUT, GPIO_PUPD_NONE, pins[pin].gpio_pin); \
        gpio_bit_write(pins[pin].port, pins[pin].gpio_pin, val);                             \
    } while (0)

do { } while (0) 的来历：第一次提交（f6129e4）里 PIN_ALL_IN 是一串裸宏（用 ; 分隔）， 一旦写成 if (x) PIN_ALL_IN; else ... 就会展开成两条语句 → else 找不到 if → 编译错误或逻辑错乱。 c630553 把它全部包进 do { } while (0)，这才是宏的正确写法。 这类"看起来多余的包装"是 C 语言里少数必须做的防御。（本项目共出现 3 处：PIN_IN / PIN_ALL_IN / PIN_OUT。）

3.2 c630553（10-10 16:40）：码表 + 扫描 + SysTick 节拍 ​

这一版把 .c 从 43 行扩到约 260 行，做了 4 件事：

动作内容
① 加入码表one_digit_nums[10]（0~9 的 7 段码），十位表用 <<7 复用
② 加 show()（阻塞版）5 步 + 每步 delay_1ms(1)，整帧 5 ms
③ 加 scan()（非阻塞版）一次只走一"步"，用 static uint8_t scan_step 记忆状态
④ 挂到 SysTickgd32f4xx_it.c 里每 1 ms 调一次 bsp_188_leds_scan()
⑤ 宏加 do{}while(0)见 §2.3
⑥ 删掉 bsp_188_leds_test()临时验证代码不留在工程里（好习惯）
⑦ 把 clear 收进 set_num见 §3.3

gd32f4xx_it.c 的改动（这是本工程第一次把"用户代码"放进 SysTick）：

c
void SysTick_Handler(void)
{
    static uint16_t div = 0;

    delay_decrement();               // 原有的 1 µs 递减（第 01 篇）

    // 每1ms扫描一次188数码管
    if (++div >= 1000)               // 1 µs × 1000 = 1 ms
    {
        div = 0;
        bsp_188_leds_scan();
    }
}

刷新的账要算清：SysTick 是 1 µs 节拍 → div 数到 1000 才调用一次 → 1 ms 走一步； 一帧 5 步 → 帧周期 5 ms，刷新率 200 Hz，每个段的占空比 1/5 = 20%。

200 Hz 远高于人眼闪烁临界（约 50 Hz，见第 13 篇"视觉暂留 41.7 ms"），所以不闪； 20% 占空比意味着峰值电流要够（5 段平均分摊），亮度也比直流驱动低——这是"省引脚"要付的代价。

这次提交还有两个看点：

变化为什么重要
clear() 从 leds_status = 0 改成 &= K1 | K2清数字不该连带清图标——一次"作用范围"的修正（和第 05 篇 stoping_cnt 被两个状态共用是同一类问题）

这一版其实是一个"接口契约"的经典修复： set_num() 既然语义是"让显示器显示 num"，那么"清掉旧的"就是它份内的事。 让调用方必须先 clear() 是把内部状态泄漏给了使用者——这种"得记住先调 A 再调 B"的约定， 一旦漏掉就会出 bug（比如显示 "123" 后改成 "7"，会变成 "723"）。 凡是"必须先做 X 才能调 Y"的约定，都应该想办法塞进 Y 里面。

注意它没有调用 gpio_mode_set() —— 这是故意的：

  • GPIO 复位后的默认模式是输入（高阻），也就是我们想要的"退场"状态；

三个技巧一次说完：

代码作用等价写法
num % 100 / 10取十位num / 10 % 10（对本例都行，前者在 >99 时也正确）
one_digit_nums[x] << 7个位码表当十位码表用另写一张 ten_digit_nums[10]（表更大、易写错）
if (num > 9) / if (num > 99)前导零消隐显示 "007" 而不是 "7"，一般不是想要的

为什么 num > 199 要 return 而不是钳位：函数是"设置"语义，参数非法时不动状态是合理约定； 但代价是调用方拿到的是一个"没有反应"的函数——所以 main.c 里主动做了钳位（§3.3）。 "函数保持沉默、调用方负责夹紧"是常见的分工，但一定要在头文件注释里写清楚。

五、扫描节拍：谁来调用 scan ​

本模块给了两个入口，用途完全不同：

bsp_188_leds_show()bsp_188_leds_scan()
一次调用做什么一整帧（5 步）一步
是否阻塞是：5 × delay_1ms(1) = 5 ms否：纯 GPIO 操作，约几 µs
谁调用自测/独占场景SysTick_Handler，每 1 ms 一次
适合场景"我就想显示一下，别的不干"主循环还有别的活（读时间、刷 OLED、读 NTC）

这和第 09 篇（74HC595 数码管）、第 05 篇（充电流水灯）的结论完全一致：

只要"显示"要和"业务"并行，就必须把"一整帧"拆成"一步一次"。 而拆开之后必须有个固定节拍来推进它——本工程用过两种节拍源： ① 定时器中断（第 07/09 篇的 TIMER）；② SysTick（本篇）。

把用户代码放进 SysTick_Handler 的代价（值得知道的权衡）：

优点代价
节拍天然精确（1 µs 基准，软件分频）SysTick 优先级固定为最高（异常号 -1），会抢占所有外设中断
不用配定时器、不占额外外设Handler 里做的事越多，delay_1us() 的时基精度越差（delay_decrement() 被推后）
与 delay_1ms/1us 共用同一个计数器一旦将来在 scan() 里加入耗时操作（IIC/printf），会连锁影响所有延时

本篇的 scan() 只做 GPIO 操作，只有几微秒，所以放在 SysTick 里是安全的； 而 c630553 之前的 show() 里有 delay_1ms()，绝对不能放进中断（会死锁式地卡死 SysTick 时基）。 这也正是第 12 篇"中断里不要做耗时操作"的同一条规则的又一次体现。

七、⚠️ 引脚复用：和矩阵键盘抢线 ​

把代码里的 5 个引脚，对照 Doc/硬件信息汇总.md 的权威引脚表：

代码里MCU 引脚板上的网络名板上连到哪里
PIN1PE15KCOL_4矩阵键盘第 4 列（SW4/8/12/16）
PIN2PE13KCOL_2矩阵键盘第 2 列（SW2/6/10/14）
PIN3PE11KROW_4矩阵键盘第 4 行（SW13~SW16）
PIN4PE9KROW_2矩阵键盘第 2 行（SW5~SW8）
PIN5PE7PE7P3.13 排针（板上空闲）

也就是说：188 数码管用掉了 4 根"矩阵键盘的行列线" + 1 根空闲脚。这带来三个必须知道的结论：

  1. 188 数码管是外接模块（插在 P3 排针上），因为板上 BOM 里的数码管 LED11/LED12 是另一套（12 脚 4 位 7 段，经 74HC595 → PD0/PD1/PD4）。 —— 两种数码管、两种驱动方式，代码里都在，别搞混（第 09 篇讲的是 74HC595 那套）。
  2. 当 188 模块在用的时候，矩阵键盘不能同时扫描： 两边都在"驱动同一批引脚"，会互相干扰（显示乱、读键错乱），严重时一边输出高、一边输出低形成短路。

    目前工程里矩阵键盘在未合并的 keypad 分支（第 10 篇），当前不会同时跑——但只要将来合并进来，就必须做"二选一"或"分时复用"。

  3. 按下键盘按键 = 把两根线短接：即使键盘模块没在跑，物理按键按下也会把 KROW_x 和 KCOL_y 短接。 如果此刻 188 正在扫描，就会出现"某根公共端把电流灌进另一根"的情况 → 段亮度异常。 实际使用中要避开按键动作与显示刷新重叠，或者干脆接受"按键时显示微抖"。

这正是第 20 篇"代码 ↔ 硬件 校验"的价值所在：只看代码是发现不了这个冲突的， 必须把"代码用哪些引脚"和"板上这些引脚接到了什么"对起来看。 （顺带一提：Doc/引脚检查测试.md 的"三个必须处理的问题"里没有这一条——它是在 188 模块写出来之后才产生的新冲突。）

三点结论（比"改引脚"更重要）：

  1. 笔记里"只看代码发现不了"的那条判断是对的——作者自己也把"不能同时使用"写进了提交信息；
  2. 代码里留一条解释（// 矩阵键盘扫描 与188数码管引脚冲突，不能同时使用）比"留一行注释掉的调用"有价值得多， 它让两年后读代码的人（包括自己）立刻明白"为什么这里被注掉了"；
  3. "合了但先不启用"是一种成熟的合并策略：c4a098e 把键盘驱动合进 main（代码入库、随时可用）， 但把调用点关掉——"合并"和"启用"是两件独立的事（第 10 篇 §4.7 有完整记录）。

所以本篇 §7 的结论升级为：这个模块不是"不能和键盘同时用"，而是"必须显式二选一，并把选择写进代码注释里"。
