学习目标 ​

  1. 说清"3 个按键共用 1 根 ADC"的原理，并会算各键对应的 ADC 码值与安全间隔。
  2. 说出中值滤波为什么比"直接平均"或"取一次"更适合按键采样。
  3. 能画出 7 状态机的完整迁移图，并解释"为什么单击要等到双击等待超时才回调"。
  4. 能独立找出并修复第七章那个越界 bug，并说清它为什么在 -Wall 下不报警。
  5. 理解 __weak 回调在本工程中的角色（默认实现 = 打印，应用层可覆盖）。

一、原理：一根 ADC 线接多个按键 ​

1.1 电路：电阻分压"梯子" ​

  • 都不按 → ADC 读到接近满量程；
  • 按 SW1 → 下臂变成 R1 → 分压得到一个特定电压；
  • 按 SW2 / SW3 → 下臂是 R2 / R3 → 另两个特定电压。

核心思想：用"不同的电阻组合"给每个按键分配一个"电压指纹"，MCU 只要读一次 ADC，就知道按的是谁。 代价是：不能同时按两个（会得到第三个电压，或者落在某个键的窗口里）。

1.2 本工程的三个"指纹" ​

代码里写死了三个 ADC 码值（12 位，0~4095）：

#define KEY2_PRESS_ENCODE 2043
#define KEY3_PRESS_ENCODE 3135

KEY220431.646 V1098

（都不按）≈40953.3 V960

判定用"绝对差 < 20"：

c
if (abs(encode - key->press_encode) < 20)   // 认为这个键被按下
1

20 这个窗口对应电压 $\pm 20 \times 3.3/4096 \approx \pm 16\ \text{mV}$ —— 很紧。

三个数的间隔都在 1000 码以上（约 0.8 V），而判定窗口只有 ±20 码， 所以"误判成隔壁键"几乎不可能；真正会出问题的是"读到的值根本不在任何一个窗口里" （电阻误差、接触电阻、供电波动）→ 表现就是"按了没反应"（第八章第 1 条）。

1.3 为什么值得这么做 ​

3 个独立 GPIO 按键1 个 ADC + 3 个电阻
占用引脚31
需要外部上拉3 个（或内部上拉）0（内部有分压网络）
同时按下支持不支持
成本低多 3 个电阻（或买现成模块）
抗干扰强（数字信号）弱（模拟量，受电源纹波影响）

结论：引脚紧张 + 不需要同时按 的场合才用（遥控器、小家电面板最常见）。 本工程用它是因为：188 数码管 + 矩阵键盘 + 旋转编码器已经把 PE 口抢光了（第 26/10/29 篇）。

二、为什么要"中值滤波" ​

第一次提交（0d729ce）只做了一件事：把电压稳定地测出来——用了一个 10 次采样的滑窗，去掉最大值和最小值再平均：

c
// 0d729ce 的 bsp_adkey_scan()：中值滤波 + 打印电压
static uint8_t  sample_cnt = 0;
uint16_t sample_sum = 0, sample_max = 0, sample_min = 4095;

void bsp_adkey_scan(void)
{
    uint16_t encode = msp_adc_get(3);
    sample_sum += encode;
    if (encode > sample_max) sample_max = encode;
    if (encode < sample_min) sample_min = encode;

    if (++sample_cnt == 10)
    {
        sample_cnt = 0;
        encode = (sample_sum - sample_max - sample_min) / 8;   // 去掉一个最大、一个最小，除以 8
        float vol = encode * VREF / 4096;
        printf("vol:%f\n", vol);
        sample_sum = 0; sample_max = 0; sample_min = 4095;
    }
}

三个值得说的点：

点说明
为什么去掉最大最小模拟量最容易受单次尖峰影响（PWM 开关、别的 GPIO 翻转、电源纹波）。掐头去尾比"纯平均"更抗脉冲噪声——这就是**"中值+均值"的简化版**
除以 8，不是 10去掉 2 个样本后剩 8 个 ✓（这个 8 是"10 减 2"算出来的，不是凑的）
数据来源msp_adc_get(3) —— 第 27 篇的 ADC 序列里第 4 个通道（ADC_CHANNEL_8 = PB0），正是这一次提交给 msp_adc 加了第 4 通道

注意：0d729ce 只在 sample_cnt == 10 时才更新一次输出，也就是每 10 次扫描才产生一个有效值。 而扫描放在 SysTick 的 1 ms 分支里 → 实际采样率 100 Hz。 第二版状态机沿用了这个节奏，所以消抖时间用的是"get_us_cnt() 实际时间差"而不是"扫描次数"——这是对的（不依赖调用频率）。

问题一眼可见：三份逻辑完全相同、只有"阈值常量"和"状态变量"不同的代码。 这类代码的三个典型危害：

  1. 改一个 bug 要改三处（漏一处就变成"只有 KEY2 好使"这种诡异现象）；

四、7 状态机逐状态解读 ​

4.1 时间参数（三个宏） ​

c
#define ADKEY_PRESS_CONFORM_TIM 30000   // 消抖确认 30 ms
#define ADKEY_LONG_PRESS_TIM    500000  // 长按     500 ms
#define ADKEY_DOUBLE_WAIT_TIM   300000  // 等第二次按下 300 ms
1
2
3

三个时间全部用微秒，靠 get_us_cnt()（第 01 篇的 1 μs 时基）比较， 不依赖"扫描了多少次" —— 这一点很关键：扫描频率从 100 Hz 变成 1 kHz 都不用改参数。

4.2 状态迁移（完整版） ​

状态转移条件去向动作
IDLE|Δ| < 20（进入窗口）PRESS_CONFORM记 pre_time
PRESS_CONFORM30 ms 后仍在窗口PRESS—
30 ms 内出窗口IDLE（判为抖动）
PRESS仍在窗口 且 > 500 msLONG_PRESSon_adkey_long_press()
在 500 ms 内出窗口DOUBLE_WAIT（等一下，看有没有第二次）
LONG_PRESS出窗口IDLE（长按只报一次）
DOUBLE_WAIT300 ms 内又进窗口DOUBLE_PRESS_CONFORM记 pre_time
300 ms 后仍不在窗口IDLE★ on_adkey_click()（单击在这里才报）
DOUBLE_PRESS_CONFORM30 ms 后仍在窗口DOUBLE_PRESS—
30 ms 内出窗口IDLE（判为抖动）
DOUBLE_PRESS500 ms 内出窗口IDLE★ on_adkey_double_click()
> 500 ms 仍在窗口LONG_PRESS★ on_adkey_click_long_press()

|Δ| 即 abs(encode - key->press_encode)。

4.3 三个设计上的巧思（以及一处瑕疵） ​

① 单击"迟到"是故意的：按下 → 松开后不立刻报单击，而是进 DOUBLE_WAIT 等 300 ms； 等不到第二次才报 on_adkey_click()。 这是"单击/双击不能同时立刻确认"的本质：双击的代价就是单击要延迟一个等待窗口（300 ms 是取舍点）。

② 长按"只报一次"：进 LONG_PRESS 后不再重复回调，直到松开才回 IDLE。 否则按住不动会每秒报几十次（这类"连发"如果不需要，就不要做）。

③ "单击+长按"组合：DOUBLE_PRESS 下继续按住 500 ms 会报 on_adkey_click_long_press() ——即"单击一次后按住不放"这个动作。这是三个动作（单击/双击/长按）之外的第四个事件， 在遥控器类产品里常用来进"设置模式"。

④ 瑕疵：ADKEY_PRESS 里用的是两个 if 而不是 if/else if

c
case ADKEY_PRESS:
    if ((abs(encode - key->press_encode) < 20) && ((get_us_cnt() - key->pre_time) > ADKEY_LONG_PRESS_TIM))
    { ... }                       // 长按
    if ((abs(encode - key->press_encode) >= 20) && ((get_us_cnt() - key->pre_time) <= ADKEY_LONG_PRESS_TIM))
    { ... }                       // 松开（短按）

这次没问题（两个条件互斥：一个要求"在窗口内"，一个要求"在窗口外"，不可能同时成立）。 但写成 else if 更安全——将来若有人把两个条件改成不互斥（比如都判"在窗口内"）， 两个分支会同时执行，而这类 bug 极难发现。

六、⚠️ 数组越界：一个必须看懂的 bug ​

6.2 越界有多严重（自己算一遍） ​

adkeys[3..6] 里的 state 字段是内存里的随机值 → 大概率落到 default → 每次扫描都往越界地址写一次。 adkeys[] 是 static，它后面紧跟的就是同一个编译单元或相邻静态变量的数据—— 所以这个 bug 的表现是"别的全局变量莫名其妙被改成 0"（第 27 篇的 encodes[]、第 09 篇的 displayBuffer[] 都在附近）。

这类 bug 的可怕之处：它不会立刻崩，而是让完全不相关的模块行为异常—— 你会去查显示、查 ADC、查串口，唯独想不到是"按键模块在偷偷改它们的内存"。

6.3 为什么 -Wall 不会报警 ​

编译器能查的这个 bug 为什么躲过去
数组下标是编译期常量且越界这里是变量 i，编译期不知道值
for (i = 0; i < sizeof(a); i++) 这类明显的越界ADKEY_LENGTH 是另一个枚举，编译器不认为它与数组有关
GCC -Warray-bounds（需优化 + 常量推导）跨"枚举"和"数组"的语义关联，编译器没有这个知识

换句话说：没有任何编译器选项能可靠地抓住"用错长度"。防它只能靠写法规避。

6.4 正确写法（三选一，推荐第 1 个） ​

c
// ① 用"数组自己的长度"（最稳，改数组不用改循环）
#define ARRAY_LEN(a) (sizeof(a) / sizeof((a)[0]))
for (uint8_t i = 0; i < ARRAY_LEN(adkeys); i++)

// ② 把"按键个数"单独定义一个宏（与状态枚举彻底脱钩）
#define ADKEY_NUM 3
for (uint8_t i = 0; i < ADKEY_NUM; i++)

// ③ 让状态枚举末尾改名叫 ADKEY_STATE_LEN 并加注释"只用于状态计数，不要当数组长度"

6.5 这个 bug 的"教益"（比修法更重要） ​

阶段发生了什么教训
d6e72db三份复制粘贴，没有 bug（每个键一个变量，不存在"长度"概念）重复代码不容易错，但改不动
a1b35d8"精简"成数组 + 循环，引入越界 1 个元素★ 重构本身会引入新 bug；"精简"不是纯收益
d9cabb9加 3 个状态 → ADKEY_LENGTH 4→7，越界扩大到 4 个元素，且没碰循环★ "长度"这种跨语义的耦合，会随着功能增加悄悄恶化

一句话总结：同一个 ADKEY_LENGTH 承担了两种语义—— "状态有几个"（枚举用）和"按键有几个"（数组用）。 一个符号只该有一个含义；一旦它同时回答两个问题，两个问题就会开始互相拖累。 （对照第 26 篇：LED188_PIN_NUM 只表示"引脚个数"，所以 for (i < LED188_PIN_NUM) 是对的 ✓）

七、排查清单 ​

#现象最可能的原因怎么验证
1某个键怎么按都没反应实际 ADC 值没落进 ±20 窗口（电阻误差/供电波动）把 printf 打开看实际码值，与 945/2043/3135 对比
2按键太"钝"（要按很重/很久）窗口太窄（20），或消抖 30 ms 偏长把窗口放宽到 50~80，再试
3一个键触发别的键窗口太宽（跨过了两个键之间的间隔）三个间隔都 >1000，安全；检查是否把 press_encode 写错
4单击经常被识别成"没反应"，但双击正常单击要等 300 ms 才回调 → 不是 bug，是设计若想快点可用"松开即报单击 + 双击再补报"的方案
5显示/LED/其它模块行为莫名其妙★ 第七章的数组越界在改别人的内存把循环上界改成 sizeof(adkeys)/sizeof(adkeys[0])，看现象是否消失
6应用层定义的 on_adkey_double_click() 不生效头文件里没有它的 extern 声明补声明（或确认函数名/签名一致）
7电压读数一直在抖没做中值滤波（0d729ce 那套），或 ADC 采样时间太短见第 27 篇 §5：把采样周期加大
8长按一直重复触发在 LONG_PRESS 里又加了回调本工程只在"进入长按"时报一次 ✓

练习题 ​

  1. 修 bug：用 ARRAY_LEN 宏修掉越界，并给 adkeys[] 加编译期断言（_Static_assert）保证表长与 ADKEY_NUM 一致。
  2. 加第 4 个键：假设分压网络再加一档，写出你要改哪几行（提示：只该改"参数表 + 数量宏"，不该碰状态机）。
  3. 改单击响应速度：实现"松开后立刻报单击，若 300 ms 内又按下则撤回单击改报双击"（提示：需要一个"已报单击"标志）。
  4. 加连发：长按 500 ms 后每 100 ms 报一次 on_adkey_long_repeat()，说清怎么用状态机表达"每隔一段时间"（参考第 05 篇的时间片）。
  5. 从越界里找证据：在 adkeys[] 后面故意加一个 volatile uint32_t canary = 0x5A5A5A5A;，跑起来看它会不会被改（这是排查越界最直接的手段），验证修好之后它保持不变。
  6. 算一遍分压：给定 $R_{up}=10\ \text{k}\Omega$ 与三个下臂电阻，算出三档电压，验证它们与 945/2043/3135 是否吻合（不吻合就去核对原理图）。
