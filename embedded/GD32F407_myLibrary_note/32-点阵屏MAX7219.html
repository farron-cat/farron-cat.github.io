学习目标 ​

  1. 点阵屏里的"段"和"位"分别对应什么？为什么和数码管恰好相反？
  2. MAX7219 的一帧数据是几位？地址占哪几位、数据占哪几位？
  3. 为什么 0x0C 寄存器写 0 会让屏幕"看起来坏了"？
  4. 字模为什么有"窄体"和"满宽"两种？取模方向错了会怎样？
  5. 本工程的点阵屏和数码管共用一组 SPI 引脚，靠什么区分？

一、8×8 点阵怎么亮 ​

1.1 共阴 / 共阳 ​

一块 8×8 点阵内部就是 64 个 LED 排成 8 行 8 列，引出 16 根线（8 行 + 8 列）：

类型行线的极性列线的极性点亮方式
共阴行 = 阴极（接低）列 = 阳极（接高）行拉低、列拉高
共阳行 = 阳极（接高）列 = 阴极（接低）行拉高、列拉低

"共阴/共阳"说的是"LED 的公共端接在哪一侧" —— 和数码管的共阴/共阳是同一个概念（第 09 篇）。

买屏时最容易踩的坑：同一块 8×8 点阵，共阴和共阳的引脚顺序往往是反的。 插上去"该亮的亮成一片、该灭的全亮"——十有八九是共阴/共阳搞错了，不是代码问题。

1.2 ★ 段（Segment）与位（Digit）在点阵里的含义 ​

这是本篇最容易混的一节。教材原话：

如果以 888 数码管为例，段指的是 1 个 8 上的所有灯（A~G + DP 共 8 段）； 如果以点阵屏为例，一行中的灯为段。

位，可以理解为位置……如果以点阵屏为例，表示选择哪一行的灯。

画成表对比：

4 位数码管8×8 点阵
段（Segment）一个"8"字里的 7 段 + 小数点一整行里的 8 个灯
段的编码8 位（A~G,DP），每个 bit 控制一笔8 位，每个 bit 控制这一行的某一个灯
位（Digit）选哪一个"8"（4 个里选 1 个）选哪一行（8 行里选 1 行）
一帧要写几次位数（4 次）行数（8 次）

所以在本工程里：

"位" = 行号（1~8）        → 对应 MAX7219 的寄存器地址 0x01~0x08
"段" = 这一行的 8 个灯     → 对应写进去的 8 位数据
1
2

一句话记住：数码管的"位"是横向的一个字符，点阵的"位"是纵向的一行。 两者的"段"都是"8 个 bit 的位图"，只不过数码管的一个 bit 是一个笔画，点阵的一个 bit 是一个点。

1.3 为什么必须用驱动芯片 ​

如果直接把 64 个 LED 接到 MCU：

做法需要的线问题
64 个 IO 各驱动一个 LED64 根MCU 没有这么多脚
8 行 + 8 列直接驱动（动态扫描）16 根每 1 ms 要人工扫一遍；8×8 全亮时每列平均电流只有 1/8，很暗；还要 8 个限流电阻 + 驱动三极管

MAX7219 把这三件事全包了：

           ┌──────────────────────────────┐
   MCU ────┤ DIN  (数据)                   │
   MCU ────┤ CLK  (时钟)      MAX7219      ├── 8 行 ──┐
   MCU ────┤ LOAD/CS (片选)                ├── 8 列 ──┤  8×8 点阵
           │  内部：8×8 RAM + 扫描 + PWM   │          │
           └──────────────────────────────┘
              ↑ 只用 3 根线，扫描完全由芯片自己做

芯片替你做的四件事：

能力说明
显存内部 8 个字节，一个字节 = 一行的 8 个灯
多路复用扫描芯片自己按 800 Hz 左右轮流点亮 8 行（不用 MCU 管）
亮度调节内部 PWM，16 档（也不需要 MCU 做软件 PWM）
译码器可以把 0~9 直接译成七段码（点阵用不上，要关掉）

这就是"专用芯片 vs 通用 IO"的分界：MCU 只负责"把一帧画面推过去"，刷新这件事交给芯片。 对比第 30 篇的 WS2812——那个芯片没有显存，必须 MCU 自己按 1.25 µs 的时序推位流； 而 MAX7219 有显存，推完就不用管了（display() 之后 MCU 可以去做别的）。

二、MAX7219 做了什么 ​

2.1 内部结构 ​

关键点：显存是"掉电保持"的——你写一次 display()，芯片会一直扫下去，MCU 不用管。

2.2 16 位数据帧 ​

一次完整的写操作 = 16 个时钟：

位D15D14D13D12D11D10D9D8D7…D0
含义← 寄存器地址（4 位）→← 无关位（手册标 X）→← 数据（8 位）→

本工程用"两次 8 位写"拼出这 16 位：

c
static void Write_Max7219(uint8_t address, uint8_t dat)
{
    MAX7219_CS(0);               // ① LOAD/CS 拉低，开始一帧
    Write_Max7219_byte(address); // ② 先发地址（高 8 位）
    Write_Max7219_byte(dat);     // ③ 再发数据（低 8 位）
    MAX7219_CS(1);               // ④ LOAD 上升沿 → 芯片锁存
}

步骤为什么这么写
① CS 拉低告诉芯片"一帧开始了"，此后 16 个 CLK 都被当成这一帧
② 发地址地址在高 8 位，所以先发
③ 发数据数据在低 8 位，所以后发
④ CS 拉高LOAD 的上升沿才是"生效时刻"——之前发的 16 位只是进了移位寄存器

"先地址后数据"这个顺序是硬件协议规定的，不能反。 而且 CS 必须在 16 个时钟之后才拉高：本工程用"两次 8 位写 + 最后拉高"，正好凑够 16 位 ✅。

一个隐患：如果中途因为异常在两次写之间退出，CS 会一直保持低，下一帧的位就会和这一帧错位。 所以 Write_Max7219() 应该"要么完整发完、要么不发"——本工程的写法是对的（没有中途 return）。

2.3 五个初始化寄存器 ​

c
static void bsp_dot_matrix_max7219_init(void)
{
    unsigned int i = 0;                          // ★ 定义了没用（未使用变量）
    Write_Max7219(0x09, 0x00); // 译码方式：不进行译码

    Write_Max7219(0x0b, 0x07); // 扫描界限；8 个数码管显示
    Write_Max7219(0x0c, 0x01); // 掉电模式：0，普通模式：1
    Write_Max7219(0x0f, 0x00); // 显示测试：1；测试结束，正常显示：0
}

逐条说清"为什么是这个值"（这几行的注释是"抄来的"，含义要自己补）：

寄存器名称写入值含义为什么这么选
0x09Decode Mode（译码方式）0x00不译码，8 位数据 = 8 个点的亮灭点阵要的是"位图"，不是七段码。如果开译码，写 0x05 会变成"显示数字 5"，那就没法画图了
0x0AIntensity（亮度）0x000~15 共 16 档，0 是最暗⚠️ 见下面的警告
0x0BScan Limit（扫描界限）0x07扫描 8 行（0~7）8×8 点阵就是 8 行；少设一行就少亮一行
0x0CShutdown（掉电）0x011 = 正常工作，0 = 掉电（关显示）⚠️ 写 0 屏幕全黑，看起来像"没接好"
0x0FDisplay Test（显示测试）0x000 = 正常显示，1 = 全亮测试测试模式会强行点亮所有点，调试时有用，正式必须关

⚠️ 两个"看起来像坏了"的坑（本篇最重要的排查依据）：

现象原因修法
屏幕全黑，但代码没报错0x0C 写了 0x00（掉电模式）改成 0x01
屏幕亮但极暗，几乎看不见0x0A 写了 0x00（最暗档）改成 0x0F（最亮）或折中的 0x07
所有点全亮，什么都不显示0x0F 写了 0x01（测试模式）改成 0x00

本工程现在是"能亮但最暗"（0x0A = 0x00）。在室内暗环境下能看出字，在亮环境里几乎看不见。 这不是 bug，但是"为什么别人说这屏看不清"的第一嫌疑——0x00 到 0x0F 之间差 16 倍电流。

PA8 在硬件文档里是"空闲引出"的脚 —— 选它不抢任何已有功能 ✅。 这是本工程第一个"先查硬件文档再选脚、并且真的选到空闲脚"的模块（对比：PB8 抢了马达、PB13 抢了 CAN_TX、PB0 抢了 LCD_CS）。

但它同时把 SPI0 的从机数推到了 4 个： PA3(SPI OLED) / PA4(GD25Q32) / LCD(CS 另配) / PA8(MAX7219)。 四个从机共用 SCK/MOSI，靠各自的 CS 区分——所以 msp_spi 里不能有"CS 归一"的假设， 每个器件的 CS 都是自己管的（MAX7219 用 MAX7219_CS()，Flash 用 bsp_flash 里的宏）。

3.4 测试节拍：get_us_cnt() 数 1 秒 ​

c
static uint8_t bsp_dot_matrix_is_1s(void)
{
    static uint64_t last_cnt = 0;
    uint64_t cnt = get_us_cnt();

    if (cnt - last_cnt >= 1000000ULL)   // 1 000 000 µs = 1 s
    {
        last_cnt = cnt;
        return 1;
    }
    return 0;
}

void bsp_dot_matrix_test_tick(void)
{
    static uint16_t number = 0;

    if (bsp_dot_matrix_is_1s())
    {
        number++;
        if (number > 9) number = 0;
        bsp_dot_matrix_display_num(number);
    }
}

三点值得注意：

点说明
用的是"时间戳差值"而不是计数器和第 05/28/29 篇一样：cnt - last_cnt >= 1e6，不会因为主循环慢了而累积误差
uint64_t 的减法last_cnt 是 static，若为 0 则第一次立刻触发一次（上电后 1 帧内就显示 0）——无害
在 FreeRTOS 下 get_us_cnt() 的精度是 1 ms因为 FreeRTOS 版是由 vApplicationTickHook() 每 tick 累加 1000 µs（见第 34 篇），所以"1 秒"实际精度是 ±1 ms，够用

注意它和 taskmanager 的关系：bsp_dot_matrix_test_tick() 被注册成 10 ms 周期的任务（第 33 篇）， 所以"1 秒"的判断实际上每 10 ms 才被检查一次 → 真正触发时刻会有 0~10 ms 的抖动。 要更准，就得把它挂到一个 1 ms 的任务里（或者用软件定时器，见第 35 篇）。

用 0 和 1 对比一下"字形宽度"：

字第一版（窄体）第二版（满宽）
03C 42 42 42 42 42 66 38 → 宽度只占 6 列（0x42 = 0100 0010，两侧留空）3C 7E C3 C3 C3 C3 7E 3C → 宽度占 8 列（0xC3 = 1100 0011，几乎顶满）
138 08 08 08 08 08 08 18 → 一根细竖线 + 底座18 38 78 18 18 18 18 7E → 带斜头 + 横底，更"像字"
笔画粗细1 像素2 像素（0x7E 而不是 0x42）

所以 ae551c1 做的事是：换了一套更粗、更饱满的 8×8 字模。

为什么这件事值得单独提交？ 因为 "码表是数据，不是逻辑"—— 换字模不改一行代码结构，但视觉效果差别巨大（细体在 8×8 上几乎糊成一片）。 这也说明作者是先跑通"能显示"再调"好不好看"——和第 26 篇 188 数码管"先点亮一个段验证接线"是同一个节奏。

取模时最容易错的三件事：

错法现象
位序反了（bit0 当最左）字左右镜像（"1"会跑到右边）
行序反了字上下颠倒
行/列搞反了（按列取模）字转 90° 或变成乱码

判断方法：在纸上画一个"1"，按 8 行 8 列写成二进制，再转成十六进制，和码表逐个比对。 这是"数据对不对"最快的验证方式——比反复烧录快得多。

事实说明

五、三种"显示"方案对照 ​

到这一篇为止，本工程做了 3 套"点/段式"显示（不含 OLED/LCD 那种像素屏）。放在一起看，驱动方式完全不同：

74HC595 数码管（09）188 数码管（26）MAX7219 点阵（32）
器件2 片 74HC595 + 8 位数码管188 型（内部带驱动）MAX7219 + 8×8 点阵
MCU 占用3 根（SER/RCLK/SRCLK）5 根（高阻复用）3 根（CS/CLK/MOSI，且与 SPI 共用）
谁负责扫描★ MCU 自己（SysTick 每 1 ms 刷一位）★ MCU 自己（每 1 ms 推一步）★ MAX7219 自己（MCU 写完就不管）
显存MCU 里的 displayBuffer[8]MCU 里（无缓冲，直接推）芯片内部的 8 字节
显示内容数字（段码）数字（段码）任意图形（位图）
亮度调节无（软件 PWM 可做）无芯片 16 档 PWM
一帧写几次8 位 × 2 字节 = 16 字节5 步8 行 × 2 字节 = 16 字节
MCU 负担高（每 1 ms 一次中断）高（每 1 ms 一步）极低（只在一帧变化时写）
代码位置bsp_digital_ledsbsp_188_ledsbsp_dot_matrix

5.1 从这张表能提炼的一条结论 ​

"选哪种显示方案"的核心不是"分辨率"，而是"谁来承担扫描"：

MCU 扫描（595 / 188）：
    优点 —— 便宜（几毛钱的移位寄存器）、引脚少
    代价 —— 每 1 ms 都要占用一次 CPU（本工程是 SysTick 中断）
             一旦主循环里有长任务，扫描就会被拖慢 → 闪

芯片扫描（MAX7219）：
    优点 —— MCU 只写"发生变化的那一帧"，剩下的全交给芯片
    代价 —— 芯片贵一点、要 3 根线（但可以和别的 SPI 器件共用）

这就是本工程"中断里塞了 3 个扫描"这件事的根源（第 21 篇 §15）： 74HC595 数码管 + 188 数码管 + AD 按键 都靠 1 ms 节拍， 而点阵屏根本不用节拍（bsp_dot_matrix_test_tick() 只是"每秒改一次数字"，不是扫描）。

换句话说：vApplicationTickHook() 里那 3 个扫描（第 34 篇），将来切成独立任务时， 点阵屏不需要切——因为它本来就不在那儿。

5.2 一个反直觉的对照：MAX7219 vs WS2812 ​

MAX7219（本篇）WS2812（30）
线数3 根（CS/CLK/DIN）1 根（DIN）
有显存吗✅ 有（8 字节）❌ 无
MCU 要不要持续伺候❌ 不要✅ 要（每一位都要 1.25 µs 的时序）
能用 SPI 硬件发吗✅ 原生 SPI⚠️ 要用 SPI 位流"凑"时序
谁适合做动画芯片（改显存即可）MCU（每帧重发）

"线少"不等于"省事"：WS2812 用 1 根线换来了"每颗灯都要 MCU 亲自推位"； MAX7219 用 3 根线换来了"芯片自己扫描、自己调亮度"。这是两种典型的工程取舍。

六、遗留问题与隐患 ​

#问题位置说明
1亮度是 0（最暗档）init() 0x0A = 0x0016 档里最暗的一档。室内能看、亮环境几乎看不见。建议 0x07~0x0F
2display_num() 没有边界检查.cnum > 11 时越界读（§4.4）。当前靠上层 if (number > 9) 兜住
3num_display_map 声明 12 行、只填 10 行.c第 11/12 行是全 0，display_num(10/11) 静默全灭
4SPI 时钟可能超规格全局msp_spi 是 SPI0 + SPI_PSC_4 = 84 MHz / 4 = 21 MHz；而 MAX7219 手册的 CLK 上限是 10 MHz。⚠️ 超 2 倍 —— 能跑不等于合规，长线/多片级联时容易出错
5unsigned int i = 0; 未使用init()编译告警（-Wunused-variable）。属于移植残留
6没有菊花链（cascade）支持.c教材讲了"多片级联：前一片 DOUT 接后一片 DIN"，但代码里 display() 只写 8 行 = 一片。多片时要把数据"倒着发"（最后一片先发）

8点阵屏没有"帧缓冲"设计每次 display() 都是"直接写芯片"。没法做局部刷新/动画（改一个点也要重发 8 行）。若要显示动画，应先在 MCU 里维护一份 frame[8]，只写变化的行
9test_tick() 挂在 10 ms 任务里第 33 篇"1 秒"的判断精度实际是 10 ms（§3.4 末尾）
10SPI 从机已达 4 个，但没有互斥保护全局MAX7219 / Flash / SPI-OLED / LCD 共用 SCK/MOSI。FreeRTOS 下如果两个任务同时写 SPI，会互相踩（第 35 篇的互斥量正好能解决）

8.2 练习题 ​

  1. 调亮度：把 0x0A 改成 0x0F，对比 0/7/15 三档的观感，并算出"电流差几倍"。
  2. 补边界检查：给 display_num() 加 if (num > 9) return;，然后故意传 20 验证不再乱码。
  3. 加一个字符：把码表的第 11 行填成字母 A（自己取模），让 display_num(10) 显示 A。
  4. 做帧缓冲：在驱动里加 static uint8_t frame[8]，提供 set_pixel(x, y) / flush()，然后做一个"画一条对角线"的测试——体会"局部刷新"和"整帧重发"的区别。
  5. 菊花链：手上有两片 MAX7219 时，把 display() 改成"从最后一片开始倒着发 16 字节"，做滚动显示。
  6. 降到合规时钟：把 SPI 分频从 SPI_PSC_4 改成 SPI_PSC_8（10.5 MHz），验证显示是否正常，并对照 MAX7219 手册的 tCLK 上限说明为什么。
  7. 改用软件定时器：把这套"每秒加一"改成 FreeRTOS 软件定时器（第 35 篇的 xTimerCreate），比较"10 ms 任务里判断"和"1 s 定时器回调"的抖动差异。
  8. 横向核对：把 09 篇（595）、26 篇（188）、本篇的"扫描责任方"列成表，说明为什么 vApplicationTickHook() 里没有点阵屏的扫描。
