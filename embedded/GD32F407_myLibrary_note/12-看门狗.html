知识点地图 ​

看门狗（Watchdog）
├── 为什么需要看门狗      死机/跑飞/电磁干扰 → 自动复位自恢复，无人值守场景的兜底
├── 本质                  一个倒计时计数器，到 0 就复位
├── 独立看门狗 FWDGT      free watchdog：IRC32K 独立时钟源、12 位递减计数、喂狗无时限
├── 窗口看门狗 WWDGT      window watchdog：APB1 时钟、7 位递减计数、喂狗必须在窗口内
├── 喂狗                  把计数器的值重新装回去（FWDGT）/ 更新计数器（WWDGT）
├── 参数计算              分频 + 重装载值 → 超时时间
├── 窗口区间              [最短喂狗时间, 最长喂狗时间]，太早太晚都复位
├── 两个复位条件          WWDGT：CNT 归 0x3F 复位；窗口内喂狗才算合法
├── 写保护                FWDGT 改参数前要 fwdgt_write_enable()
├── 不可逆                一旦使能，软件无法关闭
└── 使能时机              必须在「主循环能够周期性喂狗」之后才使能

学习目标 ​

  • 说清看门狗解决什么问题，以及「喂狗」到底在做什么
  • 掌握 FWDGT 与 WWDGT 在时钟源、计数器位数、喂狗规则上的区别
  • 会算超时时间：给定分频和重装载值算出复位时间，或反过来
  • 会算窗口看门狗的喂狗窗口区间（最短/最长），并知道为什么要「不早不晚」
  • 理解「喂狗太勤也会复位」这个反直觉的设计意图
  • 知道看门狗一旦使能就无法软件关闭，因此使能位置是个工程决策

一、为什么需要看门狗 ​

1.1 问题：单片机也会「死机」 ​

程序跑飞、陷入死循环、被强电磁干扰打乱状态机——这些情况在实验室里少见，在现场设备里很常见。而现场设备往往是：

装在配电箱里 / 装在野外 / 装在无人值守的机房
        ↓
死机了没人能去按复位键
        ↓
设备一直僵在那儿，直到供电重启
1
2
3
4
5

看门狗就是为这个场景设计的兜底机制：

正常情况下：程序周期性「喂狗」→ 看门狗认为系统活着 → 计数器被不断重置 → 永不超时
异常情况下：程序卡死 → 没人喂狗 → 计数器数到 0 → 硬件强制复位整个系统
1
2

四个价值（教材的总结，值得背）：

价值说明
系统健壮性故障时自动重启，恢复运行
防止死锁死循环、意外暂停能被检测出来
数据完整性避免长期僵死导致关键数据丢失
实时性保障任务没按时完成可以复位重来

1.2 本质：一个倒计时计数器 ​

c
fwdgt_counter_reload();     // 「喂狗」= 把计数器重新装回重装载值
1

一句话记忆：喂狗 = 把炸弹的倒计时拨回去。拨得及时，炸弹永远不炸；不拨了，到点就炸（复位）。

注意一个反直觉点：看门狗的「喂狗」不是「告诉它我很好」，而是「把它重新开始数」。所以喂得对不对，本质是「节奏对不对」。

二、两个看门狗：FWDGT vs WWDGT ​

GD32F4 有两个看门狗，名字和职责都不一样：

独立看门狗 FWDGT窗口看门狗 WWDGT
全称Free Watchdog TimerWindow Watchdog Timer
时钟源IRC32K（内部 32 kHz）独立振荡器APB1 时钟（本工程 42 MHz）
主时钟挂了还工作吗✅ 会（这就是「独立」的含义）❌ 不会（依赖系统时钟）
计数器12 位递减（0 ~ 0xFFF）7 位递减（0x00 ~ 0x7F）
喂狗规则只要在归 0 之前喂就行（无下限）必须在窗口区间内喂（早了晚了都复位）
复位条件计数器递减到 0① 递减到 0x3F ② 在窗口外喂狗
预分频4 / 8 / 16 / 32 / 64 / 128 / 2561 / 2 / 4 / 8（再叠加固定的 ÷4096）
计时精度低（RC 振荡器）高（来自晶振）
适用场景整机兜底：死锁、跑飞、强干扰监控时序严格性：防止程序异常地「跑得太快」
本工程参数PSC_DIV32 + reload 100 → 100 ms0x7F/0x50/DIV1 → 窗口 4.58 ~ 6.24 ms

一句话记住两者分工： FWDGT 管「你还活着吗」，WWDGT 管「你活得是不是太快了」。

#代码作用不做的后果
1rcu_osci_off(RCU_IRC32K) + delay_1ms(1) + rcu_osci_on(...)强制重启内部 32 kHz 振荡器教材版只做 on；本工程先 off 再 on，是为了保证它从确定的状态开始起振

第 3 步 fwdgt_write_enable() 是 FWDGT 特有的坑：教材里用的是 fwdgt_config(reload, psc)（它内部会帮你写使能），本工程改成手动三步调用，所以必须自己写使能。 教材的原话说得很清楚：「使能独立看门狗的寄存器写保护功能可以避免寄存器的值被意外的配置篡改」——这是防跑飞把看门狗参数改掉的安全设计。

这次提交干了一件很重要的「清理」：把上一版（RTC 测试用）的「每 50 轮打印一次时间」整块注释掉了。为什么？看下面这段推理：

如果保留 printf：
  1 秒钟打印 2 行（约 60 字节）
  115200 波特率下发 60 字节 ≈ 60×10/115200 = 5.2 ms   ← 阻塞在串口上
  +
  组合起来，喂狗间隔会从 20 ms 变成 25 ms 以上（还好，没超 100 ms）

表面上看没超时，但风险在于「不可预测」：一旦打印内容变多、或中断占用变长，喂狗间隔就可能越过 100 ms，导致复位。而这类复位特别难查——因为它表现得像「跑一段时间就重启」。

这条经验值得记：看门狗使能之后，任何「不可预测耗时」的操作都是隐患（printf 是典型的）。调试期间要么先关狗，要么确保喂狗路径独立于耗时操作。

那句注释 // 前面的初始化会消耗时间 是全篇最值钱的一行。它解释了为什么必须挪位置：

    做完所有初始化  →  使能看门狗  →  立刻进主循环  →  每 5 ms 喂一次

《用户手册》里的说法是「看门狗一旦启动就必须周期性喂狗」，工程上的推论是：

看门狗必须使能在「此后不会再出现长时间不喂狗」的位置。

这也解释了为什么两次提交里两个看门狗只能启用一个（一个被注释掉）：不是不能同时用，而是当前主循环的喂狗节奏只能服务一种窗口设定。

另一个变化：喂狗周期从 20 ms 改成 5 ms。因为窗口看门狗的合法区间是 4.58 ~ 6.24 ms：

delay_1ms(5)  →  实际喂狗间隔约 5 ms（加上循环开销略多）
                ↓
     4.58 ms ≤ 5 ms ≤ 6.24 ms   ✅ 正好落在窗口中间

2
3

选 5 ms 的原因：窗口宽度只有 1.66 ms（6.24 - 4.58），必须选中间值才不容易因为循环抖动而越界。

为什么要"关一下再开"：IRC32K 是 FWDGT 的唯一时钟源，它可能已经被别的代码以未知状态打开过。 先关再开 + 等稳定标志，能得到一个确定的起点；而 rcu_osci_stab_wait() 失败就 return（不往下配、不使能）， 避免"用一个没起振的时钟去喂狗"——这条防御写得很到位。

⚠️ 但它带来一个跨模块的隐患，必须记住： IRC32K 也是 MCU 内部 RTC 的候选时钟源之一（第 11 篇：RTC_CLOCK_SOURCE 有 IRC32K 这一档）。 本工程 msp_rtc_init(HXTAL) 用的是 HXTAL 分频，所以现在相安无事； 但如果你哪天把 RTC 时钟源改成 IRC32K，那么调用一次 msp_fwdgt_config() 就会把 RTC 的时钟源"重启"一遍 —— 表现为走时突然变快/变慢或跳变。

教训：凡是"关掉某个共享振荡器"的操作，都要先问一句"还有谁在用它"。 （这也是第 23 篇"查手册"里"外设之间共享的资源"那一类问题的实例。）

这次封装顺带说明的一件事：main.c 的整理（067922c，比这次只早 22 分钟）把这两个函数先从 main.c 删掉， 22 分钟后它们才在 Hardware/ 下重生。"先删后建"的迁移顺序在 067922c 与 8115f1f 之间制造了一个不可编译的中间态 （详见第 27 篇 §3.3 的完整分析）。

四、独立看门狗参数计算 ​

4.1 公式 ​

① 计数时钟频率
   f_cnt = f_IRC32K / 预分频系数 = 32000 / 32 = 1000 Hz

② 每个计数的时间
   t_cnt = 1 / f_cnt = 1 ms

③ 超时时间（复位时间）
   T_out = 重装载值 × t_cnt = 100 × 1 ms = 100 ms

4.2 本工程的值 ​

项目值验算
时钟源IRC32K 32 000 Hz—
预分频FWDGT_PSC_DIV3232000 ÷ 32 = 1000 Hz → 1 ms/计数

fwdgt_config(2 * 500, FWDGT_PSC_DIV64);

   → 2 × 500 = 1000 → 2 秒

4.3 12 位计数器的量程 ​

最大超时 = 0xFFF × (256 / f_IRC32K) = 4095 × 8 ms ≈ 32.7 s   （预分频取最大 256）
最小超时 = 1 × (4 / f_IRC32K)        = 1 × 0.125 ms          （预分频取最小 4）
1
2

结论：FWDGT 能覆盖 0.125 ms ~ 32.7 s 的超时范围，对绝大多数应用够用。需要更长就得上 RTC 的唤醒定时器（第 11 篇提到过 RTC 还有这个功能）。

五、窗口看门狗参数计算 ​

5.1 时钟链 ​

WWDGT 时钟 = PCLK1 / 4096 / 预分频

本工程：
  PCLK1 = 168 MHz / 4 = 42 MHz        （APB1 分频系数为 4）
  42 000 000 / 4096 = 10253.90625 Hz   ← 4096 是固定的 12 位分频
  预分频 = DIV1（不再分频）
  → 计数频率 = 10253.90625 Hz
  → 每个计数 = 1 / 10253.90625 = 97.523 μs

/4096 是哪来的？ 窗口看门狗内部有一个固定的 12 位分频器（2^12 = 4096），它是硬件写死的，你只能通过 WWDGT_CFG_PSC_DIVx 在它之后再分频。

值含义
counter = 0x7F重装载值（初始计数值）。7 位递减计数器从 127 开始往下数
window = 0x50窗口下限值。喂狗时如果 CNT > window，直接复位
计数器「危险线」0x3F：CNT 数到 0x3F（即 CNT[6] 被清 0）时复位

5.3 喂狗窗口区间（本节核心） ​

CNT 的变化过程（从右往左递减）：

  CNT = 127 ──────────────────→ 80 ──────────→ 64 ──→ 63(0x3F) ─→ 复位

    刚喂完狗                 窗口下限 WIN    危险线    复位发生
        │                        │              │
        │◄─── 不合法区（太早） ──►│              │
        │                        │◄─ 合法窗口 ─►│
        │                        │              │
        时间起点              t=4.58ms       t=6.24ms

两个时间怎么算出来：

最短喂狗时间（不能早于它，否则 CNT 还在 80 以上）：
    (counter - window) × t_cnt = (127 - 80) × 97.523 μs
                               = 47 × 97.523 μs
                               ≈ 4583.6 μs ≈ 4.58 ms

最长喂狗时间（不能晚于它，否则 CNT 已经数到 0x3F）：
    (counter - 0x3F) × t_cnt  = (127 - 63) × 97.523 μs
                              = 64 × 97.523 μs
                              ≈ 6241.5 μs ≈ 6.24 ms

5.4 喂狗时刻对照表 ​

喂狗间隔结果原因
< 4.58 ms❌ 复位喂得太早，CNT 还大于窗口值
4.58 ~ 6.24 ms✅ 正常落在窗口内
> 6.24 ms❌ 复位喂得太晚，CNT 已数到 0x3F
完全不喂❌ 6.24 ms 后复位同上

本工程选 5 ms（delay_1ms(5)），落在窗口中间偏早的位置。

窗口宽度的意义：本工程窗口只有 6.24 - 4.58 = 1.66 ms，余量很窄。 这意味着主循环里绝对不能出现「偶尔耗时超过 1.66 ms」的操作——包括一次 printf 长字符串（第 04 篇算过：100 字节要 8.7 ms，直接超标 5 倍）。

这就是「窗口看门狗逼着代码必须非阻塞」：它把「不许偷懒」变成了硬件强制。和第 05 篇（流水灯的阻塞坑）、第 09 篇（数码管必须非阻塞扫描）是同一条线索。

六、为什么要有「窗口」——设计意图 ​

看到「喂太勤也复位」这个规则，第一反应都是「这不是找麻烦吗」。它的真实意图是抓住一类特定故障：

假设程序被干扰后，跳进了一个「疯狂喂狗的死循环」：
    while (1) { fwdgt_counter_reload(); }     ← 狗永远不咬人
        ↓
   FWDGT 视角：一直在喂狗，系统「活着」→ 永不复位 → 设备彻底僵死

加了窗口之后：
    喂得太勤 → CNT 还没数下来 → CNT > WIN → 立即复位  ✅ 故障被抓出来了
1
2
3
4
5
6
7

两种看门狗的「防故障类型」对照：

看门狗能抓到什么故障抓不到什么
FWDGT程序卡死、完全不喂狗程序跑飞但仍在喂狗
WWDGT卡死（太晚喂）+ 跑飞但乱喂（太早喂）—

还有一个常见用途：窗口看门狗可以监控任务时序。比如「每 5 ms 必须完成一轮采集」，把窗口设成 4.5~6 ms，就相当于给主循环加了一个「节拍正确性」的硬件检查。

教材的第三种说法（很贴切）：「防止程序异常死循环提早跑完」——即防止程序跑得比设计的快。

喂狗的位置，决定了看门狗能保护到什么。

对比三种放法：

放法保护能力代价

7.2 使能时机的三条规则 ​

规则原因
所有初始化做完之后再使能初始化耗时不确定，可能在开狗后超时（bbce6b7 那句注释就是这条）
使能之后立刻进入喂狗循环中间不要插耗时操作
调试阶段先注释掉看门狗打断点、单步都会让程序停下 → 狗一定咬人（这是初学者最容易被坑的地方）

调试时的经典现象：程序在调试器里单步走，走到一半突然复位、断点丢失、看起来像「芯片坏了」。十有八九是看门狗。

8.3 两个看门狗的选择建议 ​

需求选谁
只想兜底防死机FWDGT（简单、独立时钟源、不用管精确时间）
主时钟可能失效（停振、改频率）FWDGT（WWDGT 依赖 APB1）
要监控任务时序 / 防「跑太快」WWDGT
要长时间超时（> 32 s）都不用，考虑 RTC 唤醒定时器
学习/初学项目建议先用 FWDGT，理解了再上 WWDGT

九、排查清单 ​

现象优先检查
程序跑一会儿就复位（周期固定）喂狗间隔 > 超时时间；或喂狗太勤 < 最短时间（WWDGT 独有）
一开始就反复复位看门狗使能太早，后面的初始化超时了 → 挪到 main() 末尾
烧录后连 printf 都来不及输出就重启同上，且 printf 本身耗时（100 字节 ≈ 8.7 ms）
调试器里单步就复位正常现象——打断点/单步时程序停了，狗必然咬人。调试时先注释掉看门狗
配置了分频和重装载值但超时时间没变FWDGT 忘了 fwdgt_write_enable()（写保护导致配置静默失败）
超时时间差一个数量级预分频/时钟频率算错（IRC32K 按 32 000 算，不是 32 768）
WWDGT 时间怎么算都不对别忘 /4096 这个固定分频；APB1 = 168/4 = 42 MHz
WWDGT 一启动就复位window 值取错：窗口值必须小于 counter、大于 0x3F
改了主循环的延时后行为全变喂狗节奏被改变了 —— 喂狗间隔是硬约束，不能随手改
加了新任务后开始复位新任务耗时把喂狗间隔撑破了窗口/超时 → 让任务非阻塞
看门狗想关掉关不掉设计如此：使能位只能由复位清除。想「关」只能改代码重新烧录
复位原因不明可以用备份寄存器（第 11 篇）记录复位前的状态，或读 RCU_RSTSCK 判断复位来源

十一、练习题 ​

  1. 把 msp_fwdgt_config() 和 msp_wwdgt_config() 抽成 Hardware/msp_wdgt/，接口参照第 11 篇 msp_rtc 的风格（参数化 + 无用例时的默认行为）。
  2. 做一次「故意喂太晚」的实验：把 delay_1ms(5) 改成 delay_1ms(10)，用串口打印或 LED 观察复位周期，验证窗口下限（6.24 ms）。
  3. 做一次「故意喂太早」的实验：把 delay_1ms(5) 删掉（无延时空转喂狗），观察是否立刻复位，验证窗口上限（4.58 ms）。
  4. 实现「任务健康检查式喂狗」：给主循环里的 2~3 个任务各置一个标志，全部正常才喂狗。
  5. 用 RTC 的备份寄存器记录「本次是看门狗复位」，上电后读出来打印，区分「上电复位」和「看门狗复位」。
  6. 同时启用 FWDGT 和 WWDGT（FWDGT 超时改长一些，比如 500 ms），观察两者能否共存、需要注意什么。
  7. 启用 WWDGT 的提前唤醒中断（EWI）：在 CNT = 0x40 时产生中断，在中断里做一点「临终处理」（比如保存状态到 BKP）。
