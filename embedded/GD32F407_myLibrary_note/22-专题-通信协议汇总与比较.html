22 · 专题：笔记中所有通信协议汇总与比较 ​

这是一篇横向比较专题：把本工程用到的三种串行通信协议（USART / I2C / SPI）放在一张表上比，回答"什么时候该用哪一个"。 涉及模块：串口 USART（04、08）、IIC（15、17、18）、SPI（16、18）、以及硬件已有但代码未实现的 CAN / 单总线（20）。 整理日期：2026-10-06

你的情况建议路线

一、先分清"协议的三个层次" ​

通信协议不是一团东西，可以拆成三层看——分清了，比较才有依据：

层次关心什么USARTI2CSPI
物理层（电气）用几根线、什么电平、推挽还是开漏2 线，推挽2 线，开漏 + 上拉4 线，推挽
链路层（帧/时序）怎么分帧、怎么同步、有没有应答起始位+数据位+停止位、无应答起始/地址/数据/ACK/停止CS 选中 + 时钟移入移出、无应答
应用层（语义）字节代表什么自定义（本工程是 printf 和命令）寄存器地址 + 数据命令/地址 + 数据

"应用层"这一层最容易被忽视，却最能决定代码形态：

I2C 器件（PCF8563）：写"寄存器地址"→ 再读写数据      → 接口长得像"读写寄存器"
SPI 器件（OLED/Flash）：拉低 CS → 发命令 → 发数据      → 接口长得像"发命令流"
UART：            没有约定，全靠你自己定协议          → 接口长得像"收发字节"

这解释了为什么三个驱动的 API 长得完全不同： msp_iic_write_nbyte(addr, reg, data, len) / bsp_spi_oled_write_byte(dat, cmd) / send_string(huart, str) —— API 的形态是被协议语义"逼"出来的，不是随便设计的（第 17/18 篇都印证了这一点）。

二、三种协议各是什么（一句话版） ​

先补一个"第四种"：单总线（1-Wire / WS2812）——只有一根数据线，没有时钟线， 靠"高电平持续多久"或"固定时隙"来编码。第 30 篇的 WS2812 就是这一类： 它甚至可以用 SPI 的 MOSI 去"发"（把若干个 SPI 位拼成 1 个单总线位）， 见 第 30 篇。"用 SPI 发别的协议"是嵌入式里很常见的一招。

协议一句话本工程的典型场景
USART / UART两个人打电报：约定好速度，一根线发一根线收，没有时钟线printf 调试输出；与 STC 单片机通信
I2C一条街上喊名字：两根线（时钟+数据），每个设备有地址，喊到谁谁应答PCF8563（RTC）、OLED、触摸屏
SPI一条专线直达：四根线（时钟+双向数据+片选），选中谁就只跟谁说话OLED（SPI 版）、字库芯片、SPI Flash

三条"最本质"的差异（如果只记三条，记这三条）：

本质差异后果
① 有没有时钟线USART 异步 → 双方靠波特率对齐（速度慢且对误差敏感）；I2C/SPI 同步 → 时钟由主机给（快且可靠）
② 有没有地址 / 片选I2C 靠地址（两线挂一串，省引脚）；SPI 靠 CS（一拖多要加引脚，但省掉了地址字节和 ACK）
③ 电气是推挽还是开漏推挽（USART/SPI）→ 边沿陡、快；开漏+上拉（I2C）→ 能"线与"、能多设备共线，但慢

第 ③ 条是全篇最值得记住的因果链：

想"多设备共线" → 必须"线与" → 必须开漏 → 必须有上拉 → 上升沿是 RC 曲线 → 速率受限
反过来：推挽驱动 → 边沿陡 → 可以跑 21 MHz（SPI），但一根线只能接一个从机

SPI 那一列现在挂着四个从机（2026-10-16 之后）： PA5(SCK) / PA7(MOSI) 由 SPI-OLED（CS=PA3）、LCD（CS 另配）、GD25Q32 Flash（CS=PA4）、MAX7219 点阵屏（CS=PA8） 共用， PA6(MISO) 只有 Flash 用。同一时刻只能有一个 CS 有效——这就是 SPI"点对点协议假装多点"的代价（第 24 篇 §7.3）。

★ 四个从机之后，"CS 必须严格一人一根"这件事更关键了： 本工程每个器件自己管自己的 CS（Flash 用 bsp_flash 的宏、点阵用 MAX7219_CS()、OLED 用 PA3）， msp_spi.c 里没有任何"CS 归一"的假设 —— 这是对的（对比 I2C 靠地址，SPI 靠片选）。

I2C 那一列现在挂着四个从机（2026-10-15 之后）：U5 OLED（0x78）、U8 PCF8563（0x51）、U2 SC12B（0x40）、触摸屏。 同样是"一条总线挂多个器件"，两种协议的应对方式完全不同：

I2CSPI
怎么区分从机设备地址（写进每一帧的第 1 个字节）片选 CS（一根独占的线）
加一个器件要多花0 根线（地址就够）1 根线（CS）
代价每帧多 1 字节地址 + 每次都要 ACKCS 线随器件数量线性增长

本工程"4 个 I2C 从机 vs 3 个 SPI 从机"，正好把这两种思路都演了一遍。

注意三处"工程上有意思的差异"：

差异说明
同一份驱动服务两个串口（句柄化）因为串口是"参数化的外设"——参数不同、逻辑一样（第 04 篇的三级台阶）
I2C/SPI 用"宏开关 + 双实现"因为"软件实现"和"硬件实现"逻辑完全不同，无法用参数统一；但对外接口必须一致（第 15/16 篇）
只有串口上了 DMA 和中断因为串口是"数据流"型：字节源源不断、长度不定；I2C/SPI 是"命令-响应"型：一问一答，不值得上 DMA

最后一行是个重要的工程判断："要不要上 DMA/中断"取决于数据是不是"流"。 屏幕刷屏（1024 字节）虽然量大，但它是"一次性写完就结束"，用阻塞式发送也能接受（38 ms，每秒刷一次无所谓）；而串口接收是"随时可能来、长度不定"，不中断就没法处理。

五、选型决策（本章最实用） ​

拿到一个新器件，按四个问题走：

Q1：这个器件板子上有几个同类？
 ├─ 只有一个 / 可以每个独占一组引脚 → 走 Q2
 └─ 需要挂一串（≥3 个，引脚紧张）  → 【I2C】（两线挂一串，靠地址区分）
        （典型：RTC + EEPROM + 传感器 + 小 OLED 挂在同一组 PB6/PB7 上）

Q2：它的数据量大不大？
 ├─ 大（屏幕、Flash、SD 卡、高速 ADC）→ 【SPI】（21 MHz，比 I2C 快两个数量级）
 └─ 小（几十字节/次）                 → 看 Q3

Q3：需要"确认对方收到"吗？
 ├─ 需要（可写寄存器、要求可靠）→ 【I2C】（有 ACK）
 └─ 不需要                     → 【SPI】更简单

Q4：是不是"另一台设备/电脑"要跟我对话？
 └─ 是（PC、蓝牙模组、另一个单片机）→ 【USART】（异步、可远距离、加点校验就很可靠）

六、耗时对比：同样传 1 KB（本章数字最直观） ​

统一算"传 1024 字节"要多久（第 18 篇刷一次 OLED 整屏正好是 1024 字节）：

这三行数字能直接解释工程里的好几个决定：

工程现象用本表解释
printf 输出 60 字节会让看门狗喂狗节奏错位（第 12 篇）串口最慢：60 字节 ≈ 5.2 ms，而 WWDGT 窗口只有 1.66 ms

为什么"串口适合调试、不适合传数据"（第 04 篇）88.9 ms/KB → 1 KB 要近 0.1 秒，数据量一大就崩
为什么给串口上了 DMA（第 08 篇）越慢的总线越要 DMA——因为 CPU 等不起
触摸按键中断里读一次 I2C 就是"几百微秒"（第 31 篇）本表的最低档：软 I2C 每字节 ≈ 36 μs（250 kHz 下 9 个位），读 2 字节寄存器（地址帧 + 寄存器号 + 2 字节数据 ≈ 4 字节）≈ 150 μs —— 这个量级放在中断里，足以把主循环的 I2C 时序打断
SPI Flash 明明跑在 21 MHz，写 10 个字节却要 46 ms（第 24 篇）★ 瓶颈根本不在总线：擦一个 4 KB 扇区是芯片内部的物理时间（typ 45 ms），命令只占 1.5 µs。提高 SPI 时钟对擦写速度毫无帮助

有个反直觉的推论：慢的总线更需要 DMA。 串口每字节约 87 μs，如果 CPU 阻塞着等，浪费巨大；所以第 08 篇给串口上了 DMA。 而 SPI 21 MHz 下一字节约 0.38 μs，阻塞等一会儿其实无所谓——所以本工程的 SPI 至今没上 DMA。 "要不要 DMA"看的是"单字节耗时 × 字节数"是否值得 CPU 去等。

6.1 ★ 第三个维度：协议之外的时间（Flash 这一课） ​

Flash 是本工程第一个"通信极快、任务极慢"的器件，它把"耗时"这件事拆成了两层：

层次时间谁决定提高时钟有用吗
通信时间1 KB ≈ 0.4 ms（21 MHz）总线时钟✅ 有用
器件内部时间擦 4 KB 扇区 ≈ 45 ms；写 1 页 256 B ≈ 0.7 ms器件物理（高压擦写）❌ 完全无用

推论（对"选协议"的直接影响）：

  1. 选 SPI 而不用 I2C/串口的理由，对 Flash 依然成立（读数据、发命令快）；
  2. 但"写操作快不快"跟协议毫无关系——所以"用 Quad-SPI / 更快时钟"只在读的场合有意义；
  3. 真正决定 Flash 用法的是"擦除次数"：能凑满一整个扇区再写，就绝不写第二次（第 24 篇第七章）。
  4. 它引入了第二种"必须等"：第 13 篇把时间分成"硬件时间/软件时间"，这里补上第三类——物理时间（第 13 篇 §7.4）。

一句话总括这个专题：协议决定"每字节多快"，器件决定"每个操作多慢"。 前者可以靠换协议优化，后者只能靠"少做几次"来优化。

七、电气差异：为什么 I2C 慢、SPI 快（因果链） ​

【I2C】必须"多设备共线"
     ↓ 那就必须"线与"（任何一个设备都能拉低，谁也不能强推高）
     ↓ 那就必须"开漏输出 + 上拉电阻"
     ↓ 那上升沿就是"上拉电阻 × 总线电容"的 RC 充电曲线
     ↓ 电阻不能太小（省电 & 驱动能力），电容不能太小（线长/挂载数决定）
     ⇒ 上升时间被限制在百 ns ~ μs 级 ⇒ 速率上限 ≈ 100 k ~ 400 k（快速模式 1 MHz 也吃力）

【SPI】点对点，不需要共线
     ↓ 可以"推挽输出"（主动拉高、主动拉低）
     ↓ 边沿由晶体管驱动，陡得多
     ⇒ 可以跑到几十 MHz（本工程 21 MHz）

I2C 用"软件模拟"很常见（本工程默认就是软件 I2C）——因为开漏 GPIO 就能做，速度也不快，软件能跟上。
SPI 用"软件模拟"就吃亏了——推挽 GPIO 翻转速度受 CPU 限制（几百 kHz ~ 几 MHz），

四种协议的定位对比（补上 CAN 和 1-Wire 会更完整）：

协议线数拓扑速率核心特点典型场景
USART2点对点中（115 k~几 Mbps）简单、异步、无地址调试、模组通信
I2C2多设备总线低（100 k~1 M）有地址、有应答低速器件群
SPI4+CS点对点高（几十 M）快、简单、无应答数据流（屏/Flash）
CAN2（差分）多主总线中（最高 1 Mbps）差分抗干扰、硬件仲裁与重传、错误检测汽车、工业
1-Wire1多设备低一根线供电+通信、严格时序单颗温度传感器

CAN 的独特之处（值得单独记住）：它是本表里唯一"硬件负责可靠性"的协议——自动重传、自动仲裁（谁先说话由硬件决定）、CRC 校验、错误帧。I2C 的 ACK 只确认"收到了"，SPI 和 UART 干脆什么都不保证。 所以"要多节点 + 要可靠"的场合，CAN 是正解；本工程的几个串口通信场景都还没有可靠性要求，所以用 UART 就够了。

九、自测题 ​

  1. 用"线数 / 拓扑 / 寻址 / 同步 / 双工 / 速率 / 电气 / 应答"八个词说出 USART、I2C、SPI 的差别。
  2. 为什么三个驱动的 API 形态完全不同（write_nbyte(addr,reg,...) / write_byte(dat,cmd) / send_string(str)）？这和各协议的"应用层语义"有什么关系？
  3. "I2C 慢、SPI 快"的根因在哪一层？请把因果链完整说一遍。
  4. I2C 为什么必须开漏？开漏带来了什么好处、什么代价？
  5. 同样传 1 KB：USART 115200、I2C 400 kHz、SPI 21 MHz 各要多久？各举一个"这个数字解释了某个工程现象"的例子。
  6. 为什么"越慢的总线越需要 DMA"？为什么本工程的 SPI 至今没上 DMA？
  7. I2C 每字节比 SPI 多 1 位（ACK）——这在传 1 KB 时多花多少时间？
  8. 本工程哪两个器件挂在同一组 I2C 线上？这体现了 I2C 的什么优势？
  9. 本工程 SPI 上挂了屏幕和字库芯片两颗——为什么需要两个 CS？如果只用一根 CS 会怎样？
  10. 如果一个新器件"支持 I2C 也支持 SPI"，你会怎么选？（给出判断步骤）
  11. USART、SPI 都"没有应答"，它们各自靠什么保证可靠？（举本工程的做法）
  12. CAN 和 I2C 都说"多设备总线"，它们的可靠性机制有什么区别？

十、练习题 ​

  1. 做一次实测对比：用逻辑分析仪分别抓 UART 发 10 字节、I2C 发 10 字节、SPI 发 10 字节的波形，量出实际耗时，和第六章的理论值对比。
  2. 算一遍误差：串口 115200 在 APB2（84 MHz）和 APB1（42 MHz）下的实际波特率误差各是多少（第 13 篇 5.9 节有算法），并解释为什么两端误差要"总共小于一定值"。
  3. 换总线实验：把 PCF8563（I2C）换成挂在 SPI 上（假设有 SPI 版本的 RTC 芯片），写出需要改的代码清单，体会"换总线要改哪几层"。
  4. 加一根 CS：在 SPI 总线上再挂一颗 SPI Flash（W25Q），画一张"SPI 总线接线图"，标清 SCK/MOSI/MISO 共用、CS 各自独立。
  5. 补 CAN：按硬件文档的引脚（PB13/PB12 + TJA1050），把 CAN 收发跑通，并和第 04 篇的串口做一次"抗干扰/可靠性"的对比实验（例如故意干扰总线，看谁的误码率低）。
  6. 补单总线：驱动 DHT11（PB15），体会 1-Wire 的"严格时序"——它没有时钟线也没地址，全靠微秒级延时（对比一下：这和软件 I2C 的延时要求有什么异同）。
  7. 写一张自己的对比表：把你手头项目的所有通信器件列出来，按本专题的十一维度填一遍，找出"有没有选错总线"的地方。
