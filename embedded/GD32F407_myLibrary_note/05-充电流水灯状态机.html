一、需求：充电宝的指示灯 ​

想象你手上是一个充电宝，正面有 4 颗 LED。它需要这些行为：

场景表现
没充电（空闲）全部熄灭
正在充电4 颗灯依次点亮→依次熄灭，循环往复，像水在流
电量变化了电量 +1（本工程用按键模拟）
停止充电按当前电量亮起，闪烁 3 次，然后熄灭
想看看还剩多少电按当前电量亮着，持续几秒（第 3 次提交新增）

「电量」在本工程里是假的：battery 从 1 开始，按 KEY2 加 1。真实项目里它应该来自 ADC 采样。用按键模拟传感器输入是学习阶段的常用手法——先把显示逻辑写完，硬件到位再换数据来源。

状态和 LED 的对应关系：

battery亮几颗灯
1LED1
2LED1 LED2
3LED1 LED2 LED3
4LED1 LED2 LED3 LED4

2.1 阻塞到底阻塞了什么 ​

这是本篇最关键的一问。看看当时的 main()：

正常的调度节奏是：每 20 ms 一轮，25 轮（500 ms）处理一次状态机。

一旦按下 KEY1（bsp_battery_flow_start() 被调用），while(1) 就再也回不来了：

时间轴：
main ──扫按键──等待20ms──扫按键──等待20ms── 按下KEY1 → start()
                                              └───────────── 永远卡在这里 ─────────────
                                                流水灯在闪，但：
                                                · bsp_keys_scan() 不再被调用 → 按键全部失灵
                                                · bsp_battery_flow_process() 不再被调用 → 状态机死了
                                                · 串口虽然靠中断还能收，但回调里想做的事全做不了

被卡住的东西后果
按键扫描按 KEY3（停止充电）毫无反应，你没法让流水灯停下来
状态机处理battery_state 改了也没人处理
任何后续功能想加个「充电时打印电量」都做不到

一句话记住：在裸机程序里，任何 while(1) 或长 delay() 都等于「把 CPU 借出去不还」。你的代码不是不能跑，是跑起来就把别人全饿死了。

2.2 这一版留下的正确资产 ​

别以为这版全错，它定下了几个后面一直沿用的设计：

设计说明

flow_flag 与 battery 分离一个表示「流水到第几颗」，一个表示「有几颗电量」——两个概念分开存是后面流水逻辑能对的前提
模块划分业务放 Driver/bsp_battery_flows/（严格说该放 App/，但先用起来）

三、提交 cfb1ea4：改成状态机，不阻塞 ​

提交信息：[更新] 充电流水灯，使用状态机，充电流水灯状态时不阻塞

这是状态机最核心的思想转变：

v1（阻塞版）v2（状态机版）
「开始充电」这个动作立刻开始流水，并一直做下去只改一个变量，然后返回
谁来做具体的事被调用的函数自己process() 每次被调用时做一点
返回时耗时无限长 / 数秒微秒级

「函数只负责改变状态，不负责执行过程」——记住这句话，它是状态机与「顺序流程」最本质的区别。

函数头那行注释「每 500ms 调用一次」非常重要：它约定了 process() 的时间契约。里面的计数逻辑（stoping_cnt >= 6 表示闪 3 次）全部建立在这个前提上。改调用周期，闪烁速度就跟着变——这是这套写法最大的特点，也是最大的隐患（见第七章）。

这两个变量各管什么：

变量含义初值变化
battery当前电量（1~4）1只在 update() 里 +1
flow_flag「水流」当前流到第几颗跟随 battery每次 process() +1，超过 4 就回到 battery

为什么要回到 battery 而不是回到 0/1？ 因为电量本身也要显示——充电时不是从零开始流水，而是从「当前电量」那里开始：

battery = 2 时的流水过程（每 500ms 一帧）：

帧1: flow_flag=2  → LED1 LED2 亮            （显示：2 格电）
帧2: flow_flag=3  → LED1 LED2 LED3 亮       （水流前进）
帧3: flow_flag=4  → LED1~LED4 亮            （满格）
帧4: flow_flag=5→回2 → LED1 LED2 亮         （回到起点）
帧5: 同上循环...

3.4 停止闪烁：用计数器代替 for 循环 ​

v1 里是 for (i = 0; i < 3; i++) { 亮; delay(500); 灭; delay(500); }，搬到状态机里必须换成**「每次调用做一步」**：

c
case STATE_STOPING:

    else
    {
        // 熄灭

把 for 循环翻译成计数的套路：

原来：for (i = 0; i < 3; i++)  { 亮500ms; 灭500ms; }

为什么是 6 而不是 5？ 因为每次 process() 之间隔 500 ms，「亮→灭→亮→灭→亮→灭」正好 6 步。这也是为什么 stoping_cnt 先自增再判断：保证每一步都真的执行过。

一个小瑕疵：这段是「先自增，再判断 >= 6」，和 STATE_SHOW 里「先判断，再自增」的写法不一致（见 6.3）。同一个变量在两条分支里用了两种推进方式，读起来容易绕。

三个周期是怎么凑出来的：

于是两个任务各自有了自己的节拍，互不干扰：

每一轮（20ms）：
   ├── 扫按键（快任务，20ms 一次，保证按键响应及时）
   └── 每 25 轮才做一次状态机（慢任务，500ms 一次，够用就好）

这就是「裸机多任务 / 时间片轮转」的雏形。对比 v1：process() 里的代码和原来的 while(1) 内容几乎一模一样，但因为它「做一步就返回」，主循环又拿到了控制权，按键重新能响应了。

delay_1ms(20) 这种写法也有代价：主循环整体被固定成 20 ms 一轮，如果哪一步耗时超过 20 ms，整个时间基准就漂了。参考笔记 TASK.md 里讲的「用 get_us_cnt() 自己管时间」，就是解决这个问题的下一步进化——本项目在数码管（第 09 篇）和蜂鸣器（第 07 篇）里用上了这种写法。

STATE_SHOW 和 STATE_STOPING 的区别：

STATE_STOPINGSTATE_SHOW
表现闪烁 3 次常亮 一段时间
结束方式闪完自动熄灭（转 IDLE）亮够 3 秒转 IDLE

注意这个 case 的 stoping_cnt 判断在自增之前：

第 1 次调用：cnt=0 → 0<6，不转IDLE → 亮灯 → cnt=1
第 2 次调用：cnt=1 → 1<6，不转IDLE → 亮灯 → cnt=2
...
第 7 次调用：cnt=6 → 6>=6 → 归零 + 转 IDLE（灯没亮，因为已经切状态了）

显示时长 = 6 次 × 500 ms = 3 秒。STATE_SHOW 因为在判断之前就自增，实际是「先亮后自增」，显示 6 帧；而 STATE_STOPING 是「先自增后判断」，亮灭共 6 帧。两种写法都达到了目的，但同一个计数器在两处语义不同，这是后面要清理的债。

六、逐状态解读（最终版） ​

6.1 STATE_IDLE：唯一一个「没内容」的状态 ​

c
case STATE_IDLE:
    bsp_leds_close_all();
    break;
1
2
3

每 500 ms 全灭一次。看着像浪费，其实是对的：它保证从任何状态切到 IDLE 后，屏幕上残留的灯一定会被清掉。状态机里的 IDLE 状态通常承担「归位」职责，不要因为它"什么都不做"就写空。

6.2 STATE_CHARGING：流水 + 显示电量 ​

规则在 3.3 节已经拆过，这里补一个容易忽略的点：

c
if (flow_flag > 3) bsp_leds_open(LED4); else bsp_leds_close(LED4);
1

为什么用 > 而不是 >=？ 因为 flow_flag 表示「水流已经流到第几颗」，而「第几颗要亮」的规则是「编号 ≤ flow_flag 的都亮」：

flow_flag亮的灯表达式判断
1LED1flow_flag > 0 真，flow_flag > 1 假
2LED1 LED2>0 真，>1 真，>2 假
4LED1~LED4全真

如果写成 >=，flow_flag=1 时 LED2 的 1 >= 1 也成立 → 会亮两颗灯，显示就多了一格。

6.3 STATE_STOPING 与 STATE_SHOW：同一个计数器，两种用法 ​

判断时机语义实际帧数
STATE_STOPING先 cnt++，再判断「已经做了几帧」6 帧（亮 3 灭 3）
STATE_SHOW先判断，再 cnt++「已经显示了几帧」6 帧常亮

两处都复用 stoping_cnt，所以从 STOPING 转到 SHOW 时，计数器的残留值会影响 SHOW 的时长。好在 STOPING 结束时会把它清 0，实际不出问题——但这是「靠巧合正确」，不是「靠设计正确」。

七、遗留问题（拿来练手的最好素材） ​

#问题现象改法
1电量是假的bsp_battery_flow_init() 里直接 battery = 1;换成 ADC 采样，bsp_battery_flow_init() 里读一次，update() 里定期刷新
2stoping_cnt 被两个状态共用从 STOPING 切到 SHOW 时计数器残留每个状态用自己的计数器，或进入状态时显式清零
3时间契约写在注释里process() 的注释写「每 500ms 调用一次」；如果主循环里 delay_1ms(20) 改成 10，闪烁就快一倍用 get_us_cnt() 在状态内部自己算时间（参考笔记 TASK.md 第 2.4 节「时间独立管理」）
4bsp_battery_flow_show() 无人调用定义了但没接线绑到 KEY4，或删掉
5业务代码放在 Driver/ 下严格按分层应该放 App/ 或 Middleware/迁移（本工程 App/、Middleware/ 目前是空的）
6battery 无上限按 KEY2 多次会超过 4，flow_flag > 4 的逻辑会错乱battery = (battery % 4) + 1; 或加 if (battery > 4) battery = 4;

第 3 条最值得动手改：把 process() 改成「自己判断时间到没到」，就能彻底摆脱对调用周期的依赖。这也是本工程后续（蜂鸣器 wait_us()、数码管 bsp_digital_leds_scan()）采用的写法。

十、练习题 ​

  1. 给 battery 加上上限保护（最大 4），并让 KEY2 在满格时循环回 1。
  2. 把 bsp_battery_flow_show() 绑到 KEY4 上，验证「按一下亮 3 秒」。
  3. 改造 process() 让它自己管时间：删除主循环里的 cnt >= 25 判断，改成 process() 内部用 get_us_cnt() 判断「距上次处理是否超过 500 ms」。
  4. 仿照参考笔记 TASK.md 第 2.5 节的「任务表 + 调度器」，把「扫按键」「处理状态机」「数码管扫描」组织成一张任务数组，用一个 scheduler_run() 统一调度。
  5. 把电量来源换成按键之外的东西（比如 ADC 采一个电位器），让「显示电量」这个状态真正有意义。
